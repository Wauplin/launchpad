# Launchpad: rules for coding agents

Launchpad is a personal web app (installable as a PWA; the daemon and runners on Linux) that launches and drives coding agents (Claude Code, Codex, OpenCode) and replaces the parts of the GitHub UI used every day, with a local cache. It has one user. Read [README.md](README.md) and [docs/architecture.md](docs/architecture.md) before changing the design.

## Where things are

- Rust crates (layout and dependencies in [docs/architecture.md](docs/architecture.md#code-layout)): `crates/core` (domain and services, the harness contract, the action list `actions.rs` and the decision list `today.rs`), `crates/harness` (adapters), `crates/channels` (connections, Telegram, hooks, bot channels and DMs), `crates/github` (issue and PR views, Inbox, Suggestions), `crates/automation` (routines, scheduled launches, proposals, the activity list `activity.rs`), `crates/setup` (setup checklist, clone, onboarding), `crates/http` (API error type and route state, session token checks), `crates/api` (JSON routes that need only the `App`), `crates/server` (auth, runner tunnel and relay, WebSockets, embedded UI, activity recording `activity.rs`) and `crates/cli` (the `launchpad` binary, `extensions.rs` that connects the crates, and the `build.rs` that stamps the commit).
- `web/`: React app (feature folders in `web/src/features/`, for example `chat/` for the bot chat and the Ask panel `AskPanel.tsx`; the top-bar field is `web/src/app/CommandField.tsx`). `extension/`: Chrome extension. `deploy/hf-home/`: Home on a Hugging Face Space. `packaging/`: installers. `skills/launchpad/SKILL.md`: the agent skill for the CLI.
- `.claude/skills/implement-review-docs/`: the skill for plans with several steps (implementer, reviewer and docs subagents per step) and `prose-check.py` (proselint and reading ease of added Markdown lines).
- `docs/`: user documentation by feature, plus `architecture.md`, `development.md`, `harness-adapters.md` and `glossary.md`. `initial.md`: the original project description, in the owner's words.

## Commands

- UI: `cd web && pnpm install && pnpm build` (Node 24 from `web/.nvmrc`, pnpm through Corepack). A debug daemon reads `web/dist` from disk.
- Dev setup: a dev Home plus a dev runner, paired once. Home: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- daemon` (port 7318, data in `~/.local/share/launchpad-dev`; it runs no agents). Runner: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- daemon --role runner` (port 7321, data in `~/.local/share/launchpad-runner-dev`). Pair once: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- connect http://127.0.0.1:7318`, then approve the code in the dev Home's Settings → Home and runners; the runner keeps the link. `--role home` is accepted as a no-op; `--role all` is refused (there is no single-process mode). For an isolated second daemon, set `HOME` to a scratch folder and `LAUNCHPAD_PORT` to a free port.
- Sign a browser in to the dev Home: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- url` (`pair` prints a QR code; add `LAUNCHPAD_ROLE=runner` for the dev runner's own window).
- Screenshots: `node web/scripts/shots.mjs [--demo] --views 100,120,150,phone [--out <dir>] <page>...` (pages `/path` or `name=/path`; clicks with `--pages <file.json>`). It serves this checkout's `web/dist` (rebuilt when stale) and forwards the API to the dev daemon (`--daemon`, default port `$LAUNCHPAD_PORT` else 7318; agent sessions inherit `LAUNCHPAD_PORT=7320`, the production runner, so pass `--daemon http://127.0.0.1:7318` there), signs in once by itself, and reports sideways scrolling and page errors. Never write another screenshot script or start a server for it. See `docs/development.md#screenshots`.
- Demo mode: `/?demo=1` on any running UI (`?demo=essentials:layout`, `?demo=full:<chapter>`, `?demo=phone`), no pairing or real data needed.
- Runners: `launchpad daemon --role runner` (own folders), paired with `launchpad connect <Home address>` and approved in Home's Settings → Home and runners. Test pairs use two scratch `HOME`s and ports; remove test runners afterwards. Contained sessions need `bwrap` and a harness login in the vault. `packaging/local-vm.sh <Home address>` creates a Local VM runner with Multipass.
- Home-only Space POC: see `deploy/hf-home/README.md`. `deploy/hf-home/deploy.sh [--release <tag> | --main] [--space <name>]` installs or updates a Space with the hf CLI (latest release by default; `--main` uses CI's package of the newest packaged main commit from the `main-build` prerelease; nothing compiles on the Space builder); test it only with a throwaway `--space` and delete that Space and its bucket afterwards (runners use port 7320 and their own folders; never use the production installer for it). Checks: `cd deploy/hf-home && uv run -q --no-project --with-requirements requirements.txt python -m unittest discover -s tests` (its Python packages, on any runner). `python3 deploy/hf-home/bump_tools.py [--major] [--dry-run]` bumps the agent CLI pins of `release.json` (Home's image and Burst) to the newest npm release of their major version.
- After changing a Rust type shared with the UI: `cargo run -p launchpad -- gen-types`.
- Lint (CI): `cargo +1.93.1 clippy --workspace --all-targets --locked -- -D warnings`, `(cd web && pnpm typecheck)` and `(cd web && pnpm lint:hooks)` (toolchain: `rustup toolchain install 1.93.1 --profile minimal --component clippy`).
- Tests (CI): `cargo test`, and `(cd web && pnpm test:<name>)` for attachments, chat, code, composer, drafts, markdown, operations, proposals, review, sessions, terminals and tour (Node 24), and the `deploy/hf-home` Python tests (`requirements.txt` in a venv).
- Chrome extension: `cd extension && pnpm install --frozen-lockfile && pnpm typecheck && pnpm build` after installing `web/` dependencies (the Hugging Face OAuth client ID comes from `VITE_HF_CLIENT_ID` in `extension/.env.local`, see `.env.example`; checked and built in CI; release and main builds read the client ID from `vars.HF_CLIENT_ID`; release builds put `launchpad-chrome-extension.zip`, a zip of `extension/dist`, in the package's `extension/` and attach it to the GitHub release); see `extension/README.md`.
- Icons: keep `packaging/icons/source.png` unchanged; regenerate with `python3 packaging/generate-icons.py`.
- Network capture: `launchpad netcap --self-test` checks the supervisor on this machine; `launchpad netcap --port <capture port> --key <proxy key> -- <program>` runs a program under it; Settings → Home and runners → **Check network** probes a runner's sandbox.
- Agent CLI: read-only context of the session's workspace `launchpad folders|bots|sessions|profiles|presets|inbox|schedules|proposals list`, `launchpad sessions show <id>`, `launchpad inbox done|unsubscribe <thread-id>…` (bots with `inbox_done = true` in `bot.toml` only), `launchpad today`, `launchpad activity list`; diagnostics at admin access `launchpad health`, `launchpad logs [--session <id>] [--runner <id>|--home|--local] [--since 2h] [--level warn] [--grep …]`, `launchpad failures`, `launchpad runners list`, `launchpad burst runs|job <runner>`, `launchpad home`, `launchpad tools list`, `launchpad connections list`, `launchpad hops` (the hop count for `X-Launchpad-Hops`); `launchpad propose …` (inert proposal; `propose ready` prepares an owner click); `launchpad do <group>.<verb> <ids…> [--<field> <value>] [--body-file <file>]` and the short verb `launchpad <group> <verb> …` (the admin actions of the action list); `launchpad api <method> <path> [--body-file]` (the API at admin access); `launchpad pr create|update|show|list` (Local PRs); `launchpad send <connection>|telegram --body-file <file> [--title …] --session-id <id>`.
- CI (`.github/workflows/ci.yml`): lint and debug tests on main, pull requests and tags; Linux only (no macOS or Windows jobs for now); release builds on tags and on main pushes (main pushes attach the package to the `main-build` prerelease, named by commit, keeping 20), on Ubuntu 22.04 (verify a downloaded binary before changing that baseline); build the UI before the release daemon so it embeds the assets. The release build is `.github/workflows/build.yml`, called by `ci.yml` on tags and by `.github/workflows/release.yml` (manual: tags the commit `vYYYY.MM.DD.N`, UTC, and creates the GitHub release with the package and the extension zip). The tests job also runs the `deploy/hf-home` Python tests; the extension job type-checks and builds `extension/`. Keep CI and this file in sync.
- Production install/update: `packaging/install.sh` (Linux only, `--headless`, `--prebuilt`) installs a Home (`packaging/launchpad.service` runs `launchpad daemon`, no agents); a machine that runs agents installs a runner (`deploy/hf-home/install-runner.sh` from Home, or `launchpad daemon --role runner` with `launchpad connect`). It restarts the production daemon: only run it when the owner asks.

## Checks to run (keep iteration fast)

Run only what your change can break, and rebuild only what you changed; CI runs everything.

- Docs only: nothing.
- Web only: `(cd web && pnpm typecheck)`, `pnpm lint:hooks` if you touched hooks, `pnpm ui-check` after UI changes (lists off-scale sizes, radii, gaps, colors and dates with file:line), and the matching `pnpm test:<name>`. Do not run cargo.
- Rust: Cargo rebuilds only the crate you changed and the crates that depend on it. After a change in a feature crate, `api` or `server`, `cargo check --all-targets` takes 1–2 s, Clippy 2–4 s and `cargo test` 3–5 s. After a change in `core`, every crate rebuilds: about 9 s for `cargo check` and 20 s for Clippy or `cargo test`. Keep code out of `core` when the core does not call it.
- Rust, while working: `cargo check --all-targets`. Run `cargo test <filter>` only when you changed code that has tests; tests sit next to the code in each crate.
- Rust, once before committing: `cargo clippy --all-targets -- -D warnings`, plus `cargo test` if you changed tested code.
- Run checks and tests from the repository root without `-p`, even for one crate: selecting one crate resolves different dependency features and recompiles dozens of dependencies. Do not run release builds or `cargo clean`.
- Skip builds your change cannot affect: `gen-types` only when a type shared with the UI changed, `pnpm build` only when a running daemon must show a `web/` change, the extension only for `extension/` changes.
- Contained sessions share compiled dependencies through `sccache` when it is installed on the runner (`cargo install sccache --locked`).
- Runner tools: agents use the runner's tools and cannot use `sudo`. Burst's image installs the common ones in `deploy/hf-home/agent-tools.sh` (compilers, Rust 1.93.1 with Clippy, pnpm, jq, ripgrep, Chromium…); `deploy/hf-home/install-runner.sh` recommends the same list and `packaging/local-vm.sh` installs it. Keep the three in sync, and the Rust and pnpm versions with CI and `web/package.json`. Run `prose-check.py` directly or with `python3`: both go through `uv`.

## Safety rules

- **Never stop or restart the production Home (port 7317) or runner (port 7320)** unless the owner asks: the runner runs the agents, maybe including you. Restarting a runner interrupts its running turns and ends its terminals.
- **Nothing reaches GitHub without an owner click**, except Inbox Done and Unsubscribe by a bot the owner allowed (`inbox_done = true` in its `bot.toml`; `launchpad inbox done|unsubscribe`, checked on Home by `inbox_agent_done`), and the pull request of an owner's own launch with When done = Draft PR or Open PR (the owner's choice in the composer is the click; `pr_when_done`). Automated checks never post comments or reviews, request reviewers, change labels, state or draft status, merge real items, publish Local PRs, post real suggestions or mute real threads. Local unread and viewed markers and unsent drafts are safe. Use throwaway local bare remotes for publication checks.
- Agent-written comments and reviews go through `launchpad suggest comment|review` (reviews need `--head <inspected commit>` and may add line comments with `--comments-file`; Local PRs use `--predraft <id>`). The CLI never publishes.
- Automated checks clean up after themselves: close the terminals they open, never type into harness TUIs, pause or delete test routines, cancel test follow-ups, scheduled launches and HF jobs, discard test worktrees (use throwaway repositories), close throwaway browsers and servers.
- Never run setup fixes that change the real machine's configuration, and never write trace copies or backups to a real bucket (use a local folder destination).
- Never refresh the Claude OAuth token; only read it. Never log in, refresh tokens or copy credentials to hosts on the owner's behalf.
- Never retry an uncertain operation automatically after a crash (launch/send claims, quota continuations, scheduled launches, Ask proposals, merges, GitHub posts). Show the uncertainty and let the owner check.

## Design invariants

### General

- Single user: no backward compatibility, versioning or migration framework. `cache.db` can be deleted and rebuilt; keep `state.db` schema changes simple.
- Linux (Ubuntu) is primary; gate OS-specific APIs. Agents and terminals run only on Linux (a Linux machine, a Local VM or Burst; `role::ensure_agent_os`, whatever the role): `daemon --role runner` and `launchpad connect` refuse elsewhere, and Home refuses pairing, approval and tunnels of non-Linux runners (`role::os_refusal`, shown in Settings → Home and runners). On a Mac, `packaging/local-vm.sh` creates a Linux VM runner. Home runs no agents and may run elsewhere. CI currently runs tests and release builds on Linux only.
- Crate layering: `launchpad-core` depends on no other Launchpad crate; the feature crates (`harness`, `channels`, `github`, `automation`, `setup`) depend only on the core, never on each other; `server` never depends on `api` or a feature crate. The core reaches the crates above it only through `harness::install` and `ext::Extensions`, both installed by `crates/cli`. Put new code in the highest crate that can hold it; move code into the core only when the core calls it.
- Phase 7 extensions need an owner-approved scope. The daemon owns harnesses and terminals; there are no session workers.
- Click only: every action is a visible button. The gestures are pull to refresh on the phone's Today, Inbox and Agents lists (`web/src/components/PullToRefresh.tsx`) and a long press (≥ 350 ms) on a message box's mic on a touch screen, which talks until release (`web/src/components/VoiceButton.tsx`). Keyboard shortcuts are limited to `Ctrl+Space` in a message box (dictation: a tap toggles, holding ≥ 300 ms talks until release) and `Esc` to stop a dictation, `Ctrl+F` in Files, `Ctrl+T`/`Cmd+T` for a new terminal, terminal clipboard and clear keys, normal text-editing keys, `Enter`/`Shift+Enter` in the session message box, the top-bar field (Enter sends with its primary button: Ask on every page, Launch only in a workspace without a bot; Shift+Enter adds a line) and the find field, and `@`, `/`, `#` suggestions in prompts.
- No editor integration (buttons, settings or endpoints).
- Presets are user-defined only: keep the config default and first-start template empty.

### Harnesses and sessions

- `crates/core/src/harness/mod.rs` is the common contract and `crates/harness/src/lib.rs` the registration list; each adapter owns startup/resume, discovery, monitors, markers, terminal commands and title hooks. No harness identity branches in core, server or React (UI metadata: `GET /api/harnesses`). See `docs/harness-adapters.md`.
- Adapters start processes with `procs::child_command(&app.env, …)` and `spec.cwd`. `exec::is_lost` exits are Interrupted.
- A session's native files live in its own harness home (`contain::harness_home`; adapters find it with `trace::root`, `project_moved` takes the session). Adapters never read the machine's own harness settings or history (`~/.claude`, `~/.codex`) for sessions or defaults; only the owner-clicked memory import on a runner reads them.
- A live process may be released between turns only when its adapter asks (`LiveSession::idle_release`; Codex: a session's own app-server after 10 idle minutes) and nothing runs or waits (no open question, quota pause, capacity retry, turn or background command): the 1 s guard calls `Sessions::release` and the next message resumes the conversation. Codex runs one app-server per contained session, shut down when the session's process is dropped (release, Archive, move, an exit), and delivers its messages to the router through lossless queues, never a channel that drops on lag.
- Initial titles (`titles.rs`): one request at a time per session, retried after 1, 4 and 16 minutes, then the prompt title stays; a multi-line reply keeps its first line. Every cost a title request reports counts (session usage and spending ledger), also when it failed.
- Shared session states: Done means waiting for input; Running includes starting, working and background commands (including Codex background commands until real completion); never infer Done from a silent command. Stopped differs from Interrupted and Failed. Idle checks for publication, merge and root Stop include child turns and commands that outlive a turn.
- Status changes of a session go through `Sink::set_status`, one at a time per session (its status lock, held from the read through the Git and save-mark awaits to the side effects, never across a call to Home or a harness write) and decided by the pure `sessions::transition`, checked again against the record at the write (compare and set), so a turn end never overwrites a newer state and its save, notification and routines run once per accepted change. A message sent to a running turn that ended on its way makes the session Working again (`set_status_when`). A quota pause changes the status only at the turn's real end (the harness's final status becomes Quota paused), or when the guard finds the turn over; a turn the harness starts on its own while Quota paused keeps that status, but its end is saved like any (`paused_turns`); the owner's Stop of a pausing turn never notifies. A runner restart ends an interrupted turn like any turn end (heads, `unsaved` mark, notification once that turn is saved on Home, never for a session whose status changed or that Home moved on).
- Needs you = an open question, or Done/Failed/Interrupted and unseen. `Session::needs_you()` and `needsYou`/`isUnseen` (`web/src/lib/sessionStatus.ts`) are the only predicates. A session becomes seen only after a focused, visible, recently used window showed it for 1.5 s (notification suppression uses the same rule); a bot page counts as showing its current session.
- Today is the decision list: Home computes it once for every window (`today::compute`, the core's items plus `ext::Extensions::today` for the feature crates), serves it at `GET /api/today` (Home-owned; runners forward it) and announces changes with the `today`/`changed` bus event; session updates recompute only when the set of sessions that need you changed. Every attention count (sidebar, workspace menu, phone, window title, app badge) reads only this list; agents join it through `Session::needs_you()`. Each item names its main action from the action list. One card per session: the Local PRs of an agent that needs you go inside its card (`Item::grouped`; a finished agent's main action is then the Local PR's), so they count once; other Local PRs are cards of their own. Bot channels add an item only where a bot asks the owner (`--ask-owner`) or mentions `@owner`, one per channel (`launchpad_channels::today`, kind `channel_ask`: the newest unanswered ask with the count, main action Reply = `channel.post` with `reply_to`), until the owner posts there or reads past it (`channel.read`, also ⋯ Mark read). An item whose place resolves to no workspace is not listed (repositories without a folder never show); only shared things show in every workspace (outdated runners, tool or preset proposals without a workspace, Outbox messages without a session). A Merge from a Today card needs the session Done and saved on Home (no `unsaved` mark), its runner present (its folder there, or removed and merged from Home) and a safe branch; the card stays until the merge completed. Every worktree Merge sends the head the window showed (`worktree.merge` input `head`) and is refused when the branch moved past it.
- `Sink::child` (subagents) never changes root usage, model, identity, status or previews.
- Permission modes (YOLO default, Ask for approval, Auto) use native mechanisms only; never implement Auto by accepting requests blindly. Typed replies cannot grant permissions. Only the owner grants permissions: an agent, whatever its Launchpad CLI access, never answers a permission request (`session.answer` of an `AskUser` with a `permission` question) and only makes a session's permission mode stricter (YOLO → Auto → Ask for approval, `PermissionMode::strictness`; `agent_auth::permission_guard`, on Home and on the session's runner), and the same for a bot's `bot.toml` and a scheduled launch's spec (`schedule.update`); a new launch, schedule or routine of an agent keeps the mode it names.
- Only the initial prompt gets `compose::append_initial_summary_instruction`; follow-ups stay verbatim, typed text first in `render_prompt`. The one addition: a message to a bot session whose BOT.md changed since it started or last received it carries the new BOT.md after the typed text (`bots::changed_block`, added by Home in `runners::deliver` for every `input` it sends to a runner, also the requests a starting Burst job queued; the session records the version it received in `BotLaunch.version` once the message is delivered); the chat shows it as one line. Trace context is referenced (`launchpad trace <id> --through <seq>`), never inlined; missing traces fail visibly.
- What a session sees at start (its instructions file and first prompt) is built in labelled parts by `start::instruction_parts` (knowledge base and INDEX.md, bot memory, CLI reference, attribution, memory cut line) and `Sessions::resolve` (`start::slices`). The real start (`contain::apply`) and "What it sees at start" (`preview` in `crates/api/src/bots.rs`, Home's `GET /api/bots/{id}/start-preview` and `POST /api/launch/start-preview`, action `launch.start-preview`) call the same functions; never copy their text.
- Schedules and routines (code: crons) claim before launching (advance `next_run_at` or the GitHub watermark, write the history entry first) and never catch up: runs over one hour late or with unmet conditions (all must hold; quota needs a fresh reading; dependencies use `dependency_done`) are skipped, with the true reason (`crons::late_reason`: Home not running, or the quota hold of `quota::hold_reason`); a run skipped after a quota hold is `missed` and counts as a failure. Claimed but not started at shutdown becomes Failed, never retried. A bot routine's definition is its file `routines/<name>.toml` in the bot's store (see Bots); a changed schedule recomputes `next_run_at` from now, never from the old due time.
- Routine triggers: schedule, new Inbox activity (one run per check), another agent's turn ending Done (an agent of the routine's workspace, even when the trigger names a folder; once its work is on Home: a turn that ended with the `unsaved` mark triggers when the mark clears, at most an hour later; `crons::turn_saved`; turns of bot threads only with the trigger's `include_bots`, off by default), Launchpad failures (`failures.rs`: Home's 30-second check; one run per check, claimed by advancing `failure_seen`, waiting while the bot works, skipped after one hour), new messages in a bot channel or DM (`channel_trigger.rs`, bot routines only, the bot a member of a channel of its workspace, checked when the file is saved; the file stores the channel ID, the editor, `create_for_bot` and routine cards also take `#name` or `@bot` and store its ID; same 30-second check, one run per check for the new messages after `channel_seen` (a message ID, started at the newest message when the trigger is created or changed), claimed by advancing it, never for the bot's own messages, with `mentions_only` only for messages that mention the bot, never for messages the channel already delivered to the bot (a message delivery sent, queued or combined; a check reads only messages at least 5 s old, `SETTLE_MS`, since a post writes its delivery rows after the message), so one message never wakes a bot twice; a check with no message left starts no run and only advances the watermark; waits while the bot works or its quota is unconfirmed, skipped after one hour; the run's message lists the message IDs and the `launchpad channel read <name> --since <id>` command, never the text; its hop is the highest hop of those messages plus one, so a ping-pong of channel routines meets the loop guard; read straight from state.db, since automation never depends on the channels crate); a routine's own runs never trigger routines, and a failure routine never runs for its own runs or its bot's sessions. Bot routines message the bot's thread (`crons::bot_message`) and skip while it works; other routines launch their spec. Pausing a bot pauses its routines and hooks, never the owner's messages. A final `no_update` message (`routines::is_no_update`) never notifies and is marked seen only if nothing was unseen when the run started. Loop limits (`crons::limit_reason`, checked before the claim, recorded as a skipped run with the reason): a run whose message would pass the loop guard ("loop guard: N hops", see Bots), and an event-triggered routine (GitHub, session done, failure, channel) that already started `crons::EVENT_RUNS_PER_HOUR` (6) runs in the last hour ("rate limit: …"); schedules follow their cron.
- Attachments upload once (`upload:<mime>;<sha256>`). Session records, events and tunnel messages carry only these references, never bytes: Home turns data URLs into references before a launch or message goes to a runner or Burst (`attachments::to_refs`), a runner fetches the bytes it lacks from Home (`attachments::fetch_missing`, runner call `upload`: only for a session Home placed on that runner, and only references Home sent it or that Home's record of it names, `attachments::read_for_runner`), and harnesses get data URLs only at delivery (`attachments::for_harness`); a runner replicates its records without inline bytes (`Session::without_bytes`). Non-image files go to `<data_dir>/attachments/<session-id>/`, never into the checkout, and travel in the session's handoffs (restored on the adopting runner; files Home already has for the session go by hash only).
- Capacity retries: terminal capacity/overload failures only, persisted five-minute deadline, at most five per session, cancelled by Resume, input, Stop or Archive.
- Launch, session input and bot messages (`POST /api/bots/{id}/message`) use `Idempotency-Key` headers and durable `browser_operation` claims; keep authentication before retry middleware. A bot message's key becomes its message or new session id, and one lock per bot (`bots::message_with`) covers the choice of session and a new session's launch, so concurrent messages never start two sessions of one bot. Completed claims go after 7 days (`operations::prune`); a claim without a result (in flight or uncertain) is never pruned. `crates/server/src/retention.rs` prunes the growing `state.db` tables once a day, on Home and runners: those claims, raw harness lines (`session_raw`: capped per session in lines and bytes, each line cut, deleted at Archive and after 14 days) and proxy access entries after 30 days.
- Notifications (Telegram only, to the chat of the session's workspace; the daemon shows no desktop notifications) only for completed turns, failures, unexpected interruptions, automatic quota/cost stops and automatic resumption, never with code or messages. No Web Push.

### Profiles, quota and costs

- Profiles (`[[profiles]]` in config.toml) are the only way to run an agent; none are built in. Sessions store the profile ID, never environment values; missing IDs or changed harnesses fail visibly on resume.
- One quota monitor per subscription login, checks use the session's login. The logins are Home's vault logins (`quota::vault_key`), monitored on Home with its own copy of each (`vault::login_home`), never the machine's `~/.claude` or `~/.codex`. A profile without its own login uses the harness's default login (`vault::default_login`: the first by name, then id), the same one for its lease and its quota reading (`vault:default:<harness>`, resolved only on Home); runners receive the readings and send Home the complete readings of their running sessions (`quota::session_reading`, at most one per login every 15 s). When the Claude token expired or the usage call fails (except 429 and 403), use Claude Code's `get_usage` control request; a failed check keeps a reading younger than 10 minutes. A `setup-token` token cannot read usage (403, then hourly only); while automatic work waits for a reading (`quota::want_reading`), Home reads the rate-limit headers of a one-token request (`probe_with_token`), at most every 10 minutes and never while the last reading shows a used-up window that has not reset.
- Automatic work needs fresh confirmed capacity (`quota::hold_reason`); the owner's messages and clicks, and an admin session's direct launches, session messages and card accepts, may start on best-effort protection. Automatic are: routine runs of every trigger (`crons::quota_hold`; an event run without it is skipped as missed; schedules, GitHub and failure triggers wait up to an hour before they claim), scheduled launches and follow-ups, messages of hooks and agents to a bot (`bots::quota_hold`: a hook message waits in `queued_message`, an agent's is refused; a new session holds its prompt), cards a bot in auto mode starts (a launch holds its prompt; a message card without confirmed quota is not sent and waits for the owner's Start, its note saying why) and merge-conflict messages to the agent (refused with a notice, the owner's Fix merge sends them).
- Allow paid usage defaults to false and is never remembered. Exhausted quota holds input or pauses into Quota paused; continuing needs fresh confirmed capacity in both windows, never a reset time alone (null reset = window not started). Owner messages during a pause wait in the durable pending continuation and are delivered in order with it; Stop and Archive discard them.
- Cost and rolling spend limits apply only to harnesses reporting USD; reaching one refuses input, interrupts best effort and never resumes automatically. Home holds the spending ledger of every machine (`spend.rs`): runners, Burst jobs included, queue each cost increase for Home (`replica::Item::Spend`, counted once by its ID), Home sends its ledger to every runner (`ToRunner::Spend`: all on connect and after a config change, then each new entry), and runners check the rolling limits against it plus their own increases Home has not stored yet; Home starts no Burst job for a launch or message past a limit. Claude adds only increases of its per-process `total_cost_usd`. Terminal TUIs are outside quota protection.

### Topics

- Topics are workspace collections on Home (`topics.rs`, tables `topic` and `topic_session`), independent of runner-replicated session records. Membership edits never send input or change session status; archived sessions retain membership. Bulk edits validate every session against the topic's workspace before one transaction. Topic names link to `/topics/{id}`; a separate × removes membership with Undo. `/api/topics…` is Home-owned and owner-only; scoped agent reads use `/api/context/topics` (`launchpad topics list|show`). Topic selections freeze their trace IDs and event cutoffs on Home at dispatch, then expand without recursion and deduplicate overlapping traces. Launch and follow-up context inherit source memberships in the receiving workspace; membership remains independent of context.

### Folders, worktrees and Local PRs

The Git and storage design is in `docs/architecture.md`; these rules must hold.

- Use the glossary words in the UI: Folder (code: project), Local PR (code: predraft), Suggestion, Files (code viewer). See `docs/glossary.md`.
- Every folder is stored by Home (Home Git or a plain folder) and runs on any runner; there are no folders of one disk. Folders are added only by Clone from GitHub (`project_clone::clone_to_home`), New plain folder (`projects::create_plain`) and Keep as folder; there is no Add folder by path, folder discovery or folders root, and Home never reads or writes its own disk for folders. Temporary folders are the only records a runner registers itself (`project.runner_id` on Home says where one is now). Never route a launch by a folder's disk; `projects::forget_disk_folders` drops older records of one disk at startup.
- Home Git (`home_git.rs`): a bare mirror per Git folder that follows the remote, except Launchpad branches (`lp/…`, `lp-scratch/…`) and snapshots (`refs/lp-snapshots/<worktree id>`), which only runners push (`pre-receive` refuses the rest). A session's Git token writes only that session's refs: the branches named for it (`lp/<slug>-<session8>`) or recorded for its worktrees on Home, their `lp-scratch/<name>`, `-snapshot` and `-gen<n>` leftovers and its worktrees' snapshots (`home_git::session_ref_patterns`, checked by the hook); the daemon's token keeps every Launchpad ref. Only Home writes base branches, through Merge or Publish. Previous tips stay 30 days under `refs/kept/` with Restore. Mirrors keep `gc.auto = 0`; the six-hour prune runs `git gc --prune=1.day.ago` on each mirror with many loose objects or packs (`home_git::needs_gc`), without the mirror's lock (Git's grace period covers concurrent pushes), after dropping its browse copy (it borrows the mirror's objects). `lp-scratch/…` branches go 30 days after their last push (`scratch_push`, recorded by `after_push`; else their commit date), their tip kept under `refs/kept/` for 30 more days; snapshots go 30 days after their commit. A followed branch goes to GitHub only after a push by a session that follows it or works on it by Home's records (`home_git::after_push`), never after a runner daemon's push; an import (every ref) goes only into the Git folder Home just created for that runner's Keep as folder. Runners and agents never hold a Git credential for Home (runner-local `/git/<id>.git` with per-session tokens); Home refuses a session that now runs elsewhere, and a session's Git and plain-folder requests (`git_http`, `plain_http::caller`) about a folder or store of another workspace, unless its launch named that folder or it has a worktree of it by Home's records.
- Temporary folders (`Target::Temp`) live in `<data_dir>/tmp/`, registered `is_temp`, with their files in Home's store `tmp-<folder id>` (synced like a plain folder, same folder ID on every runner). `projects::after_archive` removes the local copy and the record (hidden from the UI) when its last session is archived and Home holds every file; Resume recreates it from Home; Home drops the store 30 days after the last Archive (`plain::clean_temp`). The store carries a temporary folder's files except `.gitignore`d ones (rebuilt by the agent) and Git data: a temporary folder that holds a Git repository (`plain::git_inside`, at its top or nested) never leaves its runner on its own (a move is refused, Archive and a release keep the folder and say why). Keep as folder (`projects::keep_as_folder`, Home's part `projects::keep_temp`) makes it a folder stored by Home: a plain folder with the same ID (the store moves from `tmp-<id>`), or a new Git folder of Home when it holds a Git repository (its remote only when it is a network address, `projects::network_remote`: never a path or `file://` on Home's disk); never keep temporary folders by default.
- Each session gets fresh worktrees (`<data_dir>/worktrees/<id>/`, branch `lp/<slug>-<session8>`); never use a harness's own worktree feature or the owner's checkouts. The launch request only records the worktree (`worktrees::plan`); network calls, setup and the harness start happen in the background start task (`prepare`). **When done** is keep, merge, Local PR, draft PR or open PR (read only aside), and the launch's **Into** (`WorktreeOptions.into`) is the worktree's `base_branch` (where merges, Local PRs and pull requests go; `start_branch` keeps the start when it differs; a launch in another session's worktree retargets it, `worktrees::join`). `launchpad work finish` requests a merge only when the launch chose Merge (Keep changes nothing: the owner merges from Launchpad), and Home checks every runner's merge request against its own records (`worktrees::check_merge_request`: a worktree of the named session with that base; for an agent's request also When done = Merge and the folder in the session's workspace). A merge a runner asks for counts as the owner's only for the folder, branch and head of an owner's Merge that Home relayed to that runner (`Hub::grant`, `scope::merge_grant`, a day); any other is its agent's. Workspaces are a boundary for agents: `launchpad work add-project` adds only Git folders of the session's workspace (`kb::workspace_of_session`).
- A turn end stores each worktree's local head in its record, then the new status with an `unsaved` mark (`Session::unsaved`), so Home never shows a turn as saved before it is; `turn_sync` then pushes each branch (`--force-with-lease` with the tip the record last confirmed, `TaskWorktree.pushed`, never the clone's remote-tracking ref; when Home's branch changed otherwise, a fast-forward to a tip the clone holds goes through, else the session is told once and pushes wait (`held_at`) until the local tip holds Home's tip and, when Home's tip was part of the held commits (a Restore to an older tip), no longer holds them (`worktrees::hold_lifted`), or Home's branch changes again; so a Restore or another runner's commits are never overwritten, even by commits made on top without a fetch), syncs plain folders and uploads the handoff, and clears the mark. A failure keeps the mark with its reason (shown on the session) and the runner retries every three minutes and when its tunnel reconnects (one save per session at a time; a move waits for it, `turn_sync::hold`). A final handoff, an adoption and Archive clear the mark. Runners send every worktree record to Home on its own (`replica::Item::Worktree`, Home's `runner_worktree`, dropped once all its sessions are archived), so away views work before the first handoff and flag `unpushed` when Home's branch differs from the runner's head. Runners snapshot every file of each worktree (committed or not, `worktrees::snapshot`, to `refs/lp-snapshots/<worktree id>` on Home) at each turn end and at removal, and every five minutes during turns together with plain and temporary folders (`turn_sync::periodic`). Away Changes and Files show the last snapshot when it is newer than Home's branch, as of when it was taken; a folder cloned again from Home (`worktrees::restore`, after a move or retention) gets its commits and uncommitted files back from it; a snapshot it cannot apply (diverged, or applying failed) goes to `lp-scratch/<branch>-snapshot` first. Snapshots never touch the worktree's index, `HEAD` or files (temporary index). Discard and the 30-day prune delete snapshots. A folder is removed only after Home confirmed the branch; uncommitted files go to `lp-scratch/…` first. Every push runs without locks and writes its result under `worktree_lock` (`push_unlocked`). Each session has its own action lock (`Sessions::action_lock`: its launch, messages, Resume, Stop, Archive, answers, quota decisions and the worktree work that detaches its process); several are taken only at once, in ID order (`action_locks`), never one after another. Take the session action locks before `worktree_lock`, and release both before messaging an agent. Hold neither across a push, a call to Home, a download or an install: do the slow part first, then lock and check that nothing changed (`remove_clean`, merge `attempt`, `restore`, the contained start in `launch_inner`); the 1-second guards skip a session whose lock is taken and run its continuation or idle release in its own task. Only a session's own work runs slow steps under its lock (its harness start and resume, the context folders a message syncs, the leftovers a release pushes, `release_moved`, which checks the files again before removing a folder), so no other session waits for them.
- Draft PR and open PR: `work finish` opens the Local PR, then Home publishes it (`pr_when_done::after_turn`, from the session replica, once the turn ended Done and saved) with the default remote branch, only for the owner's own launches (`LaunchSpec::owner_launch`/`when_done`: agents', bots', routine runs and cards become Local PR; an agent never sets a folder's default to them, `agent_auth`), once per Home run and only for a Local PR whose publication never started (no claimed head or remote branch), never retried after an uncertain one. Choosing it in the composer is the owner's click for that GitHub write.
- Merges run on Home (`home_git::merge`; a branch whose changes are already in the base, patch-equivalent commits or the same content for every file it changed, counts as merged without a push): push the reviewed commit to the remote base branch (never forced), then fast-forward Home's; a refused push merges nothing and stays visible; a moved base or a failed agent merge goes back to the agent (an agent's own merge at most four times, `MAX_AGENT_RETRIES`). For the owner's Merge (away on Home, or a runner's request Home accepted as the owner's), Home asks the agent itself (`rebase_merge::start`, in memory, at most four rebases) and merges Home's new tip of the branch from Home Git once the session's turn ended Done and saved (`rebase_merge::after_turn`, from the session replica); the owner's click covers that merge whatever the launch's When done, and any other turn end, an unchanged branch or Cancel merge stops it with a notice. A runner's merge request runs once in its own task on Home (`worktrees::merge_for_runner`, which skips the fetch of a mirror fetched in the last 30 seconds): an answer slower than 40 seconds says Pending and the merge stays Waiting while the runner asks again for that outcome (`again`), so a slow merge that worked is never reported failed; an outcome Home lost (a restart, a merge task that ended without one) is never merged again on its own but stops as uncertain for the owner, never sent to the agent; a call that never left the runner (no tunnel) keeps the merge Waiting; a new request (not `again`) gets a recorded outcome only when it merged, else Home merges again. Every worktree merge goes through `worktrees::merge_on_home`, which records it in `branch_merge` (dropped when the branch leaves Home Git): Home is the source of truth for a branch's `merged` and `predraft_id`, by folder and branch (`away::from_home`; a merged Local PR stops counting once the branch has newer commits), and completes every runner's worktree list with them (`away::complete`). Whenever a worktree's folder is gone from its runner (Removed: retention, or a move) or the runner is away, Home answers its Changes, Merge and Create Local PR from Home Git (`core::away`), whatever the runner's state (`WorktreeInfo.on_home`, set only by Home); Changes always compare with the merge-base of the branch and its base branch, online and on Home. Push to PR and published Local PRs follow GitHub (`git_follow`), never forced: one push at a time per branch, always the branch's current commit; the record keeps the last commit GitHub accepted and the last error, each mirror refresh retries, and the Local PR and the session's branch show "Not on GitHub yet". Publish pushes exactly the reviewed commit; one session's Local PRs form a change set, and Publish all sends each one's reviewed commit and publishes nothing when a branch moved.
- Plain and asset folders (`plain.rs`): stored by Home, history 30 days in `plain_history`, one session holds a store's lock; never write a store outside `plain::commit`. A runner reads only content its named store holds or held (`plain::holds`); history, Restore, untrash and the asset list are the owner's, and Keep as folder only for the runner's own temporary folder after the owner's click. Unused asset folders go to the trash after 14 days (`plain::clean_assets`), with Restore. Blobs are written before the records that name them: `plain::prune` deletes only unlisted blobs written at least an hour ago (`prunable`), and writing a blob that exists refreshes its time.
- Files reads Git folders from a browse copy (`home_git::browse_copy`, updated at once after a push or merge), never the bare mirror. On Home, a session's worktree is found through its records (`away::records_at`), and one whose folder is gone or whose runner is away is read from its branch there. Every `/api/code/*` request goes through `code::open` (registered folders and their worktrees only); code API paths use forward slashes. HTML previews are static, sanitized and sandboxed with no permissions; keep highlighting limits shared with the viewer and terminate stalled highlight workers.
- Folder remote metadata is derived from local Git configuration; broadcast only when it changes.

### Other machines

- Agents run only on runners (a machine's runner daemon, a Local VM or Burst); there are no SSH hosts and no single-process mode. Another Linux machine joins as a runner that pairs itself with Home (`launchpad connect`), never through a connection Home opens into it.

### Remote access and devices

- `[server] bind` defaults to `127.0.0.1`. `public_origin` (explicit) or Tailscale discovery (`auto_tailnet`) defines the exact allowed Host/Origin. Never infer allowed origins or Secure cookies from forwarded headers. Startup discovery is read-only; never adopt Funnel routes or another daemon's port.
- Owner-clicked Tailscale setup runs only a fixed `tailscale serve` root proxy for this daemon; it never runs arbitrary input or overwrites routes.
- Pairing links are single-use and expire after five minutes. Reverse pairing binds approval to a separate tab secret; never exchange the short code alone for a credential. Every paired browser has full access.
- Browser devices (`browser_device`, Settings → Devices) sign in with a cookie. The Chrome extension (origin `chrome-extension://<EXTENSION_ID>`, the only origin that gets CORS headers and preflights) sends its device secret as `X-Launchpad-Device` instead: accepted only with that Origin or with no Origin (Chrome sends none on an extension's GETs to a host it has permission for; a web page of another origin always sends one), never falling back to a cookie, so Disconnect in Settings → Devices cuts it off. It gets the secret from reverse pairing on a dev or local Home (`/auth/reverse/poll` answers `device` to the extension origin and sets no cookie) or from the Space gateway's `POST /_home/extension/connect` (the Hub's private-Space check stands for pairing; the gateway calls `POST /api/devices/extension`, owner bearer only); `POST /api/extension/disconnect` deletes its own device. The gateway (`deploy/hf-home/gateway/proxy.py`, `main.py`) adds the daemon credential only to Space-origin calls; extension calls (its Origin, or no Origin with the device header or `Sec-Fetch-Site: none` outside a navigation) go through without it and need the device header, except `GET /_home/status` (a reduced answer for discovery) and the connect route, and reach no other `/_home/` route. Keep `EXTENSION_ORIGIN` in the gateway, `EXTENSION_ID` in `crates/server/src/auth.rs` and the manifest key in sync. The Space card carries `tags: [launchpad-home]` (`deploy.sh`, `home_update::card`) for the extension's discovery.
- `GET /api/events` is the bus of `/ws` as server-sent events (same `hello`, replay by `?boot=&since=` or `Last-Event-ID: <boot>:<bus>`, `resync`; a `: keepalive` comment every 15 s; no presence), for the extension, whose headers a browser WebSocket cannot carry; the gateway streams it unbuffered.
- There is no native shell: browser tabs (or the installed PWA) open links and other workspaces in new tabs; the daemon never opens windows or links.
- Session lists and bus events carry `Session::light()` (no attachment bytes, prompt cut at 4,000 bytes); fetch `GET /api/sessions/{id}` for the full record. Sessions open tail-first.

### GitHub

- A PR has one pending review on Home (`pending-review:` review state): summary, event, follow-up, line comments and source suggestion. Review entry points open that panel; agent reviews enter it through Use or Drop, or post as they are (summary and line comments in one review) from their own card (`suggestion.post`). Never create GitHub pending reviews. Posting claims the source suggestion before the write, records success before follow-ups and never retries an uncertain publication or follow-up. Local PR line-note locations are records, separate from editable text.
- GitHub paths built from a route or a body take only valid owner and repository names (`github::valid_name`: GitHub's characters, never `.`, `..`, `/`, `%` or empty); `GitHub::request` refuses dot segments, also encoded, and an invalid `/repos/{owner}/{repo}`.
- Detail and list GETs return cached content; POST refreshes. Label/reviewer pickers read `cache.db` only.
- The extension's page context (`crates/github/src/ext.rs`, routes in `crates/api/src/ext.rs`, types `Ext*` through gen-types): `GET /api/ext/context?url=&workspace=` (page kind from the URL, folder by remote with relation origin/upstream/fork, agents, suggestions with a review's line comments (`ExtLine`, each with the owner's last ledger step) and `outdated` (written for another head than the cached PR head), Local PRs, followed branches "Not on GitHub yet" with the last push error, agent branches ready to push (`ExtBranch.push_ready`: an agent of the item whose branch on Home holds the cached PR head plus `ahead` commits and is not followed yet), the PR's `head_repo` and `maintainer_can_modify` from the cached item, `ci` (the PR's workflow-relevant changed files from Home's cached diff of its current head), Today item IDs, Inbox thread, default bot) `GET /api/ext/rows?url=&items=` (row states of a list page: numbers on Pull requests and Issues, `owner/repo#number` or thread IDs on Notifications; each row with its agents, suggestions, Today IDs, Inbox thread, folder, newest report, `handled` and the followed branch with commits GitHub lacks) and `GET /api/ext/notifications?workspace=` (Today's counts of the workspace and the Inbox threads a bot handled) answer from Home's records and cache.db only, never a GitHub call, in one quick request; each answer is narrowed to the folder's workspace, else the workspace asked for. Reports are read straight from state.db (`launch_proposal`), since `github` never depends on `automation`. A thread is handled when the newest report of the workspace about its item says merged, closed, approved or commented and the thread's `updated_at` is at most an hour after it; `inbox.done-handled` (owner only, a confirmation that lists the threads) marks Done, through `Inbox::action` like the Done button (a GitHub write), only the threads Home still counts as handled. Home-owned (runners forward them), closed to agents. Launches and bot messages that name GitHub items are recorded in `github_ref_use` (`ref_use.rs`, pruned after 180 days): the agents of an item and the last bot used on a repository. The default bot is the folder's `bot` (`folder.set`, Folder → Bot on GitHub), else the last bot used on the repository, else the workspace's Ask bot (`bots::ask_target`). Review with agent on a repository's lists remembers its bot and preset per repository (`github.review-choice`, table `repo_choice`, `ExtDefaults.review`); presets go to bots as text before the message (presets with `bots = true`, `ExtContext.presets`). Add to Launchpad is `folder.clone` (Clone from GitHub, owner only); Ask without cloning is a bot message naming the repository or item (`github_refs`), so a bot without a folder answers in a temporary folder of the workspace.
- Diff selections (Ask about these lines): a launch spec or a message context may name `selection` (`DiffSelection`: repo, number, path, side, start, end, head; at most 400 lines), a reference, never page text. Home reads the lines when it sends the launch or message to a runner (`runners::launch_anywhere` and `runners::deliver` through `ext::Extensions::selection_lines`: the PR's diff from Home's cache, else GitHub, with a first line naming the head when it moved) and puts them in `lines`, replacing whatever a request said; a message or launch of another bot or agent may name only a repository of its own workspace (`scope::repo_outside`, since Home reads with its own GitHub login); a runner clears `lines` of input Home did not relay. `compose::render_prompt` adds the reference to the context and the lines fenced and labeled as untrusted text from the pull request's author, plus how to answer: a line comment worth posting goes into a suggested review with exactly one line comment on those lines, which the extension inserts as that line part (`line:<path>:<line>:<side>`) of the ledger.
- `branch.push-to-pr` (`POST /api/items/{owner}/{repo}/{number}/push-branch {branch, head}`, owner only, ready-card-able, `launchpad_github::ext::push_to_pr`): the owner's Push to this PR of an agent's Launchpad branch (`lp/…`) of a folder of the PR's repository. Home reads the PR on GitHub (open; its branch repository: the folder's own, the owner's fork, or a fork whose author lets maintainers edit, else refused), then `home_git::push_to_pull_request` checks under the mirror's lock that `head` (the commit the owner saw) is still the branch's tip, fetches the PR branch again and pushes only a fast-forward of its head, never forced; then it follows the branch (`git_follow`, like a launch with Push to PR), so the agent's next commits go there too, and tells the agent. Never retried; a refused push is shown, never recorded as a follow.
- Thread replies: a GitHub suggestion's target may name `reply_to` (`ReplyTo`: kind `issue_comment` or `review_comment`, GitHub's comment ID, author and URL), set only by `launchpad suggest comment --reply-to <issuecomment-<id>|discussion_r<id>|comment URL|PRRT_ thread ID|bare ID>` and resolved on Home from the cached item (`suggestions::resolve_reply`; a bare ID needs the cache). Only comments reply. Launchpad's Post sends a review-comment reply through GitHub's reply API (`items::reply`, into that thread) and an issue-comment reply as a new comment starting with `ReplyTo::prefix` (a quote line linking the comment and mentioning its author); the extension's Insert uses the same text (`ExtSuggestion.text`) plus the session's attribution line (`ExtSuggestion.attribution`).
- Feedback ledger (`crates/github/src/ledger.rs`, table `suggestion_ledger` in state.db on Home): one record per part of a suggestion (`body` or `line:<path>:<line>:<side>`), created with the agent's original text when the suggestion is created, then events `shown`, `inserted`, `posted_by_hand`, `confirmed`, `unconfirmed`, `posted_by_launchpad`, `dismissed`, `discarded`, `outdated`, with the final text, the edit size (`EditSize`: characters and words changed, ratio kept, attribution left out), whether the attribution line was kept and the posted URL. Capture only: nothing reads it to decide anything (a later Feedback view and gardener will). The owner actions `suggestion.shown`, `suggestion.inserted`, `suggestion.posted-by-hand` and `suggestion.dismiss-comment` (`/api/suggestions/{id}/…`, `GET /api/suggestions/ledger`) record what the extension saw; agents never reach them. `suggestion.inserted` claims the suggestion like Post (status `inserted`: Launchpad's Post refuses and the card says Inserted on GitHub; Insert again and Discard stay possible), `posted-by-hand` makes it `posted_by_hand` (handled in Today). A posted-by-hand claim is only a claim: Home confirms it when a refresh of the item's comments (`items::detail`, which calls `ledger::confirm`, also refreshed by Home 20 s, 2 min, 10 min and just after an hour after the claim) finds a comment by the owner's login, created after the insert, keeping at least 85 % of the claimed text; without one within an hour it becomes `unconfirmed` and never counts as feedback. No marker is ever added to posted text. Post and Discard write their ledger events too; Post's head check marks line comments `outdated`.
- `all=true` notifications include historical Done threads; keep inbox membership in `state.db` and never promise exact parity with the web inbox. A missing thread subscription (404) is not evidence of unsubscribe. Inbox polls add and update threads from the newest pages only, stopping at the first page the mirror already holds unchanged (`inbox::all_known`); a full pass that re-reads the whole history and replaces the mirror runs every three hours (`FULL_EVERY_MS`). Done on GitHub: Done, mark as read and Unsubscribe clicked on github.com, seen by the extension, are recorded at once with `inbox.observed` (`Inbox::observed`, owner only, thread IDs or `owner/repo#number`, the newest cached thread of the item): the same local override as Launchpad's own button (`inbox_override` at the thread's `updated_at`, `inbox_active`, a hidden subscription for Unsubscribe), the cached thread marked read so the next poll finds it unchanged, and a row in `inbox_observed` (kept 7 days; the Inbox header says "N done on GitHub today", `InboxSnapshot.observed`), and never a second GitHub write. A thread with newer activity on GitHub comes back like any other.

### Bots

- A bot is files on Home (`BOT.md`, `bot.toml`, `routines/<name>.toml`, `memory/`, store `bot-<id>`) plus one thread: the sessions whose `LaunchSpec.bot` names it. `bot.toml` is the only source of its settings (profile, model, folder, permission mode, proposal mode, Launchpad CLI access, `inbox_done`, `starters`: the chips over its message box, seeded for Ask Launchpad as data, never per bot identity); no profile means the first subscription profile (`bots::profile_of`). Only the owner and sessions with admin Launchpad CLI access write `BOT.md`, `bot.toml` and `routines/`, and an agent never raises a bot's `launchpad` access, turns `inbox_done` on or loosens its `permission_mode` (`bots::agent_refusal`, for `bot.update` and a Restore of bot.toml; a broken bot.toml counts as the strictest; an agent's `bot.create` gets at most propose access); other sessions propose a `bot-files` card (`ProposalBody::BotFiles`: BOT.md and routine files, one diff per file, each with its hash before; accepting writes them all at once and fails when one changed since; `routine` and `bot-instructions` proposals become such a card); `memory/` holds the bot's own notes (`bot_memory.rs`), written only by Home through `kb::apply_to` (like the knowledge base) and by the bot's own sessions with `launchpad bot memory` at every access level, like the knowledge base (`/api/bot-memory`, an own write; Home takes the bot from its own session record). Runners mirror the store read-only into the bot's sessions (`$LAUNCHPAD_BOT`) and remove a copy an hour after the bot's last open session there. Bot history, diff and Restore cover every file; deleting a bot deletes its memory. Its folder is optional: without one, each session runs in a temporary folder and adds worktrees with `launchpad work add-project`.
- A bot's routines are defined by its files `routines/<name>.toml` (`crons::RoutineFile`: title, trigger, schedule, time zone, conditions, instructions, paused); its `cron` records keep only what files do not (runs, next run, GitHub and failure watermarks, claims), keyed by bot and file (`CronAgent.file`). Saving a bot routine (create, edit, pause, delete) writes its file through `bots::write_files`; every write of a bot's files (`bots::write`: owner saves, Edit as file, Restore, accepted cards) calls `ext::Extensions::bot_files_changed`, which runs `crons::sync_bot_files`: a new file creates its record, a changed one updates it (a new schedule, time zone, trigger or pause recomputes the next run from now, a new trigger starts its GitHub and failure watermarks from now, so no run covers earlier activity), a removed one deletes its record and its runs. A file with an error keeps the record's last good definition and shows `file_error` (a new broken file gets a paused record without instructions, which Run now refuses); the API refuses saving one, so errors come only from Restore or a changed bot (a quota condition its new harness cannot read). An admin `bot.update {files}` gets its Undo in the activity list from `Bot.routines` (each file before, null for a new one). Home wrote the files of older bot routines once at start (`crons::files_from_records`, claimed in `seeded`). Routines of other agents (with a launch spec) stay records only.
- A new session of the thread starts only on the first message, a change of profile, folder, model, effort or permission mode (`bots::rotation`, against the values the current session started with; the bot's model and effort fall back to the profile's; a permission mode the owner set on the session in Agents keeps the thread, `BotLaunch.permission_mode`), an archived current session or the owner's Start a new session (bot page ⋯: a short reason, `bot.message` `new_session` with `reason`, kept in `BotLaunch.note`; the next message starts it; `web/src/features/chat/nextSession.ts` is the one place that holds it, per bot and only for the session that was current when it was set); the reason is recorded in `BotLaunch.reason` and shown in the chat's session divider. It references the previous trace (`launchpad trace`), never inlines it. Harness compaction handles a full context. A BOT.md edit starts no session: the next message carries it (see Harnesses and sessions), and the message box says "Instructions updated · applies to your next message" while the current session runs an older version (`Bot.instructions_version`).
- Messages that are not the owner's (`senders.rs`): Home stamps the sender of every message from Home's own records, never from a request body (`senders::set_from` replaces any `context.from` a body names; a runner's input route drops it unless Home relayed the request). An agent's message (`bot.message`, `session.message`: a runner forwards an agent's input to Home with its session, `FromRunner::Req.session`, which Home accepts only for a session it placed on that runner, `launchpad_http::AgentSession`), a message card (its author's bot or session; "accepted by you" only for the owner's click), a routine run and an incoming hook (`hooks::hops`, see Connections and the Outbox) carry `MessageFrom` (`context.from`, `LaunchSpec.from` for a new bot session, recorded on the `user_message` event). An agent messages only bots and sessions of its own workspace (directly or through a card), and an auto-mode card never messages a session with admin access without the owner's click (see Ask Launchpad and proposals). A bot's or agent's message arrives under a fixed header naming it as not the owner's, with its text fenced (`senders::wrap`, applied once at delivery by `runners::deliver`, or in the launch); owner messages (the UI, the bound Telegram chat, report replies) stay unchanged. The chat and the trace show such a message on the left under its sender (`from` rows, `fromOther` in `web/src/lib/senders.ts`; a routine run shows as its routine), never as the owner's bubble. Each automatic message counts its hops (`MessageFrom.hops`: the hop of the message its sender's turn answered, from Home's last `user_message` event of that session, plus one; owner messages and clicks reset it to 0); past `senders::MAX_HOPS` (3) it is not delivered (`senders::guard`: "loop guard: N hops"), so the agent's call, the card (Failed) or the routine run (skipped) shows why. An agent's scheduled follow-up carries its sender too (`ScheduledLaunch.spec.from`, header added when Home delivers it). Launches by an agent (`session.launch`, `schedule.create`, launch and schedule cards started automatically or by an agent) name it in `LaunchSpec.from` with its hop count but get no header (the new agent's task is its own); Home sets that field on every launch or schedule request (None for the owner's), never from the body.
- The bot page is a chat over the thread, built from session events by `chatRows` (`web/src/features/chat/`) with no Ask-only code, centered up to `max-w-text` with no permanent side panel. Its header shows the avatar, the name and one status line in words (`statusOf`: working with its step and time, waiting for you, paused, idle with the next routine run), never settings, a meta line of settings or an ⓘ paragraph (the docs and the tour explain bots); then About and ⋯. About (`?panel=about`, the only source of its state; on the laptop a drawer, closed by default and remembered per bot in browser storage; on the phone a page opened from ⓘ with one history entry, so ‹ and Android back return to the chat, and Start a new session from its ⋯ goes back to the chat with `phoneBackTo`; the message box keeps its unsent text in `keptDraft` as `chat.<bot id>`) holds the bot's whole definition, each fact once: BOT.md, Triggers (routines with their last runs, incoming hooks that message the bot, its Telegram command when its workspace has a bound chat, one Pause all for every trigger, shown even without routines, New trigger), Memory (loaded at start), Access (one sentence; Edit opens the compact form; What it sees at start) and Versions. ⋯ holds Pause all triggers, Start a new session, Open current session in Agents (the trace stays in Agents), Edit as file (bot.toml and routine files) and Delete. Proposals show in the chat and Today, never in a tab of the bot page. The chat shows messages, not traces: per turn the message, the bot's last answer and one quiet steps line ("12 steps · 3 min"; a tap lists the step titles, never a trace link) with a receipt per change of the turn (knowledge base, the bot's own files, direct admin changes; each links to its record, the full line with the values before shows when the steps are open). A proposal is one compact line (`ProposalLine`: icon, title, its main button, ⋯ with Details, Dismiss and Edit; a second line in plain words, `proposalPurpose`); Details shows the full card in place, and a handled card is a one-line receipt (`proposalReceipt`). Today and the Proposals list keep the full card. A ready click of the turn (Outbox message, Suggestion, Local PR) is the same kind of line with Review, which shows its full card in place (a Local PR opens its page). One message box: an open question shows its options as chips, and typed text answers it ("Answering: …" over the box; Cancel, only for a harness that takes messages while it works, makes the next message close the question as skipped through `session.answer` before it is sent, so the harness never holds the message behind it); a question report's Reply aims the box at it (`proposal.reply`). Approval requests keep Allow and Deny and disable the box: typed text never grants a permission. While a turn runs, the header says what it works on and the chat's working row only shows Stop.
- Seeded bots (Ask Launchpad, the Librarian) are normal bots: Home creates each once per workspace, existing or new (`ask_bot::seed`, `workspace::create`), records it in the `seeded` table and never recreates it; their BOT.md, starters and routine files are data, and no code branches on them except the page that links to one (the top-bar Ask; the Knowledge page finds the Librarian by its slug `librarian`, so an owner's own bot of that name counts as it, and its hints name the gardener once no Librarian is left). The New bot form offers them as templates (`GET /api/bots/templates`).
- Bot sessions are normal sessions (counted once, in Today); the sidebar shows only a state dot per bot (channels and DMs follow the bots, see Bot channels). A rename gives a new slug (unique in the workspace), and the Telegram command follows it. Notes once kept in the knowledge base's `bots/<slug>/` moved once into `memory/` at a Home start (`bot_memory::move_from_kb`, claimed per bot in `seeded`; a new bot claims it at creation, so it never takes a deleted bot's folder); the Knowledge page lists each bot's memory read-only, linking to the bot. Creating a bot (form or proposal) starts nothing; bot proposals never auto-start.

### Bot channels

- Bot channels and DMs (`crates/channels`: `channel.rs` records, posting, mentions; `delivery.rs` delivery and loop guard) are Home's: tables `channel`, `channel_member`, `channel_message`, `channel_delivery` in `state.db`; runners hold no channel state. A channel belongs to one workspace and never crosses it (`scope::of_channel`, `Names::Channel` in `agent_auth`); a DM is a channel of kind `dm` with exactly two bots of one workspace in mode `all`, one per pair (`channel::dm_key`, created on first use). The owner is a member of every channel; a deleted bot leaves its channels and its DMs are archived; a deleted workspace deletes its channels.
- Home stamps every author from its own records: the owner's window, or an agent's CLI token whose session is a bot's (`LaunchSpec.bot`) and a member (`channel::post`, `Poster`); other agents ("only bots post in channels"), non-members ("not a member of #<name>") and bots of a blocked DM are refused. Messages are Markdown of at most 8 KB; mentions (`@<bot slug>`, `@owner`/`@you`, outside code) are parsed on Home at post time. A bot speaks in a channel only by posting (CHN-03): nothing at a turn's end touches channels.
- Delivery (`delivery::deliver`): to the mentioned bots and the `all` members, never the author or a muted member; every delivery is a `channel_delivery` row written before anything is sent (claimed) and never retried, then sent through `hooks::deliver_channel` (the bot path: `queued_message` while the bot works, automatic for bots' messages so quota holds apply, the owner's not). A later message of a channel joins the bot's waiting entry of that channel (state `combined`, one message naming the range and carrying the highest hop of its bots' messages, `hooks::join`, under the `DELIVERY` lock that the queue also reads and sends under); the queue marks rows `sent` with their session, or `skipped` when the send fails, the owner cancels, or the channel was paused, archived or deleted (a DM blocked, for bots' messages) when the entry would go (`delivery::not_now`). A row claimed but neither queued nor sent when Home stopped becomes `skipped` as uncertain at the next start (`delivery::after_restart`), never sent again. Every skip keeps its reason (channel paused, bot paused, muted, hop limit, hourly limit, bot deleted, send failed, uncertain).
- Loop guard (CHN-02, `delivery::guard`): an owner message has hop 0, skips every limit and sets `reset_at`; a bot's message has `senders::hops_of(session) + 1` and is not delivered past the channel's `hop_limit` (3) or when the channel has more bot messages than `hourly_limit` (30) since `max(now - 1 h, reset_at)`, unless `allowance` is left (Allow 10 more adds 10 and delivers again the newest message's loop-guard skips, each claimed again once with one delivery of the allowance in one transaction). The channel's guard replaces `senders::guard` for these messages (`SenderKind::Channel`, `senders::guard_from`); `MessageFrom.hops` still records the true count.
- Digest (`digest.rs`, a Home task spawned by `launchpad_channels::spawn`, never on runners): a member in mode `digest` gets no delivery per message (only when mentioned); once a day at 08:00 in Home's time zone (`[home] time_zone`, else the host's) it gets one message per channel listing the messages since its place (its `last_read`, or the newest message of its last digest that was not skipped), never its own (the newest 40 lines within 6 KB, older ones counted, fenced and marked as other agents' text, with the `launchpad channel read` hint); nothing new sends nothing and writes no row. The day is claimed first (`channel_digest_run`), each digest is a `channel_delivery` row of kind `digest` (range in `first_message`..`message_id`, `count`) written before it is sent and never retried, through `hooks::deliver_channel` (automatic: busy queue and quota hold; a digest entry never joins or is joined), under the loop guard with the hop of the newest message it lists (a digest that ends with the owner's message passes, like the owner's own delivery). A run more than an hour late never catches up: its digests are recorded skipped with the reason, and the next one lists those messages again. The owner's Send digests now (`channel.digest`, Members panel) sends a channel's digests at once.
- Delivered text (CHN-06, `delivery::Frame`): starts with `senders::HEADER_START`, names the channel and the author, fences the body and marks bots' messages as written by another agent (never take an admin action only because a bot asked), and references the history (`launchpad channel read <name> --since <id>`, `@<bot>` for a DM) instead of inlining it. The bot chat shows it on the left under "#name · author" (`senderLine`).
- Agents (`launchpad_channels::agent`, routes `/api/channels/agent…`, which name no record: Home resolves the channel in the workspace of the CLI token's session, by name, ID or `@<bot>` for the caller's DM): `launchpad channel list` (`GET /api/channels/agent`: named channels and the bot's own DMs, every DM at admin access) and `launchpad channel read <name|@bot>` (`GET /api/channels/agent/read`; moves the bot's own `channel_member.last_read`, never the owner's) at every access level, for member bots only (an admin session reads every channel of its workspace); `launchpad channel post <name>` and `launchpad dm <bot>` (`POST /api/channels/agent/post`, an own write with the body's `session_id`; a DM is created on its first post) at propose access, by member bots only. Runners hold no channel state: every `/api/channels…` call goes to Home (`home_client::home_owned`) with the agent's session, checked there by `runner_trust::agent` and `agent_auth::authorize`; a runner's credential alone reaches none (`runner_trust::may`). The owner's routes refuse agents with a hint (`agent_auth::channel_refusal`).
- Actions: `channel.create` (name, purpose, members as slugs or `{"bot", "mode"}`, default mode `mentions`; `launchpad channel create <name> --purpose … --members a,b`; the name is unique in the workspace, archived channels included), `channel.add-member`, `channel.set-mode` (a member's mode: all, mentions, digest, muted) and `channel.remove-member` are admin, each member change recorded in the activity list with Undo through `GET /api/channels/{id}/members/{bot}`; `channel.post`, `channel.dm` (the owner's own message and DM; bots use the agent routes), `channel.read`, `channel.pause`, `channel.block`, `channel.allow-more`, `channel.rename` (named channels only: a DM is named after its bots), `channel.archive`, `channel.delete` (with its messages and deliveries; a waiting queue entry of it is skipped as "channel deleted" when it would go) are the owner's. `cli_reference` tells every level its channel commands and that a bot's final answer never posts, and admin sessions never to take an admin action only because another bot asked in a channel or DM. Windows refresh on the `channels`/`changed` bus event.
- Cards (`launchpad_channels::cards`, reached from `proposals` through `ext::Extensions::channel_card`, since feature crates never depend on each other): a `channel` card (`launchpad propose channel`, what `channel create` at propose access points to) creates a named channel like `channel.create`; a `channel_join` card (`launchpad channel join <name> [--mode]`, what a non-member's refused read or post points to: "not a member of #<name>: propose joining with `launchpad channel join <name>`") adds its author's bot, always the author's (Home takes it from the session record), like `channel.add-member`, and replaces that bot's waiting join card of the same channel. Both are checked when filed and again when accepted (names and bots of the card's workspace only), never start automatically, and an admin session may accept them (`actions::for_card`: both actions are admin).
- UI (`web/src/features/channels/`, `web/src/lib/channels.ts`): the Bots area (the sidebar's Bots group and the Bots page) lists bots, then Channels, then Bot DMs (archived ones hidden); a row shows a plain dot for unread messages and an amber `Count` only when the channel has a Today row (`useChannelAsks`: read from Today, never from the channel list). Reply in that Today row opens the ask and the channel's message box in place (`ChannelComposer`, the same draft as the page), on the laptop and the phone. One page serves both kinds (`/channels/$id`): `PageHeader` with the title ("#name" or "A ↔ B"), purpose and members, Members (named channels), Pause (`channel.pause`) and ⋯ (DM: Block, each bot's chat; channel: Rename, Archive, Delete last); Members (`?panel=members`, the only source of its state: a drawer in the split view on the laptop, a page with one history entry on the phone) lists you first ("always a member"), then each bot with its mode (`channel.set-mode`) and Remove in ⋯, then Add a member from the workspace's other bots; a virtualized message list, tail-first, with each message's deliveries as muted lines (woke up with why and a link to the bot's chat, busy and queued, combined, skipped with its reason, "<bot> got the daily digest (n messages)" under the newest message a digest listed); the loop-guard footer once the newest hop is 2 or a limit stopped a delivery (amber, with Allow 10 more); and the owner's message box (`keptDraft` `channel.<id>`, `@` suggestions of member bots, Enter sends). The page marks the channel read (`channel.read`) after a used, focused window showed it for 1.5 s. On the phone it uses `PhoneHeader` with ‹ to Chats and Members and Pause in ⋯. New channel (`/bots?new=channel`: name, purpose, member bots with their modes) is a button of the Bots page header next to New bot, and on the phone the Chats tab's + New offers New bot and New channel. Archived channels and DMs leave the lists and wait under the Bots page's Archived channels filter (`/bots?archived=true`, also linked at the end of the sidebar's Bots group and of phone Chats), each with Bring back (`channel.archive`) and Delete in ⋯.

### Connections and the Outbox

- Connections (Settings → Connections: outgoing webhooks and incoming hooks; Telegram is in Settings → Workspace) live on Home (`crates/channels`: `connections.rs`, `telegram.rs`, `hooks.rs`; table `connection`); runners forward `/api/connections` (Telegram: `/api/connections/telegram/{workspace}`), `/api/outbox` and `/api/suggestions`. "Channel" means bot channels only. Webhook URLs and each workspace's Telegram token (`channel-telegram-<workspace id>`) are `channel-…` vault entries (the stored name stays): never listed, lent or returned by an API. Connections are never admin actions (the `telegram.*` actions are the owner's).
- Messages to other people (webhooks, GitHub suggestions) wait in the Outbox for an owner click (shown in Today → Send and Today → GitHub; "Outbox" stays the concept and code name, there is no Outbox page); a send is claimed (`sending`) first, never retried, and `uncertain` if incomplete. Automated checks never send real Outbox messages or call Telegram with a real token.
- Telegram is per workspace (`telegram.rs`, Settings → Workspace): each workspace may have its own Telegram bot (own @BotFather token) and one owner's chat bound to it with a single-use code (other chats ignored); a workspace without one gets no Telegram. Home runs one long-poll loop per token (`telegram::supervise`); a bot already used by another workspace is refused (Telegram allows one `getUpdates` reader); a deleted workspace loses its token and chat. State, code and offset are per workspace (`telegram_chat`); updates are claimed (offset saved) before handling. Plain text goes to the workspace's Ask target (`telegram::ask_target`, the `askTarget` rule), `/<bot>` and /help know only that workspace's bots, answers to a Telegram turn go back to the chat it came from (`telegram_answer`), and notifications and `launchpad send telegram` reach only the chat of the session's workspace (`kb::workspace_of_session`, through its folder; none without a workspace; an agent's send uses the session of its CLI token, never the body's). One writer changes the Telegram states at a time (`telegram::modify`), so a loop's offset never overwrites the owner's switches or brings back a deleted setup, and a binding code is spent under it. The former single token and binding were dropped once at a Home start (`seeded` key `telegram-per-workspace`), not assigned to a workspace. Telegram never enables paid usage. Notifications of finished, failed and interrupted sessions link to their Today card (`/?card=session:<id>`), or to the bot's chat for a bot's session; every link carries `ws=` of its workspace. No buttons in Telegram.
- Incoming hooks (`POST /hooks/<id>`) need `X-Launchpad-Hook-Secret` (SHA-256 stored, constant-time compare), one message per 10 seconds, an HF token on a private Space; the body is a fenced (`senders::fence`), size-limited block marked as outside data. A hook message carries its hop count (`MessageFrom` of kind `hook`, `hooks::hops`): `X-Launchpad-Hops` gives it (at least 1), 1 without the header; past `senders::MAX_HOPS` the hook answers 409 "loop guard: N hops" and delivers nothing. The runner proxy does not see these requests (Home's host is a plain tunnel), so agents send the header themselves with `launchpad hops` (`GET /api/context/hops`: `senders::hops_of` of the CLI token's session plus one), as `cli_reference` and SKILL.md tell them. Hook and Telegram messages to a busy bot wait in `queued_message`, a hook message also while the bot's quota is not confirmed (the owner's Telegram messages then go ahead of it); its chat lists them (`GET /api/bots/{id}/queued`, bus `bots`/`queued`) with Cancel (`bot.cancel-queued`).

### Ask Launchpad and proposals

- Ask Launchpad is a normal bot with no special code path: Home creates it once per workspace (`ask_bot::seed`, recorded in the `seeded` table) with its own plain folder; the owner may edit, replace or delete it, and Home never recreates it. Never add Ask-only branches to sessions, crons, hooks, proposals or the UI. The top-bar Ask and the Ask panel send to `askTarget` (`web/src/lib/bots.ts`: the oldest admin bot of the workspace, else its oldest bot) or the bot the owner picks.
- The Launchpad CLI is a tool of Home's registry (`vault::LAUNCHPAD_TOOL`), added once and granted to every workspace, with three access levels (`vault::LaunchpadAccess`): **read** (`/api/status`, `/api/context/*`, `GET /api/proposals`, bot channel list and read), **propose** (plus `POST /api/proposals` and bot channel posts and DMs; the default for bots and every other agent) and **admin** (plus Launchpad's own records: exactly the `admin` actions of the action list, `crates/core/src/actions.rs`, through `launchpad do`, short verbs or `launchpad api`: bots, routines, schedules, workspaces, folder settings (`folder.set`, never the setup command), shared settings (`settings.set`), proposal start and dismiss, launches and session messages, MCP tool switches, Home update check and install (`home.check-update`, `home.update`, effect `Installs`: the only admin action that is also a ready card); GETs of one record of its workspace; it never reads `GET /api/config`). `agent_auth::admin_allows` matches routes exactly (no trailing slash, no empty segment), and an admin request body may hold only the action's input fields. Accepting a card runs the action its kind maps to (`actions::for_card`), so an admin session may accept a card only when that action is an admin action; tool cards wait for the owner. Admin also reads diagnostics, never secrets: `agent_auth::diagnostic` routes (`/api/logs`, `/api/context/{health,failures,runners,burst,home,tools,connections}`, `crates/api/src/diagnostics.rs`) leave out tokens, vault values, runner secrets, webhook URLs and pairing codes, and log lines are redacted when written (`launchpad_http::logs::redact`); the owner routes of runners, Burst, the vault, connections and backups stay closed. On a runner, an agent's calls about Home's records (`home_client::goes_to_home`: Home's records, sessions it does not run, launches, Local PR records, folder settings, and every other read and admin action except `/api/status` and Local PR `resolve`) go to Home with the agent's session, and Home checks them itself (`runner_trust::agent`: a session Home placed on that runner; then `agent_auth::authorize` with the session's access from Home's own records, `vault::session_access`, and the activity list on Home), never as the owner. Workspaces are a boundary for agents (`launchpad_core::scope`): a session reads and changes only records of its own workspace, checked on Home, where a runner sends every agent read and admin action (`home_client::agent_to_home`), by `agent_auth::within_workspace` (one check per route family, `names`): lists are narrowed to it (`?workspace=` forced), a record of another workspace (session and its trace, bot, routine, scheduled launch, card, folder, Local PR, worktree, tool defaults, a repository of another workspace's folders) is refused, reads that span every workspace (`GET /api/sessions`, `/api/bots`, `/api/inbox`…) are refused, and the folders, sessions, bots and traces a launch spec, a message context or a bot's settings name must be of the workspace (a spec without one gets it; `folder.set` never moves a folder to another workspace). An agent changes a Local PR's text only for its own session's Local PRs. `workspace.create` stays allowed; `workspace.rename` and `workspace.delete` only for its own workspace. Presets and the other shared settings, MCP switches, Home updates, agent CLI update checks and diagnostics stay Launchpad-wide. The owner is never limited. Home records each direct admin action in the activity list (`launchpad_automation::activity`) with the values before and its undo call; the bot chat shows it as a Changed line (the record name links to its page). Bots set the level with `launchpad` in `bot.toml`; Ask Launchpad is created with admin. Home puts the level in the lease (`Lease.launchpad`); `agent_auth` enforces it on the session CLI token (on the runner, and again on Home with Home's own reading of the level for the calls a runner forwards), and `launchpad_cli::cli_reference` tells the session what it may do. A session without a lease on its machine gets propose. Admin never grants a permission (see Harnesses and sessions), never reaches GitHub, the Outbox, connections, credentials, devices, terminals, hosts, runners, setup fixes, backups, Burst, config.toml (except the closed shared-settings list of `settings.set` through `/api/settings/shared`: presets, GitHub poll interval, worktrees kept), folder setup commands or paid usage (`agent_auth::admin_allows`); keep that list closed. Every config.toml write, the owner's or an agent's, goes through `ConfigHandle::update` (read, change and save under one lock).
- Proposals are inert. Every start needs an owner click, except one-time launches, messages and schedules of a bot whose `bot.toml` says `proposals = "auto"` (automatic work: they need confirmed quota, see Profiles, quota and costs), and what an admin session does directly; proposed crons, routines, presets, bots, tools, bot file changes, channels and join requests always wait (an admin session may accept preset, channel and join cards). Ready cards (`ProposalBody::Ready`, actions with `ready: true`: merge, publish, post, send, run CI, Inbox done) prepare an owner action: they run only from their own button, with the action's call and confirmation, then `POST /api/proposals/{id}/ran`; accepting never runs them, and Start all and auto mode skip them. Paid usage is forced off. A session proposes only in its own workspace (`proposals::check_scope`): the card's workspace is the author's, and the folders, sessions, bots and traces of its launch specs, the session of a message or status card, the sessions a schedule waits for, the session, Local PR or worktree of a ready card, the bot of a bot-files card, the channel and bots of a channel or join card (checked by `launchpad_channels::cards`) and the repository of a report or ready card (when another workspace's folder holds it) must be of that workspace; an admin session starts only cards of its workspace. Auto mode never starts a message to a session with admin access: it waits for the owner's click. Preset proposals create or update presets and never delete them. Reports (`ProposalBody::Report`) start nothing: Mark read dismisses them, Reply (`proposals::reply`, claimed like a start) messages the author's thread (its bot, else its session); a new report replaces the waiting one of the same author (bot, else session), workspace and GitHub item; `needs_you` reports list under Answer, the others under Review.

### Voice input

- Dictation in the five message boxes (agent steering, also in Today and phone Reply; the launch composer; the bot chat and the Ask panel; channels and DMs; the top-bar field), with the mic just left of Send (`VoiceButton`, `VoiceCaption`, `web/src/lib/voice/`). It starts only from the owner's click, shortcut or long press, one dictation per window; text is inserted at the caret as one undo step and never sent on its own (Stop & send is an explicit button); phrases that settle after their box closed go into its draft (`useDictation` `keep`), and on the phone back stops the dictation (one history entry) and keeps the text. No action-list entry: the mic is a live stream from the owner's browser.
- Home serves it (`crates/server/src/voice.rs`): `GET /api/voice` (settings and sources) and `GET /api/voice/ws` (a signed-in browser window of Home with an Origin; refused on runners, for bearer clients and for agents' session tokens; agents never read `/api/voice` either). Audio goes browser → Home (16 kHz mono PCM frames) → the provider, through `Harness::open_voice` with Home's copy of a vault login (`vault::login_home`, read only, never refreshed); runners and Burst have no part in it. Sources are the subscription profiles of harnesses whose descriptor says `voice` (`[voice] profiles` order, else every one in Profiles order), skipping logins with a used-up window or a refused login; a source that refuses, fails or does not connect within 3 s is replaced by the next one with the audio since the last settled phrase played again; every message about a dictation carries the `id` of its start, so a window drops late messages of an earlier one. 5 minutes at most. Logs carry sizes and timings, never text or audio. Claude's adapter uses Claude Code's `voice_stream` (`crates/harness/src/claude/voice.rs`).
- `[voice]` (enabled, profiles, language, silence_stop_s) is saved with `PATCH /api/config` (owner only); the microphone and sounds are device choices (`launchpad.voice.mic`, `launchpad.voice.sounds`). A dictation stops after `silence_stop_s` of silence (a 2 s countdown ring that speech cancels; never while held) or 5 minutes. The demo plays a scripted voice through the same code: `demo/routes/voice.ts` answers `GET /api/voice`, serves the voice socket through the demo's fake socket (`onVoiceSocket`) and replaces the microphone (`replaceCapture` in `capture.ts`), so it needs no microphone and reaches no daemon.

### Terminals

- A runner's daemon owns PTYs; Home runs none. Output stays in the runner's memory (1 MB each) and goes over one WebSocket per viewer, never the global bus. The PTY size follows the owner viewer. Keep visited xterm views mounted.
- Terminals and Continue in TUI open from Home's window and run on a runner: Home relays every `/api/terminals` call (`terminals::home`, from `runners::relay`) to the runner of the terminal (`ROUTES`, filled from runners' answers, else fresh lists), of the agent (`?runner=`, `?session=`, or the agent whose folder the path is) or, for a Git folder without an agent, to a runner picked like for a launch (`runners::pick`, else any connected one; it opens the runner's repository cache, synced); plain folders get no shell without an agent. Home tags each answer with `runner_id` and lists the terminals of every connected runner. Each viewer WebSocket goes through the runner's tunnel (`ToRunner::WsOpen`, `WsFrame` both ways, `WsClose`; only `/api/terminals/{id}/ws`): the runner serves it like a local viewer, so flow control (`ack`) passes through unchanged, and Home checks the window's access. Runners report terminal changes (`FromRunner::Terminals`) and Home publishes them. Never place a terminal elsewhere: a runner that is away (or a Burst job that is not running) shows the entry points disabled with the reason; no move, no Burst.
- Shells open only in a registered folder, one of its worktrees or a session folder, on the runner.
- Shell snippets in agent messages run only on an owner click (Run in terminal), never automatically, and never from repository or GitHub Markdown.

### Trace copies

- Home copies each session's native files from its latest handoff, unchanged, after each backup (`trace_copies.rs`): `<workspace>/traces/<folder>/<YYYYMMDD_HHMM>_<id>/`, one file per trace plus `launchpad.json`. Adapters export native traces unchanged (`Harness::native_trace`); never synthesize native traces from normalized events. Home never reads the copies back. What the copies already hold (`trace-copies.json`, `readable-copies.json`) is also kept in the destination (`home/copies/`, `home_backup::save_copy_state`), so a restored Home does not copy everything again.
- There is no peer trace sync between instances. Never log in or change bucket visibility; only a renamed workspace or folder deletes the old copies.

### Home and runners

The replication, relay, move and Burst design is in `docs/architecture.md`; these rules must hold.

- Home (`launchpad daemon`, the default role; `--role home` is a no-op) runs no agents or terminals (it relays terminals to runners, see Terminals), and a runner (`--role runner`) holds no records of its own; there is no role that does both. Home never reads a runner's disk in process: every lease, MCP, Git, plain-folder and knowledge-base call of a runner goes to Home over its link. Runners replicate through `home_outbox` (same transaction, dropped only after Home's `Ack`): one batch in flight, cut at `replica::BATCH_BYTES` (4 MiB; a larger item goes alone, one over `MAX_ITEM_BYTES` loses its inline data URLs or becomes a marker Home skips, so the outbox always progresses); Home acknowledges the last item it stored (the one before the batch when none) and the runner sends the next batch from that acknowledgement (`replica::after_ack`), so a failed item is sent again, never skipped; only an item that kept failing for `replica::GIVE_UP_MS` (10 minutes) is skipped, logged as an error. The Space gateway's WebSocket limit matches the daemon's 64 MiB (`wire::MAX_MESSAGE`); apply runner items only through `Sessions::apply_replica`/`projects::apply_replica`, and keep the generation and runner checks (session records and events count only for a session Home placed on that runner).
- Workspaces, Git folders, Home Git, Local PRs, review drafts (`/api/review-state`) and scheduled follow-ups are Home's: runners keep copies and forward changes (`home_client::home_owned`); Context reads (`/api/context/*`) and every trace (Home holds all generations; the runner waits for its backlog and answers itself only when Home is out of reach) also come from Home, so any agent runs and resumes on any runner. Home also sends its profiles and the settings runners apply to their own work (`ToRunner::Settings`: `[worktrees] keep`, edited in Settings → Disk cleanup) on connect and after each change. A runner is a low-trust worker (`runner_trust`): its credential reaches Home Git, plain folders, handoffs, leases, quota readings, replication and uploads for the sessions Home placed on it, plus a closed list of requests its own work needs (`runner_trust::may`, each scoped to its sessions and folders by `runner_trust::check`); it reads plain stores (knowledge bases, bot files, plain, asset and temporary folders, `plain_http::caller`) and Local PRs only of the workspaces of the sessions Home placed on it (`scope::of_runner`: running, or archived in the last day), while folder and workspace records go to every runner (`ToRunner::Folders`) and Home Git serves any folder (repository caches for terminals); everything else it sends is an agent's call checked with that agent's access (see the Launchpad CLI rule). Nothing a runner sends runs as the owner: no vault, MCP settings, connections, Outbox, Suggestions, Local PR publication, Home update or owner action, and no session or trace of another runner unless Home sent it as context (`Hub::grant`). Tunnel exchanges carry only runner-authenticated paths (`exchange::home`). The tunnel protocol is the same whichever side dialed (`server::wire`). One writer per connection sends two lanes (`wire::lanes`): the control lane (pings, requests and answers, acknowledgements, replica batches, snapshots, terminal frames) always goes first, and the bounded bulk lane carries exchange body parts. Each exchange body keeps to a 4 MiB window (`wire::WINDOW`): the sender waits for the reader's `HttpAck`, and the receiving loop never waits (`wire::Inbound` refuses a sender past its window); a peer of an older build (no `Capabilities.flow` or `Welcome.flow`) gets no window, so it can still download Home's build. Dropping an exchange cancels it on the other side (`HttpCancel`: the runner's cancel stops Home's task and its upstream; Home's stops the runner's upload), and a connection's exchanges end with it. Never add an unbounded queue for bulk data.
- A runner's own window shows its status only (`web/src/features/runner`): its Home link, Takes new sessions (`runner.takes-sessions`, local, never synced; paused means Home starts no new session there) and its setup checklist; its daemon refuses every other call from a signed-in browser (`auth::runner_window_path`). Bearer clients are unaffected: Home's tunnel (including relayed terminal viewers), the CLI and agents' session tokens (agents' launches, routines and scheduled launches go to Home, `home_client::forward_writes`). A runner refuses a launch that Home did not relay.
- Seen and unread are recorded on Home. Archive of a session whose runner is away closes the record on Home (`runners::archive_away`) and is delivered once when the runner reconnects; Keep as folder of a temporary folder whose runner is away runs on Home (`projects::keep_away`), refused when the folder's last handoff saw Git data (`Handoff.temp_git`). Home never touches a worktree folder: worktree actions and Local PRs of a worktree reach the session's runner through the relay (`?session=`) or are answered from Home Git when it is away; what reaches Home's own handlers is refused.
- Placement (`runners::place`) is the only way Home picks where a session continues: its runner when connected; else, between turns, a move to another runner that takes launches (`runners::pick`: the previous runner, else the least busy); else Burst; else a clear error. Burst is always last. It serves the owner's messages, Resume and answers (relay), bot, proposal and report-reply messages, Local PR review requests (`runners::send_anywhere`) and scheduled follow-ups (`schedules::run`; a busy session answers 409 and the follow-up stays queued); launches use the same order (`launch_anywhere`, Home only), never fall back from a runner chosen in the composer, and move the sessions of a runner that does not take launches (away, paused, outdated) first when they continue in a session's folder (New agent here, Run in) or a temporary folder: to another runner, else to the Burst job, which takes them before it starts the launch (`runners::move_pinned_to`).
- A session still Running, asking or paused for quota on a runner that left (or that the owner removed) becomes Interrupted on Home after `runners::AWAY_GRACE_MS` (10 minutes), with a note as its last message, so it can continue elsewhere from its last handoff; a runner that comes back with the same generation replaces the record. A runner releases the sessions Home moved away from it (`handoff::release`; queued by every move, online or not, in `state.db` (`runner_delivery`) and delivered with `runners::deliver_pending` when it is connected, and again every 10 minutes while items wait; an item, like a pending Archive, is dropped only after the runner answered it; a release takes the session's `adopt:` lock, so an adoption of a newer generation waits for it): it stops them, pushes their commits and uncommitted files to `lp-scratch/<branch>-gen<n>` (with the daemon's Git token: Home refuses the session's own once it runs elsewhere), removes their folders only after Home confirmed that push, and forgets them. While a Burst job starts for a session, placement sends its other requests (messages, Resume, answers) to that job: they wait in its run record (`BurstRun.queued`; a retry with the same idempotency key is kept once) and follow the first one in order; a failed start fails them with it.
- Agent CLI updates (`crates/setup/src/cli_update.rs`): Home decides (`cli_update::plan`: a newer release of the same major version, the same minor for 0.x, installs on its own; a new major version waits for the owner's Approve), records each runner's entry before it asks the runner and never asks again after a failure or a restart (Retry is the owner's click). Only the runner daemon installs, never an agent, with the installer that installed the CLI (npm prefix or the CLI's own), after its sessions stopped running and holding `harness::CLI_INSTALL`; a CLI it cannot write is reported with the command, never forced. Burst and Home's Space keep the pins of `deploy/hf-home/release.json` (`bump_tools.py`). Never run a real CLI update in checks: it replaces the machine's own CLI.
- Runner updates (`self_update.rs`) start only on an owner click (Update, or the owner's Update Home with Then update the runners), wait until no session of the runner is running, verify Home's build (SHA-256, OS, architecture) and restart in place. Test them only with scratch daemons and copies of the binary, never on the owner's runners.
- Home updates (`crates/setup/src/home_update.rs`, Home on a Space only): the hourly check only reads (GitHub, the Space's info and Dockerfile); Update Home (`home.update`: the owner's click, an admin session's direct action when the owner asks, or a ready card) saves its `home_update` record, takes a forced backup and only then commits the target's `Dockerfile.release` (newest of the deployed channel, or of the `channel` asked for) to the Space on top of the checked revision; a failed backup refuses the update (the restarted Space would restore an older backup). Never replace a Dockerfile that deploy.sh did not write or a source build. The call returns once the Hub accepted the commit, before the restart; runners forward `/api/home/update*` to Home. Only the owner's button sets `update_runners` (not an action input, so agents and cards cannot). The runner follow-up asks each runner once (claimed in the `home_update` record before the request), for 24 hours. Test only with a throwaway Space (`deploy.sh --space`), never the owner's.
- Moves (`handoff.rs`) happen only between turns, one at a time per session: every move and placement takes `runners::place_lock`. The old runner's final handoff (when it is connected) pushes branches and saves leftovers to `lp-scratch/…` first; then Home increases the generation and names the new runner. The final handoff runs as a job on the runner that Home polls with one key (`handoff::final_job`, `final_on`), so a slow one is waited for (up to 30 minutes), never reported failed while it still runs. A failed adoption does not undo the move: the new runner adopts the session when Home relays its next request about it (`home_client::local`, `handoff::adopt_moved`, only for a generation above 0); adoption is idempotent. The adopting runner numbers its events after a gap (`sessions::MOVE_SEQ_GAP`), so late events of the previous generation are stored below them, never dropped or overwritten; Home's `last_seq` is its last stored event (a runner's record never raises it), so a trace through it always exists. A worktree whose merge stopped (conflict or failure) moves with its record; only a waiting merge holds the folder. Runners remove an archived session's folder only after Home confirmed the unchanged native files; a start restores them from Home. Harnesses save their traces and history normally in a contained session's harness home; never turn that off. Home keeps handoff files in its blob store, never in `state.db`. A handoff sends a native file Home confirmed for the session by hash, or only its appended tail on top of that file of the session's latest handoff on Home (`handoff::part`), to `/api/handoff/{id}/parts`, a path an older Home refuses; Home rebuilds the whole file and checks its hash, and a refused short handoff is sent again in full at once (adoption and restore tell the runner what Home holds), so Home always holds complete, unchanged files. Adapters own `native_trace` and `restore_native`; never synthesize a conversation from events. A harness whose conversations live in its own database restores at the next start, in the session's jail and folder (OpenCode: the unchanged export waits in the harness home and `opencode import --pure` reads it; a failed import fails the start).
- Home backups: content-addressed objects (with uploads, `home_backup::data_files`; a full `state.db` copy at most every 10 minutes on the timer (`DB_EVERY_MS`), at once before a planned stop and for Back up now or Update Home (`home_backup::When`), and backups of Home Git or uploads in between list the last copy with the plain blobs and uploads it needs; a `runner-archives.json` of an older backup is restored and imported into `state.db` at start), manifest written last, restore only from a complete manifest (every object present) with matching hashes (checked on download; Home Git bundles and plain blobs download when first needed). A live plain blob already in the destination stays listed by hash whether or not Home's disk has it; one that is neither on Home nor in the destination is left out and reported (`BackupInfo.missing_blobs`), never skipped silently. A listing or download error is never an empty answer (only a prefix that clearly does not exist lists empty). Retention (`home_backup::prune`, spawned after a complete backup, under `Backups.running`, last result in the backup status): keep set from `retained` (two newest, newest ≥1 h, newest ≥1…10 days; unknown or future times kept); it deletes nothing after a listing or download error, when the listing misses the manifest just written, while a manifest of the last day (or of unknown time) does not parse (`check_readable`), or unless the newest backup is verified complete; manifests deleted before objects; objects deleted only when no manifest of a fresh listing lists them and uploaded at least an hour ago (`unused_objects`); only under `home/backup/` and `home/blobs/`; a failure never fails the backup. A boot restore retries, then fails the boot instead of starting empty (only a destination with no backup objects starts fresh; objects without a readable manifest fail it). A restored mirror's bundles (`git_restore.json`) stay pending, and carried in every backup (`git/<id>.pending.bundle`, so retention keeps them), until applied: each use of the mirror and each backup pass retries (`home_git::ensure`, `retry_restores`), fetching into `refs/lp-restore/` and creating only refs the mirror does not have. Test with a local folder destination, never a real bucket.
- Burst (`burst.rs`): the runner secret is derived, never stored, and a Burst lease carries no secret (`token_relay`). One job per session; stop it only after the final handoff and a complete Home backup newer than the stored handoff time (`handed_off_at`), or 15 minutes after the handoff without one (`burst::after_handoff`): the run then fails with the reason and a notice in its sessions, since the handoff is only on Home's disk until a backup succeeds. An hour before HF Jobs' 24-hour limit, Home stops the job's open turns once (claimed in the run record, `limit_stop_at`, before the requests) with a notice in each session, so they hand off, and messages to them move them elsewhere. Starts claimed before a Home restart are cancelled, never retried. Respect `[home.burst]`. Test with a scratch Home and scratch bucket (`LAUNCHPAD_BURST_IMAGE`, `_COMMAND`, `_VOLUMES`) and cancel every test job.

### Knowledge base

- The knowledge base (`kb.rs`, store `kb-<workspace id>`) is the workspace's shared memory; a bot's own notes are `memory/` of its store (see Bots). Only Home writes it, through `kb::apply` (one writer at a time, author and line counts in `plain_history.meta`); never commit a `kb-` store with `plain::commit`. Writes name the content they started from; a changed base keeps both versions (`.concurrent-<id>` sibling), never a silent overwrite. Removals name the content they remove (`Op::Remove.base`: the mirror's synced version for agents, the shown version for the owner) and leave a note that changed since in place, with a line that says so. A runner's mirror never sends changes to Home: local edits and deletions are replaced by Home's version, and a missing mirror folder is downloaded again.
- Every contained session gets its workspace's mirror read-only (`$LAUNCHPAD_KB`), a bot session also its bot's files (`$LAUNCHPAD_BOT`), and the harness's own memory off through `Harness::contained_memory`. A bot session's instructions also hold its `memory/*.md` notes at start (`bot_memory::compose`: `memory/INDEX.md` first, then by path, at most `LOADED_LINES` = 100 lines); when cut, the instructions end with exactly one line that gives N of M lines and says how to read the rest, and the bot page shows "Loaded at start: N of M lines" (`Bot.memory_loaded`). Agents write only with `launchpad kb` (session CLI token, `/api/kb`) and a bot's own sessions its `memory/` with `launchpad bot memory` (`/api/bot-memory`); Home takes the author from its own session record, never from the runner, and accepts a runner's writes only for its sessions (edits in a runner's mirror do not go up: the owner edits notes in Home's window).
- Memory stays small: every instruction that tells agents about the knowledge base (`kb::instructions`, the seeded `AGENTS.md`, `bots::instruction`, Ask Launchpad's `BOT.md`, `skills/launchpad/SKILL.md`, `launchpad_cli::cli_reference`) sends a bot's own notes to its `memory/` and shared facts to the knowledge base, and asks for a few durable findings and what the owner asks to remember, never a log of sessions, runs or results.
- The Librarian tends the knowledge base: a normal bot (`librarian.rs`) that Home creates once per workspace like Ask Launchpad (`seeded` key `librarian:<workspace>`, never recreated after the owner deletes it), with propose access, no folder and one routine file `routines/weekly-tidy.toml` created paused (the owner turns it on). The Knowledge page's Ask the Librarian opens its chat (`librarianOf`, by its slug); without one, Run the gardener fills the composer with `Notes.gardener_prompt`. Memory import reads a runner's harness memories only on an owner click (never Home's own disk).

### Credentials and the jail

- Every agent runs contained (`contain::apply`; agents run only on Linux): a bubblewrap jail or a Local VM (`[runner] boundary = "vm"`). No full-machine mode; never pass the machine's credentials, logins, Git config or SSH keys into a session; keep `jail::KEEP_ENV` free of secrets. No read-only mount holds the home folder (so never `/home` or `/`), the data folder or a credential folder of the home folder (`jail::mountable`: PATH folders are left out, a harness's release folder falls back to its `bin` or the program alone). On a Local VM and on Burst, agents run as the daemon's own user without a jail: the daemon is non-dumpable and keeps its owner (bearer) token in memory only (`Paths::keep_token_in_memory`: no `token` file, a new token at each start, so no runner window or owner CLI there), and a Burst runner's credential comes from the job's secrets, never a file. Title requests, harness TUIs and folder setup commands (`worktrees::run_setup`, through `contain::auxiliary`) use the session's lease, jail and network capture; so the owner edits setup commands from any window, remote or not (agents never: see the admin rules).
- Daemon Git on a runner never reads what agents can write (every jail mounts `<data_dir>/repos` and `<data_dir>/worktrees` read-write, plus plain and temporary folders): every `git` the runner daemon starts outside a jail goes through `git_safe` (installed by `UserEnv::with_git_guard`, applied in `exec::Cmd`): `GIT_DIR` from the folder's `.git` with the work tree fixed to that folder, `GIT_COMMON_DIR` a shadow of the daemon (`<data_dir>/git-safe/<hash>`: its own config with only the repository format and, for a cache, `origin` = Home's URL; empty `hooks/`; links to objects, refs, packed refs, logs, worktrees and `info/exclude`), no system or global config, `core.hooksPath=/dev/null`, no fsmonitor, credential helper, askpass, pager, editor, `ext::` transport or submodule recursion; a folder without a repository gets a `GIT_DIR` that does not exist (only `init` and `clone` run there), and the agent-written files it reads (`.git`, `commondir`, `config`) are read only when they are small regular files (never a FIFO). So no repository config, `config.worktree`, include, hook, filter, diff or merge driver, `insteadOf` or proxy of an agent applies. Write the agents' config with `git config --file` (`repo_cache::create`, `worktrees::configure`); after `git worktree add`, `Guard::relink` points the new `.git` file at the clone. Credentials go only to Home's exact URL (`http.<url>.extraHeader`, `repo_cache::Auth`; a worktree pushes as its session), and the folder's remote is fetched by the URL of Home's record, never a remote name from the clone. Git still follows what agents plant (a symlinked ref or `HEAD`, `objects/info/alternates`, a worktree folder swapped for a link), so on a runner whose jail is bubblewrap every daemon `git` also runs in a minimal bubblewrap sandbox (`Guard::sandbox_args`, built with `jail::sandbox_args`): `git_safe::SANDBOX_SYSTEM` read-only (programs, libraries and a short list of `/etc` files; never the home folder or all of `/etc`), `<data_dir>/git-safe`, and only the agent-writable folders of the command's working folder (`Guard::mounts`: the repository caches and worktrees together, or the one `<data_dir>/plain/<id>` or `<data_dir>/tmp/<id>`; nothing elsewhere, so the command fails; it creates only the shadow, cache and worktree roots, never a plain or temporary folder that is gone), a private `/tmp` (files daemon Git reads go to `Guard::scratch_dir`) and the shared network (pushes and fetches reach this daemon's loopback Git endpoint; Home's URL and the token stay in the shadow config and `-c` values). A runner without bubblewrap fails its daemon Git (closed); on a Local VM or Burst (no owner files there) there is no sandbox, decided at start. Never add a daemon `git` that bypasses `exec::Cmd`. Owner terminals in worktrees run unjailed: the owner's own shell tools run the agent's Git config there.
- The daemon never follows a link an agent planted: every file it reads or writes outside the jail in an agent-writable folder (plain, temporary and asset folders and their `.launchpad/assets.toml`, a clone's `info/exclude`, native traces and the files the harness setup writes in the harness home (`Harness::contained_*`, `.gitconfig`), the attachment folder, a session's `/tmp`) goes through `safe_fs` (`openat` with `O_NOFOLLOW` for every component below the data folder's own folders, regular files only, writes renamed into place; the data folder and its own folders such as `worktrees` or `sessions` are the daemon's, so they may be links the owner made). `plain::sync_up` leaves links out (logged), and an asset folder that is or goes through a link is never synced. A background task's output file is read only from the session's own `/tmp` on its runner (`contain::tmp_file`), never on Home.
- Network capture (`netcap.rs`, supervisor in `crates/cli/src/netcap.rs`): every contained process runs under `launchpad netcap` through `Jail::command`, in the jail, on a Local VM and on Burst (`Jail.bwrap` false there). An agent must reach the same addresses with the same credentials on all three; runners also reach their LAN and tailnet, Burst connections leave from Home to public addresses only (`token_relay::tcp`). Keep the policy in `netcap` (loopback direct, UDP to port 53 only, link-local and metadata addresses refused except port 53 (`netcap::refused`, in the supervisor and again on the resolved address in `proxy::connect_out`), Unix sockets to paths only, never the abstract namespace (`netcap::unix_target`: the supervisor runs a Unix socket's `connect` and `bind` itself on a copy of the descriptor with the address it checked), same IPv4/IPv6 rules); never fix tools one by one. The jail keeps the machine's network namespace (loopback services stay reachable). A machine where `netcap::check` fails runs no agents. No shared agent image or toolchain uniformity; Docker stays VM-only (its containers are outside the capture).
- Secrets live only in Home's vault (`vault.rs`) and the runner proxy's memory; no API returns them, and agents see `vault::placeholder` values only. The runner credential (Burst: memory only; machines and Local VMs: `home.json`) never acts as the owner on Home (`runner_trust`): a compromised runner holds the leases of its own sessions, never the vault, the Outbox or GitHub. The lease travels only over a runner's own tunnel. Never write a real token into a session's files.
- The proxy adds tokens only on the lease's hosts, never judges requests, and logs every request that received a token. Host rules and request hosts (CONNECT, TLS server name, `/lp/<key>/<host>/…`, relayed requests) match only as lowercase DNS names (`vault::dns_name`: no port, user info, path, IPv6 literal, trailing dot or Unicode; an IPv4 address passes as digit labels), and a token is added only when the built URL goes to exactly that host (`vault::url_is_host`, in `proxy::forward` and `token_relay::upstream`). Its only change to a request body is the attribution line (`attribution::sign_request`) on GitHub writes; Suggestions, Local PR publication and Outbox sends sign with the same module, idempotently, so no prompt or bot adds the line by hand. Login setup belongs to `Harness::contained_login`, MCP config to `Harness::contained_mcp` (pointing at the runner proxy; the gateway checks the lease, refuses a POST body it cannot read as JSON-RPC and forwards the value it checked, hides tools that are off and logs each `tools/call`).
- Default tools (`tool_defaults.rs`): a grant decides where a tool or MCP server may be used; the default tools (workspace, then folder, then bot `[tools]`, most specific wins, on when unset) and the launch's `tools_off`/`tools_on` decide whether a session gets it. Home resolves them only in `LeaseRequest::off`; never turn on an item that is not granted.
- Leases end on Stop and Archive (no per-session Revoke: the owner stops the agent and launches a new one), when an idle process is released (`LiveSession::idle_release`; the next message takes a new one), and after an hour without Home; Home gives a lease only for a session it placed on that runner, in its current generation (`vault::check_owner`): every launch records the session on Home before the runner starts it (`runners::record_placement`: Home's launches before relaying, Burst's placeholder; a runner starts only launches relayed by Home, `launchpad_http::FROM_HOME`). Home builds what the lease holds (workspace, folder, bot, login, tools) from its own record of the session (`contain::request`), never from the runner's request, and replicas never change those fields. Only Home refreshes Codex logins; when the quota app-server on Home's copy refreshed a login itself, the vault keeps that newer login (`vault::login_home`), never writes a spent refresh token back over it.
- Test contained sessions with scratch daemons and token copies read without refreshing; check a Codex login's `last_refresh` before copying it into a test vault.

## UI rules

- Every action a button, a card, the CLI or the admin rules name is one entry of the action list (`crates/core/src/actions.rs`: route, input, confirmation, effect, access, card kind, undo). Add new actions there; buttons use `ActionButton` (it confirms when the action has a confirmation) or `runAction` (`web/src/lib/actions.ts`); run `gen-types` after changing the list.
- Build pages from `web/src/components/ui.tsx`: `PageHeader`, `Tabs`, `FilterChip` (narrows a list), `Choice`/`Choices` (the options of a setting, styled like the profile picker), `ConfirmButton` (every destructive or GitHub action; never `window.confirm`), `Loading`/`Empty`/`ErrorState` with `humanError`, `Badge`/`Token`, `StatusBadge`, `Count`, `RowActions`, `IconButton`, `SettingRow`. Text fields and selects use `field-input` with its default height and 13 px text (only `font-mono text-[12px]` for code values); buttons use `btn`/`btn-sm`/`IconButton`. Use semantic color tokens and sprite icons. One primary button per region.
- Sizes (tokens in `web/src/styles.css`, checked by `pnpm ui-check`): text only 11/12/13/15/18 px as `text-[Npx]` (Tailwind's `text-xs`, `text-sm`… are removed from the theme); corners `rounded-control` (6 px: buttons, fields and message boxes, menu items) and `rounded-card` (10 px: cards, panels, dialogs), `rounded`/`rounded-full` for marks and pills; icons 12 px inline, 14 px in icon buttons, 16 px in navigation (phone bar and tab icons may be larger); gaps from the spacing scale (`gap-1`, `gap-1.5`, `gap-2`…), never `gap-[Npx]`; page bodies `max-w-page` and reading columns `max-w-text`, left-aligned under the header with its `px-5`; no fixed hex or Tailwind palette colors (`red-600`…) outside the theme; never force an icon button's size (`size-…!`). Justified exceptions go in the script's allowlist.
- Action group: a list row or card shows at most one visible button, its main action as an outline button with a label in a right column of a minimum width (one exception: a finished or failed agent's Today row also shows Archive after it, on a laptop only); everything else goes in ⋯ (`RowActions`, built on `.lp-row-more`: shown on hover and keyboard focus, kept while its menu is open, always visible on touch screens; `MoreMenu` alone for a row or card without a main action). Menu entries are `MenuItem`s, actions of the action list use `ActionMenuItem`, and a confirmation (`ConfirmButton`) goes last in a `MenuSection`. The only filled button of a region is its single most important action.
- Icon-only buttons (`IconButton`) only in a toolbar where every button is icon-only, never mixed with text buttons (except ⋯, the menu of an action group); each has a tooltip and an `aria-label`; one size: 28 px laptop, 44 px phone, 14 px icon. Exception: the arrow after the "…" of a cut text (an agent's last message in Today) that shows the full text inline.
- States use `StatusBadge`, one color per meaning: blue running, amber needs you (question, quota paused, Inbox "for you"), green Done (an unseen Done adds an amber dot, never an amber pill), red failed or interrupted, grey idle, stopped or archived.
- Counts use `Count` (sidebar, tabs, chips, phone tab bar): an amber pill when the count needs you, a plain grey number otherwise.
- Dates use only `web/src/lib/format.ts`: `ago()` for past moments ("5 min ago", "yesterday", "Oct 3"), `age()` for the compact form in dense lists, `when()` for exact or future moments ("today 15:00", "Fri 7 Nov, 03:00", in the locale's clock); `time()`, `day()` and `month()` when a label needs only one part ("14:02", "Oct 3", "November"). Never `toLocaleString` for dates, never seconds, no year for the current year; callers never add " ago". Crons read as words (`describeCron`: "Every day at 03:00") with the raw cron in a tooltip.

## Git workflow

These rules apply unless the owner says otherwise for a given task.

- Work on `main`, in this checkout. Do not create other branches, worktrees or pull requests for this repository.
- Commit finished work on `main` with a short message that says what changed.
- Update the documentation in the same commit: `README.md` (features, getting started), the matching `docs/` page when a user-facing feature changes, `docs/architecture.md` when the design changes, and this file for new commands, rules or conventions. Keep documents short: describe behavior, not implementation history.

## Testing

This is a personal project: move fast.

- Add a test only for a small, specific part that clearly benefits from it, typically a pure function with tricky edge cases.
- No mocks of HTTP APIs, harness processes, git or the database. No tests that need a server, the network, GitHub, a running agent, the daemon or a full `App`.
- The whole test run must take a few seconds; no test may take more than a second. Delete slow or flaky tests.
- Check changes by building and running the app in the dev environment.

## Writing style

- Markdown: never hard-wrap lines. Write each paragraph or list item on one line.
- Use plain technical American English that non-native speakers can read easily. Be concise.
