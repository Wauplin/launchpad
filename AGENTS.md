# Launchpad: rules for coding agents

Launchpad is a personal web app (installable as a PWA; the daemon and runners on Linux) that launches and drives coding agents (Claude Code, Codex, OpenCode) and replaces the parts of the GitHub UI used every day, with a local cache. It has one user. Read [README.md](README.md) and [docs/architecture.md](docs/architecture.md) before changing the design.

## Where things are

- Rust crates (layout and dependencies in [docs/architecture.md](docs/architecture.md#code-layout)): `crates/core` (domain and services, the harness contract, the action list `actions.rs` and the decision list `today.rs`), `crates/harness` (adapters), `crates/channels` (channels, Telegram, hooks), `crates/github` (issue and PR views, Inbox, Suggestions), `crates/automation` (routines, scheduled launches, proposals, the activity list `activity.rs`), `crates/setup` (setup checklist, clone, onboarding), `crates/http` (API error type and route state, session token checks), `crates/api` (JSON routes that need only the `App`), `crates/server` (auth, runner tunnel and relay, WebSockets, embedded UI, activity recording `activity.rs`) and `crates/cli` (the `launchpad` binary, `extensions.rs` that connects the crates, and the `build.rs` that stamps the commit).
- `web/`: React app (feature folders in `web/src/features/`, for example `chat/` for the bot chat and the Ask panel `AskPanel.tsx`; the top-bar field is `web/src/app/CommandField.tsx`). `extension/`: Chrome extension. `deploy/hf-home/`: Home on a Hugging Face Space. `packaging/`: installers. `skills/launchpad/SKILL.md`: the agent skill for the CLI.
- `.claude/skills/implement-review-docs/`: the skill for plans with several steps (implementer, reviewer and docs subagents per step) and `prose-check.py` (proselint and reading ease of added Markdown lines).
- `docs/`: user documentation by feature, plus `architecture.md`, `development.md`, `harness-adapters.md` and `glossary.md`. `initial.md`: the original project description, in the owner's words.

## Commands

- UI: `cd web && pnpm install && pnpm build` (Node 24 from `web/.nvmrc`, pnpm through Corepack). A debug daemon reads `web/dist` from disk.
- Dev setup: a dev Home plus a dev runner, paired once. Home: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- daemon` (port 7318, data in `~/.local/share/launchpad-dev`; it runs no agents). Runner: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- daemon --role runner` (port 7321, data in `~/.local/share/launchpad-runner-dev`). Pair once: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- connect http://127.0.0.1:7318`, then approve the code in the dev Home's Settings → Home and runners; the runner keeps the link. `--role home` is accepted as a no-op; `--role all` is refused (there is no single-process mode). For an isolated second daemon, set `HOME` to a scratch folder and `LAUNCHPAD_PORT` to a free port.
- Sign a browser in to the dev Home: `LAUNCHPAD_ENV=dev cargo run -p launchpad -- url` (`pair` prints a QR code; add `LAUNCHPAD_ROLE=runner` for the dev runner's own window).
- Screenshots: `node web/scripts/shots.mjs [--demo] --views 100,120,150,phone [--out <dir>] <page>...` (pages `/path` or `name=/path`; clicks with `--pages <file.json>`). It serves this checkout's `web/dist` (rebuilt when stale) and forwards the API to the dev daemon, signs in once by itself, and reports sideways scrolling and page errors. Never write another screenshot script or start a server for it. See `docs/development.md#screenshots`.
- Demo mode: `/?demo=1` on any running UI (`?demo=essentials:layout`, `?demo=full:<chapter>`, `?demo=phone`), no pairing or real data needed.
- Runners: `launchpad daemon --role runner` (own folders), paired with `launchpad connect <Home address>` and approved in Home's Settings → Home and runners. Test pairs use two scratch `HOME`s and ports; remove test runners afterwards. Contained sessions need `bwrap` and a harness login in the vault. `packaging/local-vm.sh <Home address>` creates a Local VM runner with Multipass.
- Home-only Space POC: see `deploy/hf-home/README.md`. `deploy/hf-home/deploy.sh [--release <tag> | --main] [--space <name>]` installs or updates a Space with the hf CLI (latest release by default; `--main` uses CI's package of the newest packaged main commit from the `main-build` prerelease; nothing compiles on the Space builder); test it only with a throwaway `--space` and delete that Space and its bucket afterwards (runners use port 7320 and their own folders; never use the production installer for it). Checks: `cd deploy/hf-home && uv run -q --no-project --with-requirements requirements.txt python -m unittest discover -s tests` (its Python packages, on any runner).
- After changing a Rust type shared with the UI: `cargo run -p launchpad -- gen-types`.
- Lint (CI): `cargo +1.93.1 clippy --workspace --all-targets --locked -- -D warnings`, `(cd web && pnpm typecheck)` and `(cd web && pnpm lint:hooks)` (toolchain: `rustup toolchain install 1.93.1 --profile minimal --component clippy`).
- Tests (CI): `cargo test`, and `(cd web && pnpm test:<name>)` for attachments, chat, code, composer, drafts, markdown, operations, proposals, sessions, terminals and tour (Node 24), and the `deploy/hf-home` Python tests (`requirements.txt` in a venv).
- Chrome extension (on hold: not built or checked in CI, not shipped in release archives; do not change or fix it until the owner resumes it): `cd extension && pnpm install --frozen-lockfile && pnpm build` after installing `web/` dependencies; see `extension/README.md`.
- Icons: keep `packaging/icons/source.png` unchanged; regenerate with `python3 packaging/generate-icons.py`.
- Network capture: `launchpad netcap --self-test` checks the supervisor on this machine; `launchpad netcap --port <capture port> --key <proxy key> -- <program>` runs a program under it; Settings → Home and runners → **Check network** probes a runner's sandbox.
- Agent CLI: read-only context `launchpad folders|bots|sessions|profiles|presets|inbox|schedules|proposals list [--workspace …]`, `launchpad sessions show <id>`, `launchpad inbox done|unsubscribe <thread-id>…` (bots with `inbox_done = true` in `bot.toml` only), `launchpad today`, `launchpad activity list`; diagnostics at admin access `launchpad health`, `launchpad logs [--session <id>] [--runner <id>|--home|--local] [--since 2h] [--level warn] [--grep …]`, `launchpad failures`, `launchpad runners list`, `launchpad burst runs|job <runner>`, `launchpad home`, `launchpad tools list`, `launchpad channels list`; `launchpad propose …` (inert proposal; `propose ready` prepares an owner click); `launchpad do <group>.<verb> <ids…> [--<field> <value>] [--body-file <file>]` and the short verb `launchpad <group> <verb> …` (the admin actions of the action list); `launchpad api <method> <path> [--body-file]` (the API at admin access); `launchpad pr create|update|show|list` (Local PRs); `launchpad send <channel>|telegram --body-file <file> [--title …] --session-id <id>`.
- CI (`.github/workflows/ci.yml`): lint and debug tests on main, pull requests and tags; Linux only (no macOS or Windows jobs for now); release builds on tags and on main pushes (main pushes attach the package to the `main-build` prerelease, named by commit, keeping 20), on Ubuntu 22.04 (verify a downloaded binary before changing that baseline); build the UI before the release daemon so it embeds the assets. The release build is `.github/workflows/build.yml`, called by `ci.yml` on tags and by `.github/workflows/release.yml` (manual: tags the commit `vYYYY.MM.DD.N`, UTC, and creates the GitHub release with the package). The tests job also runs the `deploy/hf-home` Python tests. Keep CI and this file in sync.
- Production install/update: `packaging/install.sh` (Linux only, `--headless`, `--prebuilt`) installs a Home (`packaging/launchpad.service` runs `launchpad daemon`, no agents); a machine that runs agents installs a runner (`deploy/hf-home/install-runner.sh` from Home, or `launchpad daemon --role runner` with `launchpad connect`). It restarts the production daemon: only run it when the owner asks.

## Checks to run (keep iteration fast)

Run only what your change can break, and rebuild only what you changed; CI runs everything.

- Docs only: nothing.
- Web only: `(cd web && pnpm typecheck)`, `pnpm lint:hooks` if you touched hooks, `pnpm ui-check` after UI changes (lists off-scale sizes, radii, gaps, colors and dates with file:line), and the matching `pnpm test:<name>`. Do not run cargo.
- Rust: Cargo rebuilds only the crate you changed and the crates that depend on it. After a change in a feature crate, `api` or `server`, `cargo check --all-targets` takes 1–2 s, Clippy 2–4 s and `cargo test` 3–5 s. After a change in `core`, every crate rebuilds: about 9 s for `cargo check` and 20 s for Clippy or `cargo test`. Keep code out of `core` when the core does not call it.
- Rust, while working: `cargo check --all-targets`. Run `cargo test <filter>` only when you changed code that has tests; tests sit next to the code in each crate.
- Rust, once before committing: `cargo clippy --all-targets -- -D warnings`, plus `cargo test` if you changed tested code.
- Run checks and tests from the repository root without `-p`, even for one crate: selecting one crate resolves different dependency features and recompiles dozens of dependencies. Do not run release builds or `cargo clean`.
- Skip builds your change cannot affect: `gen-types` only when a type shared with the UI changed, `pnpm build` only when a running daemon must show a `web/` change, the extension only for `extension/` changes.
- Contained sessions share compiled dependencies through `sccache` when it is installed on the runner (`cargo install sccache --locked`).
- Runner tools: agents use the runner's tools and cannot use `sudo`. Burst's image installs the common ones in `deploy/hf-home/agent-tools.sh` (compilers, Rust 1.93.1 with Clippy, pnpm, jq, ripgrep, Chromium…); `deploy/hf-home/install-runner.sh` recommends the same list and `packaging/local-vm.sh` installs it. Keep the three in sync, and the Rust and pnpm versions with CI and `web/package.json`. Run `prose-check.py` directly or with `python3`: both go through `uv`.

## Safety rules

- **Never stop or restart the production Home (port 7317) or runner (port 7320)** unless the owner asks: the runner runs the agents, maybe including you. Restarting a runner interrupts its running turns and ends its terminals.
- **Nothing reaches GitHub without an owner click**, except Inbox Done and Unsubscribe by a bot the owner allowed (`inbox_done = true` in its `bot.toml`; `launchpad inbox done|unsubscribe`, checked on Home by `inbox_agent_done`). Automated checks never post comments or reviews, request reviewers, change labels, state or draft status, merge real items, publish Local PRs, post real suggestions or mute real threads. Local unread and viewed markers and unsent drafts are safe. Use throwaway local bare remotes for publication checks.
- Agent-written comments and reviews go through `launchpad suggest comment|review` (reviews need `--head <inspected commit>`; Local PRs use `--predraft <id>`). The CLI never publishes.
- Automated checks clean up after themselves: close the terminals they open, never type into harness TUIs, pause or delete test routines, cancel test follow-ups, scheduled launches and HF jobs, discard test worktrees (use throwaway repositories), close throwaway browsers and servers.
- Never run setup fixes that change the real machine's configuration, and never write trace copies or backups to a real bucket (use a local folder destination).
- Never refresh the Claude OAuth token; only read it. Never log in, refresh tokens or copy credentials to hosts on the owner's behalf.
- Never retry an uncertain operation automatically after a crash (launch/send claims, quota continuations, scheduled launches, Ask proposals, merges, browser actions, GitHub posts). Show the uncertainty and let the owner check.

## Design invariants

### General

- Single user: no backward compatibility, versioning or migration framework. `cache.db` can be deleted and rebuilt; keep `state.db` schema changes simple.
- Linux (Ubuntu) is primary; gate OS-specific APIs. Agents and terminals run only on Linux (a Linux machine, a Local VM or Burst; `role::ensure_agent_os`, whatever the role): `daemon --role runner` and `launchpad connect` refuse elsewhere, and Home refuses pairing, approval and tunnels of non-Linux runners (`role::os_refusal`, shown in Settings → Home and runners). On a Mac, `packaging/local-vm.sh` creates a Linux VM runner. Home runs no agents and may run elsewhere. CI currently runs tests and release builds on Linux only.
- Crate layering: `launchpad-core` depends on no other Launchpad crate; the feature crates (`harness`, `channels`, `github`, `automation`, `setup`) depend only on the core, never on each other; `server` never depends on `api` or a feature crate. The core reaches the crates above it only through `harness::install` and `ext::Extensions`, both installed by `crates/cli`. Put new code in the highest crate that can hold it; move code into the core only when the core calls it.
- Phase 7 extensions need an owner-approved scope. The daemon owns harnesses and terminals; there are no session workers.
- Click only: every action is a visible button. Keyboard shortcuts are limited to `Ctrl+F` in Files, `Ctrl+T`/`Cmd+T` for a new terminal, terminal clipboard and clear keys, normal text-editing keys, `Enter`/`Shift+Enter` in the session message box, the top-bar field (Enter sends with its primary button: Ask on every page, Launch only in a workspace without a bot; Shift+Enter adds a line) and the find field, and `@`, `/`, `#` suggestions in prompts.
- No editor integration (buttons, settings or endpoints).
- Presets are user-defined only: keep the config default and first-start template empty.

### Harnesses and sessions

- `crates/core/src/harness/mod.rs` is the common contract and `crates/harness/src/lib.rs` the registration list; each adapter owns startup/resume, discovery, monitors, markers, terminal commands and title hooks. No harness identity branches in core, server or React (UI metadata: `GET /api/harnesses`). See `docs/harness-adapters.md`.
- Adapters start processes with `procs::child_command(&app.env, …)` and `spec.cwd`. `exec::is_lost` exits are Interrupted.
- A session's native files live in its own harness home (`contain::harness_home`; adapters find it with `trace::root`, `project_moved` takes the session). Adapters never read the machine's own harness settings or history (`~/.claude`, `~/.codex`) for sessions or defaults; only the owner-clicked memory import on a runner reads them.
- Shared session states: Done means waiting for input; Running includes starting, working and background commands (including Codex background commands until real completion); never infer Done from a silent command. Stopped differs from Interrupted and Failed. Idle checks for publication, merge and root Stop include child turns and commands that outlive a turn.
- Needs you = an open question, or Done/Failed/Interrupted and unseen. `Session::needs_you()` and `needsYou`/`isUnseen` (`web/src/lib/sessionStatus.ts`) are the only predicates. A session becomes seen only after a focused, visible, recently used window showed it for 1.5 s (notification suppression uses the same rule); a bot page counts as showing its current session.
- Today is the decision list: Home computes it once for every window (`today::compute`, the core's items plus `ext::Extensions::today` for the feature crates), serves it at `GET /api/today` (Home-owned; runners forward it) and announces changes with the `today`/`changed` bus event; session updates recompute only when the set of sessions that need you changed. Every attention count (sidebar, rail, phone, window title, app badge) reads only this list; agents join it through `Session::needs_you()`. Each item names its main action from the action list. One card per session: the Local PRs of an agent that needs you go inside its card (`Item::grouped`; a finished agent's main action is then the Local PR's), so they count once; other Local PRs are cards of their own. An item whose place resolves to no workspace is not listed (repositories without a folder never show); only shared things show in every workspace (outdated runners, tool or preset proposals without a workspace, Outbox messages without a session). A Merge from a Today card needs the session Done and saved on Home (no `unsaved` mark), its runner present (its folder there, or removed and merged from Home) and a safe branch; the card stays until the merge completed. Every worktree Merge sends the head the window showed (`worktree.merge` input `head`) and is refused when the branch moved past it.
- `Sink::child` (subagents) never changes root usage, model, identity, status or previews.
- Permission modes (YOLO default, Ask for approval, Auto) use native mechanisms only; never implement Auto by accepting requests blindly. Typed replies cannot grant permissions.
- Only the initial prompt gets `compose::append_initial_summary_instruction`; follow-ups stay verbatim, typed text first in `render_prompt`. Trace context is referenced (`launchpad trace <id> --through <seq>`), never inlined; missing traces fail visibly.
- Schedules and routines (code: crons) claim before launching (advance `next_run_at` or the GitHub watermark, write the history entry first) and never catch up: runs over one hour late or with unmet conditions (all must hold; quota needs a fresh reading; dependencies use `dependency_done`) are skipped, with the true reason (`crons::late_reason`: Home not running, or the quota hold of `quota::hold_reason`); a run skipped after a quota hold is `missed` and counts as a failure. Claimed but not started at shutdown becomes Failed, never retried.
- Routine triggers: schedule, new Inbox activity (one run per check), another agent's turn ending Done (once its work is on Home: a turn that ended with the `unsaved` mark triggers when the mark clears, at most an hour later; `crons::turn_saved`), Launchpad failures (`failures.rs`: Home's 30-second check; one run per check, claimed by advancing `failure_seen`, waiting while the bot works, skipped after one hour); a routine's own runs never trigger routines, and a failure routine never runs for its own runs or its bot's sessions. Bot routines message the bot's thread (`crons::bot_message`) and skip while it works; other routines launch their spec. Pausing a bot pauses its routines and hooks, never the owner's messages. A final `no_update` message (`routines::is_no_update`) never notifies and is marked seen only if nothing was unseen when the run started.
- Attachments upload once (`upload:<mime>;<sha256>`); non-image files go to `<data_dir>/attachments/<session-id>/`, never into the checkout, and travel in the session's handoffs (restored on the adopting runner; files Home already has for the session go by hash only).
- Capacity retries: terminal capacity/overload failures only, persisted five-minute deadline, at most five per session, cancelled by Resume, input, Stop or Archive.
- Launch and session input use `Idempotency-Key` headers and durable `browser_operation` claims; keep authentication before retry middleware.
- Notifications (Telegram only; the daemon shows no desktop notifications) only for completed turns, failures, unexpected interruptions, automatic quota/cost stops and automatic resumption, never with code or messages. No Web Push.

### Profiles, quota and costs

- Profiles (`[[profiles]]` in config.toml) are the only way to run an agent; none are built in. Sessions store the profile ID, never environment values; missing IDs or changed harnesses fail visibly on resume.
- One quota monitor per subscription login, checks use the session's login. The logins are Home's vault logins (`quota::vault_key`), monitored on Home with its own copy of each (`vault::login_home`), never the machine's `~/.claude` or `~/.codex`; runners receive the readings and send Home the complete readings of their running sessions (`quota::session_reading`, at most one per login every 15 s). When the Claude token expired or the usage call fails (except 429 and 403), use Claude Code's `get_usage` control request; a failed check keeps a reading younger than 10 minutes. A `setup-token` token cannot read usage (403, then hourly only); while automatic work waits for a reading (`quota::want_reading`), Home reads the rate-limit headers of a one-token request (`probe_with_token`), at most every 10 minutes and never while the last reading shows a used-up window that has not reset.
- Allow paid usage defaults to false and is never remembered. Exhausted quota holds input or pauses into Quota paused; continuing needs fresh confirmed capacity in both windows, never a reset time alone (null reset = window not started). Owner messages during a pause wait in the durable pending continuation and are delivered in order with it; Stop and Archive discard them.
- Cost and rolling spend limits apply only to harnesses reporting USD; reaching one refuses input, interrupts best effort and never resumes automatically. Claude adds only increases of its per-process `total_cost_usd`. Terminal TUIs are outside quota protection.

### Folders, worktrees and Local PRs

The Git and storage design is in `docs/architecture.md`; these rules must hold.

- Use the glossary words in the UI: Folder (code: project), Local PR (code: predraft), Suggestion, Files (code viewer). See `docs/glossary.md`.
- Every folder is stored by Home (Home Git or a plain folder) and runs on any runner; there are no folders of one disk. Folders are added only by Clone from GitHub (`project_clone::clone_to_home`), New plain folder (`projects::create_plain`) and Keep as folder; there is no Add folder by path, folder discovery or folders root, and Home never reads or writes its own disk for folders. Temporary folders are the only records a runner registers itself (`project.runner_id` on Home says where one is now). Never route a launch by a folder's disk; `projects::forget_disk_folders` drops older records of one disk at startup.
- Home Git (`home_git.rs`): a bare mirror per Git folder that follows the remote, except Launchpad branches (`lp/…`, `lp-scratch/…`) and snapshots (`refs/lp-snapshots/<worktree id>`), which only runners push (`pre-receive` refuses the rest). Only Home writes base branches, through Merge or Publish. Previous tips stay 30 days under `refs/kept/` with Restore. Runners and agents never hold a Git credential for Home (runner-local `/git/<id>.git` with per-session tokens); Home refuses a session that now runs elsewhere.
- Temporary folders (`Target::Temp`) live in `<data_dir>/tmp/`, registered `is_temp`, with their files in Home's store `tmp-<folder id>` (synced like a plain folder, same folder ID on every runner). `projects::after_archive` removes the local copy and the record (hidden from the UI) when its last session is archived and Home holds every file; Resume recreates it from Home; Home drops the store 30 days after the last Archive (`plain::clean_temp`). The store carries a temporary folder's files except `.gitignore`d ones (rebuilt by the agent) and Git data: a temporary folder that holds a Git repository (`plain::git_inside`, at its top or nested) never leaves its runner on its own (a move is refused, Archive and a release keep the folder and say why). Keep as folder (`projects::keep_as_folder`, Home's part `projects::keep_temp`) makes it a folder stored by Home: a plain folder with the same ID (the store moves from `tmp-<id>`), or a new Git folder of Home when it holds a Git repository; never keep temporary folders by default.
- Each session gets fresh worktrees (`<data_dir>/worktrees/<id>/`, branch `lp/<slug>-<session8>`); never use a harness's own worktree feature or the owner's checkouts. The launch request only records the worktree (`worktrees::plan`); network calls, setup and the harness start happen in the background start task (`prepare`). **When done** is keep, merge or Local PR.
- A turn end stores each worktree's local head in its record, then the new status with an `unsaved` mark (`Session::unsaved`), so Home never shows a turn as saved before it is; `turn_sync` then pushes each branch (`--force-with-lease`, so a Restore is never overwritten), syncs plain folders and uploads the handoff, and clears the mark. A failure keeps the mark with its reason (shown on the session) and the runner retries every three minutes and when its tunnel reconnects (one save per session at a time; a move waits for it, `turn_sync::hold`). A final handoff, an adoption and Archive clear the mark. Runners send every worktree record to Home on its own (`replica::Item::Worktree`, Home's `runner_worktree`, dropped once all its sessions are archived), so away views work before the first handoff and flag `unpushed` when Home's branch differs from the runner's head. Runners snapshot every file of each worktree (committed or not, `worktrees::snapshot`, to `refs/lp-snapshots/<worktree id>` on Home) at each turn end and at removal, and every five minutes during turns together with plain and temporary folders (`turn_sync::periodic`). Away Changes and Files show the last snapshot when it is newer than Home's branch, as of when it was taken; a folder cloned again from Home (`worktrees::restore`, after a move or retention) gets its commits and uncommitted files back from it; a snapshot it cannot apply (diverged, or applying failed) goes to `lp-scratch/<branch>-snapshot` first. Snapshots never touch the worktree's index, `HEAD` or files (temporary index). Discard and the 30-day prune delete snapshots. A folder is removed only after Home confirmed the branch; uncommitted files go to `lp-scratch/…` first. Every push writes its result under `worktree_lock` (`push` with the lock held, else `push_unlocked`). Take the session action lock before `worktree_lock`, and release both before messaging an agent.
- Merges run on Home (`home_git::merge`): push the reviewed commit to the remote base branch (never forced), then fast-forward Home's; a refused push merges nothing and stays visible; a moved base goes back to the agent for a rebase. Every worktree merge goes through `worktrees::merge_on_home`, which records it in `branch_merge` (dropped when the branch leaves Home Git): Home is the source of truth for a branch's `merged` and `predraft_id`, by folder and branch (`away::from_home`; a merged Local PR stops counting once the branch has newer commits), and completes every runner's worktree list with them (`away::complete`). Whenever a worktree's folder is gone from its runner (Removed: retention, or a move) or the runner is away, Home answers its Changes, Merge and Create Local PR from Home Git (`core::away`), whatever the runner's state (`WorktreeInfo.on_home`, set only by Home); Changes always compare with the merge-base of the branch and its base branch, online and on Home. Push to PR and published Local PRs follow GitHub (`git_follow`), never forced: one push at a time per branch, always the branch's current commit; the record keeps the last commit GitHub accepted and the last error, each mirror refresh retries, and the Local PR and the session's branch show "Not on GitHub yet". Publish pushes exactly the reviewed commit; one session's Local PRs form a change set, and Publish all sends each one's reviewed commit and publishes nothing when a branch moved.
- Plain and asset folders (`plain.rs`): stored by Home, history 30 days in `plain_history`, one session holds a store's lock; never write a store outside `plain::commit`. Unused asset folders go to the trash after 14 days (`plain::clean_assets`), with Restore.
- Files reads Git folders from a browse copy (`home_git::browse_copy`, updated at once after a push or merge), never the bare mirror. On Home, a session's worktree is found through its records (`away::records_at`), and one whose folder is gone or whose runner is away is read from its branch there. Every `/api/code/*` request goes through `code::open` (registered folders and their worktrees only); code API paths use forward slashes. HTML previews are static, sanitized and sandboxed with no permissions; keep highlighting limits shared with the viewer and terminate stalled highlight workers.
- Folder remote metadata is derived from local Git configuration; broadcast only when it changes.

### Other machines

- Agents run only on runners (a machine's runner daemon, a Local VM or Burst); there are no SSH hosts and no single-process mode. Another Linux machine joins as a runner that pairs itself with Home (`launchpad connect`), never through a connection Home opens into it.

### Remote access and devices

- `[server] bind` defaults to `127.0.0.1`. `public_origin` (explicit) or Tailscale discovery (`auto_tailnet`) defines the exact allowed Host/Origin. Never infer allowed origins or Secure cookies from forwarded headers. Startup discovery is read-only; never adopt Funnel routes or another daemon's port.
- Owner-clicked Tailscale setup runs only a fixed `tailscale serve` root proxy for this daemon; it never runs arbitrary input or overwrites routes.
- Pairing links are single-use and expire after five minutes. Reverse pairing binds approval to a separate tab secret; never exchange the short code alone for a credential. Every paired browser has full access.
- There is no native shell: browser tabs (or the installed PWA) open links and other workspaces in new tabs; the daemon never opens windows or links.
- Session lists and bus events carry `Session::light()` (no attachment bytes, prompt cut at 4,000 bytes); fetch `GET /api/sessions/{id}` for the full record. Sessions open tail-first.

### GitHub

- Detail and list GETs return cached content; POST refreshes. Label/reviewer pickers read `cache.db` only.
- `all=true` notifications include historical Done threads; keep inbox membership in `state.db` and never promise exact parity with the web inbox. A missing thread subscription (404) is not evidence of unsubscribe.

### Bots

- A bot is files on Home (`BOT.md`, `bot.toml`, `memory/`, store `bot-<id>`) plus one thread: the sessions whose `LaunchSpec.bot` names it. `bot.toml` is the only source of its settings (profile, model, folder, permission mode, proposal mode, Launchpad CLI access, `inbox_done`, `starters`: the chips over its message box, seeded for Ask Launchpad as data, never per bot identity); no profile means the first subscription profile (`bots::profile_of`). Only the owner and sessions with admin Launchpad CLI access write `BOT.md` and `bot.toml`; `memory/` holds the bot's own notes (`bot_memory.rs`), written only by Home through `kb::apply_to` (like the knowledge base) and by the bot's own sessions with `launchpad bot memory` at every access level, like the knowledge base (`/api/bot-memory`, an own write; Home takes the bot from its own session record). Runners mirror the store read-only into the bot's sessions (`$LAUNCHPAD_BOT`) and remove a copy an hour after the bot's last open session there. Bot history, diff and Restore cover all three; deleting a bot deletes its memory. Its folder is optional: without one, each session runs in a temporary folder and adds worktrees with `launchpad work add-project`.
- A new session of the thread starts only on the first message, a profile or folder change, an archived current session or the owner's New session checkbox; it references the previous trace (`launchpad trace`), never inlines it. Harness compaction handles a full context.
- The bot page is a chat over the thread, built from session events by `chatRows` (`web/src/features/chat/`) with no Ask-only code; the full trace stays in Agents (Open trace).
- Bot sessions are normal sessions (counted once, in Today); the sidebar shows only a state dot per bot. A rename gives a new slug (unique in the workspace), and the Telegram command follows it. Notes once kept in the knowledge base's `bots/<slug>/` moved once into `memory/` at a Home start (`bot_memory::move_from_kb`, claimed per bot in `seeded`; a new bot claims it at creation, so it never takes a deleted bot's folder); the Knowledge page lists each bot's memory read-only, linking to the bot. Creating a bot (form or proposal) starts nothing; bot proposals never auto-start.

### Channels and the Outbox

- Channels live on Home (`crates/channels`: `channels.rs`, `telegram.rs`, `hooks.rs`); runners forward `/api/channels`, `/api/outbox` and `/api/suggestions`. Webhook URLs and the Telegram token are `channel-…` vault entries: never listed, lent or returned by an API.
- Messages to other people (webhooks, GitHub suggestions) wait in the Outbox for an owner click (shown in Today → Send and Today → GitHub; "Outbox" stays the concept and code name, there is no Outbox page); a send is claimed (`sending`) first, never retried, and `uncertain` if incomplete. Automated checks never send real Outbox messages or call Telegram with a real token.
- The owner's own Telegram chat (bound with a single-use code; other chats ignored) gets messages directly. Updates are claimed (offset saved) before handling. Telegram never enables paid usage. Notifications of finished, failed and interrupted sessions link to their Today card (`/?card=session:<id>`); every link carries `ws=` of its workspace. No buttons in Telegram.
- Incoming hooks (`POST /hooks/<id>`) need `X-Launchpad-Hook-Secret` (SHA-256 stored, constant-time compare), one message per 10 seconds, an HF token on a private Space; the body is a fenced, size-limited block marked as outside data. Hook and Telegram messages to a busy bot wait in `queued_message`; its chat lists them (`GET /api/bots/{id}/queued`, bus `bots`/`queued`) with Cancel (`bot.cancel-queued`).

### Ask Launchpad and proposals

- Ask Launchpad is a normal bot with no special code path: Home creates it once per workspace (`ask_bot::seed`, recorded in the `seeded` table) with its own plain folder; the owner may edit, replace or delete it, and Home never recreates it. Never add Ask-only branches to sessions, crons, hooks, proposals or the UI. The top-bar Ask and the Ask panel send to `askTarget` (`web/src/lib/bots.ts`: the oldest admin bot of the workspace, else its oldest bot) or the bot the owner picks.
- The Launchpad CLI is a tool of Home's registry (`vault::LAUNCHPAD_TOOL`), added once and granted to every workspace, with three access levels (`vault::LaunchpadAccess`): **read** (`/api/status`, `/api/context/*`, `GET /api/proposals`), **propose** (plus `POST /api/proposals`; the default for bots and every other agent) and **admin** (plus Launchpad's own records: exactly the `admin` actions of the action list, `crates/core/src/actions.rs`, through `launchpad do`, short verbs or `launchpad api`: bots, routines, schedules, workspaces, folder settings (`folder.set`, never the setup command), shared settings (`settings.set`), proposal start and dismiss, launches and session messages, MCP tool switches, Home update check and install (`home.check-update`, `home.update`, effect `Installs`: the only admin action that is also a ready card); GETs outside a closed list; it never reads `GET /api/config`). `agent_auth::admin_allows` matches routes exactly (no trailing slash, no empty segment), and an admin request body may hold only the action's input fields. Accepting a card runs the action its kind maps to (`actions::for_card`), so an admin session may accept a card only when that action is an admin action; tool cards wait for the owner. Admin also reads diagnostics, never secrets: `agent_auth::diagnostic` routes (`/api/logs`, `/api/context/{health,failures,runners,burst,home,tools,channels}`, `crates/api/src/diagnostics.rs`) leave out tokens, vault values, runner secrets, webhook URLs and pairing codes, and log lines are redacted when written (`launchpad_http::logs::redact`); the owner routes of runners, Burst, the vault, channels and backups stay closed. On a runner, an agent's request about a session it does not run, and an agent's launch, go to Home like the owner's buttons (`home_client::forward_writes`); Home accepts from a runner only session reads and admin session actions. Home records each direct admin action in the activity list (`launchpad_automation::activity`) with the values before and its undo call; the bot chat shows it as a Changed line (the record name links to its page). Bots set the level with `launchpad` in `bot.toml`; Ask Launchpad is created with admin. Home puts the level in the lease (`Lease.launchpad`); `agent_auth` enforces it on the session CLI token, and `launchpad_cli::cli_reference` tells the session what it may do. A session without a lease on its machine gets propose. Admin never reaches GitHub, the Outbox, channels, credentials, devices, terminals, hosts, runners, setup fixes, backups, Burst, config.toml (except the closed shared-settings list of `settings.set` through `/api/settings/shared`: presets, GitHub poll interval, worktrees kept), folder setup commands or paid usage (`agent_auth::admin_allows`); keep that list closed. Every config.toml write, the owner's or an agent's, goes through `ConfigHandle::update` (read, change and save under one lock).
- Proposals are inert. Every start needs an owner click, except one-time launches, messages and schedules of a bot whose `bot.toml` says `proposals = "auto"`, and what an admin session does directly; proposed crons, routines, presets, bots, tools and BOT.md changes always wait (an admin session may accept preset cards). Ready cards (`ProposalBody::Ready`, actions with `ready: true`: merge, publish, post, send, run CI, Inbox done) prepare an owner action: they run only from their own button, with the action's call and confirmation, then `POST /api/proposals/{id}/ran`; accepting never runs them, and Start all and auto mode skip them. Paid usage is forced off. A session proposes routines and BOT.md changes only for bots of its own workspace. Preset proposals create or update presets and never delete them. Reports (`ProposalBody::Report`) start nothing: Mark read dismisses them, Reply (`proposals::reply`, claimed like a start) messages the author's thread (its bot, else its session); a new report replaces the waiting one of the same author (bot, else session), workspace and GitHub item; `needs_you` reports list under Answer, the others under Review.

### Terminals

- A runner's daemon owns PTYs; Home runs none. Output stays in the runner's memory (1 MB each) and goes over one WebSocket per viewer, never the global bus. The PTY size follows the owner viewer. Keep visited xterm views mounted.
- Terminals and Continue in TUI open from Home's window and run on a runner: Home relays every `/api/terminals` call (`terminals::home`, from `runners::relay`) to the runner of the terminal (`ROUTES`, filled from runners' answers, else fresh lists), of the agent (`?runner=`, `?session=`, or the agent whose folder the path is) or, for a Git folder without an agent, to a runner picked like for a launch (`runners::pick`, else any connected one; it opens the runner's repository cache, synced); plain folders get no shell without an agent. Home tags each answer with `runner_id` and lists the terminals of every connected runner. Each viewer WebSocket goes through the runner's tunnel (`ToRunner::WsOpen`, `WsFrame` both ways, `WsClose`; only `/api/terminals/{id}/ws`): the runner serves it like a local viewer, so flow control (`ack`) passes through unchanged, and Home checks the window's access. Runners report terminal changes (`FromRunner::Terminals`) and Home publishes them. Never place a terminal elsewhere: a runner that is away (or a Burst job that is not running) shows the entry points disabled with the reason; no move, no Burst.
- Shells open only in a registered folder, one of its worktrees or a session folder, on the runner.
- Shell snippets in agent messages run only on an owner click (Run in terminal), never automatically, and never from repository or GitHub Markdown.

### Trace copies

- Home copies each session's native files from its latest handoff, unchanged, after each backup (`trace_copies.rs`): `<workspace>/traces/<folder>/<YYYYMMDD_HHMM>_<id>/`, one file per trace plus `launchpad.json`. Adapters export native traces unchanged (`Harness::native_trace`); never synthesize native traces from normalized events. Home never reads the copies back.
- There is no peer trace sync between instances. Never log in or change bucket visibility; only a renamed workspace or folder deletes the old copies.

### Home and runners

The replication, relay, move and Burst design is in `docs/architecture.md`; these rules must hold.

- Home (`launchpad daemon`, the default role; `--role home` is a no-op) runs no agents or terminals (it relays terminals to runners, see Terminals), and a runner (`--role runner`) holds no records of its own; there is no role that does both. Home never reads a runner's disk in process: every lease, MCP, Git, plain-folder and knowledge-base call of a runner goes to Home over its link. Runners replicate through `home_outbox` (same transaction, dropped only after Home's `Ack`); apply runner items only through `Sessions::apply_replica`/`projects::apply_replica`, and keep the generation and runner checks (session records and events count only for a session Home placed on that runner).
- Workspaces, Git folders, Home Git, Local PRs, review drafts (`/api/review-state`) and scheduled follow-ups are Home's: runners keep copies and forward changes (`home_client::home_owned`); Context reads (`/api/context/*`) and every trace (Home holds all generations; the runner waits for its backlog and answers itself only when Home is out of reach) also come from Home, so any agent runs and resumes on any runner. Home also sends its profiles and the settings runners apply to their own work (`ToRunner::Settings`: `[worktrees] keep`, edited in Settings → Disk cleanup) on connect and after each change. Home accepts only `home_client::home_accepts` paths from a runner, and only runner-authenticated paths in tunnel exchanges (`exchange::home`). The tunnel protocol is the same whichever side dialed (`server::wire`).
- A runner's own window shows its status only (`web/src/features/runner`): its Home link, Takes new sessions (`runner.takes-sessions`, local, never synced; paused means Home starts no new session there) and its setup checklist; its daemon refuses every other call from a signed-in browser (`auth::runner_window_path`). Bearer clients are unaffected: Home's tunnel (including relayed terminal viewers), the CLI and agents' session tokens (agents' launches, routines and scheduled launches go to Home, `home_client::forward_writes`). A runner refuses a launch that Home did not relay.
- Seen and unread are recorded on Home. Archive of a session whose runner is away closes the record on Home (`runners::archive_away`) and is delivered once when the runner reconnects; Keep as folder of a temporary folder whose runner is away runs on Home (`projects::keep_away`), refused when the folder's last handoff saw Git data (`Handoff.temp_git`). Home never touches a worktree folder: worktree actions and Local PRs of a worktree reach the session's runner through the relay (`?session=`) or are answered from Home Git when it is away; what reaches Home's own handlers is refused.
- Placement (`runners::place`) is the only way Home picks where a session continues: its runner when connected; else, between turns, a move to another runner that takes launches (`runners::pick`: the previous runner, else the least busy); else Burst; else a clear error. Burst is always last. It serves the owner's messages, Resume and answers (relay), bot, proposal and report-reply messages, Local PR review requests (`runners::send_anywhere`) and scheduled follow-ups (`schedules::run`; a busy session answers 409 and the follow-up stays queued); launches use the same order (`launch_anywhere`, Home only), never fall back from a runner chosen in the composer, and move the sessions of an away runner first when they continue in a session's folder (New agent here, Run in) or a temporary folder.
- A session still Running, asking or paused for quota on a runner that left (or that the owner removed) becomes Interrupted on Home after `runners::AWAY_GRACE_MS` (10 minutes), with a note as its last message, so it can continue elsewhere from its last handoff; a runner that comes back with the same generation replaces the record. A runner that reconnects releases the sessions Home moved on while it was away (`handoff::release`, delivered with `runners::deliver_pending`): it stops them, pushes their commits and uncommitted files to `lp-scratch/<branch>-gen<n>` (with the daemon's Git token: Home refuses the session's own once it runs elsewhere), removes their folders only after Home confirmed that push, and forgets them. While a Burst job starts for a session, placement sends its other requests (messages, Resume, answers) to that job: they wait in its run record (`BurstRun.queued`; a retry with the same idempotency key is kept once) and follow the first one in order; a failed start fails them with it.
- Runner updates (`self_update.rs`) start only on an owner click (Update, or the owner's Update Home with Then update the runners), wait until no session of the runner is running, verify Home's build (SHA-256, OS, architecture) and restart in place. Test them only with scratch daemons and copies of the binary, never on the owner's runners.
- Home updates (`crates/setup/src/home_update.rs`, Home on a Space only): the hourly check only reads (GitHub, the Space's info and Dockerfile); Update Home (`home.update`: the owner's click, an admin session's direct action when the owner asks, or a ready card) commits the target's `Dockerfile.release` (newest of the deployed channel, or of the `channel` asked for) to the Space on top of the checked revision. Never replace a Dockerfile that deploy.sh did not write or a source build. The call returns once the Hub accepted the commit, before the restart; runners forward `/api/home/update*` to Home. Only the owner's button sets `update_runners` (not an action input, so agents and cards cannot). The runner follow-up asks each runner once (claimed in the `home_update` record before the request), for 24 hours. Test only with a throwaway Space (`deploy.sh --space`), never the owner's.
- Moves (`handoff.rs`) happen only between turns: Home increases the generation and names the new runner first; the old runner's final handoff pushes branches and saves leftovers to `lp-scratch/…`. The adopting runner numbers its events after a gap (`sessions::MOVE_SEQ_GAP`), so late events of the previous generation are stored below them, never dropped or overwritten; Home's `last_seq` is its last stored event (a runner's record never raises it), so a trace through it always exists. A worktree whose merge stopped (conflict or failure) moves with its record; only a waiting merge holds the folder. Runners remove an archived session's folder only after Home confirmed the unchanged native files; a start restores them from Home. Harnesses save their traces and history normally in a contained session's harness home; never turn that off. Home keeps handoff files in its blob store, never in `state.db`. Adapters own `native_trace` and `restore_native`; never synthesize a conversation from events. A harness whose conversations live in its own database restores at the next start, in the session's jail and folder (OpenCode: the unchanged export waits in the harness home and `opencode import --pure` reads it; a failed import fails the start).
- Home backups: content-addressed objects (with uploads and `runner-archives.json`, `home_backup::data_files`), manifest written last, restore only from a complete manifest (every object present) with matching hashes (checked on download; Home Git bundles and plain blobs download when first needed). Prune only under `home/`. Test with a local folder destination, never a real bucket.
- Burst (`burst.rs`): the runner secret is derived, never stored, and a Burst lease carries no secret (`token_relay`). One job per session; stop it only after the final handoff and a complete Home backup newer than the stored handoff time (`handed_off_at`). An hour before HF Jobs' 24-hour limit, Home stops the job's open turns once (claimed in the run record, `limit_stop_at`, before the requests) with a notice in each session, so they hand off, and messages to them move them elsewhere. Starts claimed before a Home restart are cancelled, never retried. Respect `[home.burst]`. Test with a scratch Home and scratch bucket (`LAUNCHPAD_BURST_IMAGE`, `_COMMAND`, `_VOLUMES`) and cancel every test job.

### Knowledge base

- The knowledge base (`kb.rs`, store `kb-<workspace id>`) is the workspace's shared memory; a bot's own notes are `memory/` of its store (see Bots). Only Home writes it, through `kb::apply` (one writer at a time, author and line counts in `plain_history.meta`); never commit a `kb-` store with `plain::commit`. Writes name the content they started from; a changed base keeps both versions (`.concurrent-<id>` sibling), never a silent overwrite.
- Every contained session gets its workspace's mirror read-only (`$LAUNCHPAD_KB`), a bot session also its bot's files (`$LAUNCHPAD_BOT`), and the harness's own memory off through `Harness::contained_memory`. Agents write only with `launchpad kb` (session CLI token, `/api/kb`); Home takes the author from its own session record, never from the runner.
- Memory stays small: every instruction that tells agents about the knowledge base (`kb::instructions`, the seeded `AGENTS.md`, `bots::instruction`, Ask Launchpad's `BOT.md`, `skills/launchpad/SKILL.md`, `launchpad_cli::cli_reference`) sends a bot's own notes to its `memory/` and shared facts to the knowledge base, and asks for a few durable findings and what the owner asks to remember, never a log of sessions, runs or results.
- The gardener is a normal launch the owner starts (or repeats as a routine) from the Knowledge page; memory import reads a runner's harness memories only on an owner click (never Home's own disk).

### Credentials and the jail

- Every agent runs contained (`contain::apply`; agents run only on Linux): a bubblewrap jail or a Local VM (`[runner] boundary = "vm"`). No full-machine mode; never pass the machine's credentials, logins, Git config or SSH keys into a session; keep `jail::KEEP_ENV` free of secrets. Title requests, harness TUIs and folder setup commands (`worktrees::run_setup`, through `contain::auxiliary`) use the session's lease, jail and network capture; so the owner edits setup commands from any window, remote or not (agents never: see the admin rules).
- Network capture (`netcap.rs`, supervisor in `crates/cli/src/netcap.rs`): every contained process runs under `launchpad netcap` through `Jail::command`, in the jail, on a Local VM and on Burst (`Jail.bwrap` false there). An agent must reach the same addresses with the same credentials on all three; runners also reach their LAN and tailnet, Burst connections leave from Home to public addresses only (`token_relay::tcp`). Keep the policy in `netcap` (loopback direct, UDP to port 53 only, same IPv4/IPv6 rules); never fix tools one by one. A machine where `netcap::check` fails runs no agents. No shared agent image or toolchain uniformity; Docker stays VM-only (its containers are outside the capture).
- Secrets live only in Home's vault (`vault.rs`) and the runner proxy's memory; no API returns them, and agents see `vault::placeholder` values only. The lease travels only over a runner's own tunnel. Never write a real token into a session's files.
- The proxy adds tokens only on the lease's hosts, never judges requests, and logs every request that received a token. Its only change to a request body is the attribution line (`attribution::sign_request`) on GitHub writes; Suggestions, Local PR publication and Outbox sends sign with the same module, idempotently, so no prompt or bot adds the line by hand. Login setup belongs to `Harness::contained_login`, MCP config to `Harness::contained_mcp` (pointing at the runner proxy; the gateway checks the lease, hides tools that are off and logs each `tools/call`).
- Default tools (`tool_defaults.rs`): a grant decides where a tool or MCP server may be used; the default tools (workspace, then folder, then bot `[tools]`, most specific wins, on when unset) and the launch's `tools_off`/`tools_on` decide whether a session gets it. Home resolves them only in `LeaseRequest::off`; never turn on an item that is not granted.
- Leases end on Stop and Archive (no per-session Revoke: the owner stops the agent and launches a new one), and after an hour without Home; Home gives a lease only for a session it placed on that runner, in its current generation (`vault::check_owner`): every launch records the session on Home before the runner starts it (`runners::record_placement`: Home's launches before relaying, Burst's placeholder; a runner starts only launches relayed by Home, `launchpad_http::FROM_HOME`). Home builds what the lease holds (workspace, folder, bot, login, tools) from its own record of the session (`contain::request`), never from the runner's request, and replicas never change those fields. Only Home refreshes Codex logins; when the quota app-server on Home's copy refreshed a login itself, the vault keeps that newer login (`vault::login_home`), never writes a spent refresh token back over it.
- Test contained sessions with scratch daemons and token copies read without refreshing; check a Codex login's `last_refresh` before copying it into a test vault.

## UI rules

- Every action a button, a card, the CLI or the admin rules name is one entry of the action list (`crates/core/src/actions.rs`: route, input, confirmation, effect, access, card kind, undo). Add new actions there; buttons use `ActionButton` (it confirms when the action has a confirmation) or `runAction` (`web/src/lib/actions.ts`); run `gen-types` after changing the list.
- Build pages from `web/src/components/ui.tsx`: `PageHeader`, `Tabs`, `FilterChip` (narrows a list), `Choice`/`Choices` (the options of a setting, styled like the profile picker), `ConfirmButton` (every destructive or GitHub action; never `window.confirm`), `Loading`/`Empty`/`ErrorState` with `humanError`, `Badge`/`Token`, `StatusBadge`, `Count`, `RowActions`, `IconButton`, `SettingRow`. Text fields and selects use `field-input` with its default height and 13 px text (only `font-mono text-[12px]` for code values); buttons use `btn`/`btn-sm`/`IconButton`. Use semantic color tokens and sprite icons. One primary button per region.
- Sizes (tokens in `web/src/styles.css`, checked by `pnpm ui-check`): text only 11/12/13/15/18 px as `text-[Npx]` (Tailwind's `text-xs`, `text-sm`… are removed from the theme); corners `rounded-control` (6 px: buttons, fields and message boxes, menu items) and `rounded-card` (10 px: cards, panels, dialogs), `rounded`/`rounded-full` for marks and pills; icons 12 px inline, 14 px in icon buttons, 16 px in navigation (phone bar and tab icons may be larger); gaps from the spacing scale (`gap-1`, `gap-1.5`, `gap-2`…), never `gap-[Npx]`; page bodies `max-w-page` and reading columns `max-w-text`, left-aligned under the header with its `px-5`; no fixed hex or Tailwind palette colors (`red-600`…) outside the theme; never force an icon button's size (`size-…!`). Justified exceptions go in the script's allowlist.
- Action group: a list row or card shows at most one visible button, its main action as an outline button with a label in a right column of a minimum width (one exception: a finished or failed agent's Today row also shows Archive after it, on a laptop only); everything else goes in ⋯ (`RowActions`, built on `.lp-row-more`: shown on hover and keyboard focus, kept while its menu is open, always visible on touch screens; `MoreMenu` alone for a row or card without a main action). Menu entries are `MenuItem`s, actions of the action list use `ActionMenuItem`, and a confirmation (`ConfirmButton`) goes last in a `MenuSection`. The only filled button of a region is its single most important action.
- Icon-only buttons (`IconButton`) only in a toolbar where every button is icon-only, never mixed with text buttons (except ⋯, the menu of an action group); each has a tooltip and an `aria-label`; one size: 28 px laptop, 44 px phone, 14 px icon. Exception: the arrow after the "…" of a cut text (an agent's last message in Today) that shows the full text inline.
- States use `StatusBadge`, one color per meaning: blue running, amber needs you (question, quota paused, Inbox "for you"), green Done (an unseen Done adds an amber dot, never an amber pill), red failed or interrupted, grey idle, stopped or archived.
- Counts use `Count` (sidebar, tabs, chips, phone tab bar): an amber pill when the count needs you, a plain grey number otherwise.
- Dates use only `web/src/lib/format.ts`: `ago()` for past moments ("5 min ago", "yesterday", "Oct 3"), `age()` for the compact form in dense lists, `when()` for exact or future moments ("today 15:00", "Fri 7 Nov, 03:00", in the locale's clock); `time()`, `day()` and `month()` when a label needs only one part ("14:02", "Oct 3", "November"). Never `toLocaleString` for dates, never seconds, no year for the current year; callers never add " ago". Crons read as words (`describeCron`: "Every day at 03:00") with the raw cron in a tooltip.
- Page headers: every laptop page uses `PageHeader` (`SettingsPage` builds on it): the title without an icon, a meta line of facts (counts, sync state, never the workspace name alone), actions on the right and tabs under it; headers and page bodies share the 20 px side padding (`px-5`). A top-level page has no breadcrumb of its own name; a detail page's breadcrumb names its parents (Local PR: Folders / folder; GitHub item: Folders / folder / Pull requests or Issues, or Inbox without a folder; bot: Bots; Settings page: Settings).
- Words: Launch (start an agent; Start only for proposals), Delete (data) and Remove (only out of a list), Pull requests, Channels, Disk cleanup, Search in folder.
- Page explanations go in `PageHeader intro` or `SettingsPage intro`: shown on the first visit on this device (`launchpad.intros-seen` in browser storage, never config.toml; the demo keeps them in memory and never writes it), then behind ⓘ next to the title. One explanation per page; a list never repeats the same paragraph on each item, and cards and side panels hold no help paragraphs. Keep the meta line for facts.
- Virtualize every long list, memoize row components, use `useFlushSync: false` and prefer fixed row heights (WebKitGTK performance).
- Keep heavy imports out of `router.tsx`, `main.tsx`, both shells and the sidebar; other routes load lazily.
- The phone shell (`web/src/mobile/`) reuses feature components with `usePhone()`; never fork features. The phone bar shows the section title on a tab page, with the page's primary button and ⋯ on its right (`PhoneBarEnd`; a tab page adds no row of its own for them or for a count), or ‹, the title and the page's ⋯ or ⓘ on a detail page (`PhoneBar` or `PhoneHeader` with `onBack`, `web/src/mobile/PhoneHeader.tsx`, one per page); a page never draws a second title bar on the phone, and the ‹ in the bar is its only way back (no "All settings" or "Close panel" buttons; `useBack` for pages without a single parent, `useLeave` for pages that add their own history entries, like Files). Phone Today rows show the title on up to two lines and one one-word outline button of one minimum width, without its icon; a tap on the row opens the other actions. Keep 44 px touch targets (chips, choices, fields, icon buttons, labels around checkboxes; styles.css enforces them over forced sizes). Phone fields are 16 px through an unlayered rule in styles.css, so iOS never zooms on focus; never set a field's size on the phone elsewhere. Phone Settings sections are flat (one border level). Phone toasts sit under the top bar, never over the tab bar. Keep the desktop layout unchanged at every zoom position (100–150%, default 120%, per device).
- Phone tabs: Today, Agents, Ask (the chat of the `askTarget` bot, full screen, no back button), Inbox and More (`/more`: the other pages with their state, and the workspace). The workspace sheet lists only workspaces with their counts. Phone Settings is a list in three groups (This device, On the phone, On a computer; the last shows status only). The phone session page has a bottom bar with Reply and the main action, or Merge into the base branch when it is safe; Reply replaces the bar with the message box (Hide brings it back), so no other action sits above the keyboard. Archive shows an Undo toast (`session.unarchive`, from the `UNDO` list in `web/src/lib/actions.ts`). The phone status button warns about connection, runners (refused, outdated or offline), quota, spending and the GitHub rate limit, and its sheet says why; it sits in the bar of every tab page, and a detail page's bar shows it only while it warns.
- Theme, zoom and layout are device-local (browser storage), never in config.toml.
- Workspaces: every folder belongs to exactly one workspace (`project.workspace_id`). A window shows exactly one workspace, never all of them: the rail (laptop) and the workspace sheet (phone) show other workspaces as counts only. There is no default workspace: the owner names at least one in the setup's Workspaces step (adding or cloning a folder waits for it); Home refuses to delete the last one; runners never create workspaces and wait for Home's. Adding, cloning or creating a folder requires a workspace; a repository in two workspaces is two folders. Sessions, schedules, crons and inbox threads belong to a workspace only through their folder or repository; repositories without a folder belong to no workspace (Settings → GitHub lists them). Every narrowed list, count, `#`/`@` suggestion and message-context picker uses the `useScope()` predicates, except Today, which uses the workspaces Home resolved for each item with the same rules. Settings has two parts: **Workspace** (`/settings/workspace`, the window's workspace, its name in the meta line) and **Launchpad** (shared). Notifications name their workspace and open it.
- Demo mode (`web/src/demo/`) answers every request in the browser; never call the real daemon or write browser storage from it. A new major feature updates its tour chapter (`web/src/onboarding/chapters/`), demo fixtures and handlers, and keeps `data-tour` anchors (`pnpm test:tour` checks them).
- Setup: Home's setup page (`/setup`, `HomeSetup`, or the Space gateway's) asks for a workspace, Home's GitHub login, a profile with its login in the vault, the agents' Git identity, where agents run (Burst, or a runner with the command that installs and pairs it) and a first folder (Clone or New plain folder). A runner's checklist (`setup_checklist.rs`, in its own window) only reads: Home link, jail, network capture, agent CLIs, vault logins and Git identity; a missing part shows a fixed command to copy, and Launchpad never runs it (no setup terminals). Never overwrite an existing Git identity, credential helper, SSH key or harness login, never run package managers automatically.
- The Chrome extension panel is its own small UI: never import the app's Composer, SessionPane, router or phone shell; reuse only `lib/` helpers, pure store helpers, generated types and Markdown. Browser grants bind a device, document and URL, expire after 30 idle minutes and end on Stop/Archive. Consequential browser actions are always reviewed. Keep the extension ID/key and the daemon origin allowlist in sync.

## Git workflow

These rules apply unless the owner says otherwise for a given task.

- Work on `main`, in this checkout. Do not create other branches, worktrees or pull requests for this repository.
- Commit finished work on `main` with a short message that says what changed.
- Update the documentation in the same commit: `README.md` (features, getting started), the matching `docs/` page when a user-facing feature changes, `docs/architecture.md` when the design changes, and this file for new commands, rules or conventions. Keep documents short: describe behavior, not implementation history.

## Testing

This is a personal project: move fast.

- Add a test only for a small, specific part that clearly benefits from it, typically a pure function with tricky edge cases.
- No mocks of HTTP APIs, harness processes, git or the database. No tests that need a server, the network, GitHub, a running agent, the daemon or a full `App`.
- The whole test run must take a few seconds; no test may take more than a second. Delete slow or flaky tests.
- Check changes by building and running the app in the dev environment.
