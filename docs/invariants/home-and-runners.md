# Home and runners

The design invariants every change in this area must keep. Read this page before changing the area, and update it in the same commit when a rule changes or a new one appears. [AGENTS.md](../../AGENTS.md) keeps only the cross-cutting rules; index of all areas: [README.md](README.md).

## Home and runners

The replication, relay, move and Burst design is in [architecture.md](../architecture.md); these rules must hold.

- Home (`launchpad daemon`, the default role; `--role home` is a no-op) runs no agents or terminals (it relays terminals to runners, see [Terminals](terminals.md)), and a runner (`--role runner`) holds no records of its own; there is no role that does both. Home never reads a runner's disk in process: every lease, MCP, Git, plain-folder and knowledge-base call of a runner goes to Home over its link. Runners replicate through `home_outbox` (same transaction, dropped only after Home's `Durable` mark, see below): one batch in flight, cut at `replica::BATCH_BYTES` (4 MiB; a larger item goes alone, one over `MAX_ITEM_BYTES` loses its inline data URLs or becomes a marker Home skips, so the outbox always progresses); Home acknowledges the last item it stored (the one before the batch when none) and the runner sends the next batch from that acknowledgement (`replica::after_ack`), so a failed item is sent again, never skipped; a runner drops items only at Home's `Durable` mark (a verified backup holds them, `replica::set_durable` after `home_backup::verify_base`; none from a Home without backups or an older Home, then at `Ack`; sent only to runners with `durable_ack`), detects a Home that went back on reconnect (`replica::reconnect`/`welcome`: replay, or requeue its session records after a gap), and a restored Home (`home_meta.checkpoint_at`, `replica::restored`) accepts an unknown session only with Home's placement proof (`LaunchSpec.placement`, `runners::sign_placement`; key created at start before any backup, `init_placement_key`, and used only once durable; a record without a valid proof goes to `replica_orphan`) and replays kept wake-ups (`replica::Item::Sleep`, `schedules::replay_sleep`; acknowledged only after success or an intentional discard, `replica::ack_after`, and never skipped by `give_up`, `replica::NeverSkip`); while frozen Home stores nothing; only an item that kept failing for `replica::GIVE_UP_MS` (10 minutes) is skipped, logged as an error. The Space gateway's WebSocket limit matches the daemon's 64 MiB (`wire::MAX_MESSAGE`); apply runner items only through `Sessions::apply_replica`/`projects::apply_replica`, and keep the generation and runner checks (session records and events count only for a session Home placed on that runner).
- Workspaces, Git folders, Home Git, Local PRs, review drafts (`/api/review-state`) and scheduled follow-ups are Home's: runners keep copies and forward changes (`home_client::home_owned`); Context reads (`/api/context/*`) and every trace (Home holds all generations; the runner waits for its backlog and answers itself only when Home is out of reach) also come from Home, so any agent runs and resumes on any runner. Home also sends its profiles and the settings runners apply to their own work (`ToRunner::Settings`: `[worktrees] keep` of config.toml) on connect and after each change. A runner is a low-trust worker (`runner_trust`): its credential reaches Home Git, plain folders, handoffs, leases, quota readings, replication and uploads for the sessions Home placed on it, plus a closed list of requests its own work needs (`runner_trust::may`, each scoped to its sessions and folders by `runner_trust::check`); it reads plain stores (knowledge bases, bot files, plain, asset and temporary folders, `plain_http::caller`) and Local PRs only of the workspaces of the sessions Home placed on it (`scope::of_runner`: running, or archived in the last day), while folder and workspace records go to every runner (`ToRunner::Folders`) and Home Git serves any folder (repository caches for terminals); everything else it sends is an agent's call checked with that agent's access (see the Launchpad CLI rule in [proposals.md](proposals.md)). Nothing a runner sends runs as the owner: no vault, MCP settings, connections, Outbox, Suggestions, Local PR publication, Home update or owner action, and no session or trace of another runner unless Home sent it as context (`Hub::grant`). Tunnel exchanges carry only runner-authenticated paths (`exchange::home`). The tunnel protocol is the same whichever side dialed (`server::wire`). One writer per connection sends two lanes (`wire::lanes`): the control lane (pings, requests and answers, acknowledgements, replica batches, snapshots, terminal frames) always goes first, and the bounded bulk lane carries exchange body parts. Each exchange body keeps to a 4 MiB window (`wire::WINDOW`): the sender waits for the reader's `HttpAck`, and the receiving loop never waits (`wire::Inbound` refuses a sender past its window); a peer of an older build (no `Capabilities.flow` or `Welcome.flow`) gets no window, so it can still download Home's build. Dropping an exchange cancels it on the other side (`HttpCancel`: the runner's cancel stops Home's task and its upstream; Home's stops the runner's upload), and a connection's exchanges end with it. Never add an unbounded queue for bulk data.
- A runner's own window shows its status only (`web/src/features/runner`): its Home link, Takes new sessions (`runner.takes-sessions`, local, never synced; paused means Home starts no new session there) and its setup checklist; its daemon refuses every other call from a signed-in browser (`auth::runner_window_path`). Bearer clients are unaffected: Home's tunnel (including relayed terminal viewers), the CLI and agents' session tokens (agents' launches, routines and scheduled launches go to Home, `home_client::forward_writes`). A runner refuses a launch that Home did not relay.
- Seen and unread are recorded on Home. Archive of a session whose runner is away closes the record on Home (`runners::archive_away`) and is delivered once when the runner reconnects; Keep as folder of a temporary folder whose runner is away runs on Home (`projects::keep_away`), refused when the folder's last handoff saw Git data (`Handoff.temp_git`). Home never touches a worktree folder: worktree actions and Local PRs of a worktree reach the session's runner through the relay (`?session=`) or are answered from Home Git when it is away; what reaches Home's own handlers is refused.
- Placement (`runners::place`) is the only way Home picks where a session continues: its runner when connected; else, between turns, a move to another runner that takes launches (`runners::pick`: the previous runner, else the least busy); else Burst; else a clear error. Burst is always last. It serves the owner's messages, Resume and answers (relay), bot, proposal and report-reply messages, Local PR review requests (`runners::send_anywhere`) and scheduled follow-ups (`schedules::run`; a busy session answers 409 and the follow-up stays queued); launches use the same order (`launch_anywhere`, Home only), never fall back from a runner chosen in the composer, and move the sessions of a runner that does not take launches (away, paused, outdated) first when they continue in a session's folder (New agent here, Run in) or a temporary folder: to another runner, else to the Burst job, which takes them before it starts the launch (`runners::move_pinned_to`).
- A session still Running, asking or paused for quota on a runner that left (or that the owner removed) becomes Interrupted on Home after `runners::AWAY_GRACE_MS` (10 minutes), with a note as its last message, so it can continue elsewhere from its last handoff; a runner that comes back with the same generation replaces the record. A runner releases the sessions Home moved away from it (`handoff::release`; queued by every move, online or not, in `state.db` (`runner_delivery`) and delivered with `runners::deliver_pending` when it is connected, and again every 10 minutes while items wait; an item, like a pending Archive, is dropped only after the runner answered it; a release takes the session's `adopt:` lock, so an adoption of a newer generation waits for it): it stops them, pushes their commits and uncommitted files to `lp-scratch/<branch>-gen<n>` (with the daemon's Git token: Home refuses the session's own once it runs elsewhere), removes their folders only after Home confirmed that push, and forgets them. While a Burst job starts for a session, placement sends its other requests (messages, Resume, answers) to that job: they wait in its run record (`BurstRun.queued`; a retry with the same idempotency key is kept once) and follow the first one in order; a failed start fails them with it. An automatic follow-up as the job's first request (a sleep's wake-up), refused with 409, is sent again for 30 seconds, then as `follow_up: "held"` (`burst::first_request`), which the runner holds in a quota pause until a reading confirms quota (`hold_input`), never lost.
- Agent CLI updates (`crates/setup/src/cli_update.rs`): Home decides (`cli_update::plan`: a newer release of the same major version, the same minor for 0.x, installs on its own; a new major version waits for the owner's Approve), records each runner's entry before it asks the runner and never asks again after a failure or a restart (Retry is the owner's click). Only the runner daemon installs, never an agent, with the installer that installed the CLI (npm prefix or the CLI's own), after its sessions stopped running and holding `harness::CLI_INSTALL`; a CLI it cannot write is reported with the command, never forced. Burst and Home's Space keep the pins of `deploy/hf-home/release.json` (`bump_tools.py`). Never run a real CLI update in checks: it replaces the machine's own CLI.
- Runner updates (`self_update.rs`) start only on an owner click (Update, or Update Home with Then update the runners) or an admin session's direct action when the owner asks (`runner.update`, or `home.update` with `update_runners`), wait until no session of the runner is running, verify Home's build (SHA-256, OS, architecture) and restart in place. Test them only with scratch daemons and copies of the binary, never on the owner's runners.
- Home updates (`crates/setup/src/home_update.rs`, Home on a Space only): the hourly check only reads (GitHub, the Space's info and Dockerfile); Update Home (`home.update`: the owner's click, an admin session's direct action when the owner asks, or a ready card) commits the target's `Dockerfile.release` (newest of the deployed channel, or of the `channel` asked for) to the Space on top of the checked revision only after the write barrier (`launchpad_core::maintenance`, `home_update::start`): record saved (`Pending.phase` Draining), maintenance entered (status `maintenance`, banner in every window; `server::maintenance::gate` refuses every non-read request with a retryable 503 and `Retry-After`, except Git fetches, `/api/home/update`, `/check` and `/cancel`; schedules, routines, queued bot messages and Telegram wait), running writes drained (`maintenance::drained`), the asking agent's continuation stored with its sleep (`schedules::update_wake`), the record set to Replacing, `state.db` frozen (`maintenance::freeze`: `PRAGMA query_only` on the single writer; writes fail as `maintenance::Paused`, a 503), then the final checkpoint taken and verified in the destination itself (`home_backup::checkpoint`: the bucket behind the mount, `LAUNCHPAD_HOME_BACKUP_REMOTE`, `state.db` downloaded and hashed). Any failure before the commit thaws, leaves maintenance and records Failed with why (`abort`); never commit without a verified checkpoint. A commit failure thaws only on the Hub's 4xx answer (`commit_refused`); a timeout, lost answer or 5xx keeps it frozen. After the commit Home stays frozen until `fenced` (head ≠ the update's `parent`, head without the target, runtime stage RUNNING with `running_revision` equal to the head; never inferred from a missing runtime revision or a failed stage): never thaw on a timeout or a failed build. The owner's Cancel update (`home.update-cancel`, owner only) commits `previous_dockerfile` on top of the head, which fences it. At start, before serving, `home_update::resume` marks Replacing Done when the commit matches, else re-enters maintenance. A retry after a lost answer returns the update's state (`retry_answer`), never a second commit. Never rely on the shutdown's final backup (skipped while frozen). Never replace a Dockerfile that deploy.sh did not write or a source build. The call returns once the Hub accepted the commit, before the restart; runners forward `/api/home/update*` to Home. `update_runners` (Then update the runners) is an optional input: the owner's button, an admin session when the owner asks, or a ready card the owner clicks. The runner follow-up asks each runner once (claimed in the `home_update` record before the request), for 24 hours. Test only with a throwaway Space (`deploy.sh --space`), never the owner's.
- Moves (`handoff.rs`) happen only between turns, one at a time per session: every move and placement takes `runners::place_lock`. The old runner's final handoff (when it is connected) pushes branches and saves leftovers to `lp-scratch/…` first; then Home increases the generation and names the new runner. The final handoff runs as a job on the runner that Home polls with one key (`handoff::final_job`, `final_on`), so a slow one is waited for (up to 30 minutes), never reported failed while it still runs. A failed adoption does not undo the move: the new runner adopts the session when Home relays its next request about it (`home_client::local`, `handoff::adopt_moved`, only for a generation above 0); adoption is idempotent. The adopting runner numbers its events after a gap (`sessions::MOVE_SEQ_GAP`), so late events of the previous generation are stored below them, never dropped or overwritten; Home's `last_seq` is its last stored event (a runner's record never raises it), so a trace through it always exists. A worktree whose merge stopped (conflict or failure) moves with its record; only a waiting merge holds the folder. Runners remove an archived session's folder only after Home confirmed the unchanged native files; a start restores them from Home. Harnesses save their traces and history normally in a contained session's harness home; never turn that off. Home keeps handoff files in its blob store, never in `state.db`. A handoff sends a native file Home confirmed for the session by hash, or only its appended tail on top of that file of the session's latest handoff on Home (`handoff::part`), to `/api/handoff/{id}/parts`, a path an older Home refuses; Home rebuilds the whole file and checks its hash, and a refused short handoff is sent again in full at once (adoption and restore tell the runner what Home holds), so Home always holds complete, unchanged files. Adapters own `native_trace` and `restore_native`; never synthesize a conversation from events. A harness whose conversations live in its own database restores at the next start, in the session's jail and folder (OpenCode: the unchanged export waits in the harness home and `opencode import --pure` reads it; a failed import fails the start).
- Home backups: content-addressed objects (with uploads, `home_backup::data_files`; a full `state.db` copy at most every 10 minutes on the timer (`DB_EVERY_MS`), at once before a planned stop and for Back up now or Update Home (`home_backup::When`), and backups of Home Git or uploads in between list the last copy with the plain blobs and uploads it needs; a `runner-archives.json` of an older backup is restored and imported into `state.db` at start), manifest written last, restore only from a complete manifest (every object present) with matching hashes (checked on download; Home Git bundles and plain blobs download when first needed). A live plain blob already in the destination stays listed by hash whether or not Home's disk has it; one that is neither on Home nor in the destination is left out and reported (`BackupInfo.missing_blobs`), never skipped silently. A listing or download error is never an empty answer (only a prefix that clearly does not exist lists empty). Retention (`home_backup::prune`, spawned after a complete backup, under `Backups.running`, last result in the backup status): keep set from `retained` (two newest, newest ≥1 h, newest ≥1…10 days; unknown or future times kept); it deletes nothing after a listing or download error, when the listing misses the manifest just written, while a manifest of the last day (or of unknown time) does not parse (`check_readable`), or unless the newest backup is verified complete; manifests deleted before objects; objects deleted only when no manifest of a fresh listing lists them and uploaded at least an hour ago (`unused_objects`); only under `home/backup/` and `home/blobs/`; a failure never fails the backup. A boot restore retries, then fails the boot instead of starting empty (only a destination with no backup objects starts fresh; objects without a readable manifest fail it). A restored mirror's bundles (`git_restore.json`) stay pending, and carried in every backup (`git/<id>.pending.bundle`, so retention keeps them), until applied: each use of the mirror and each backup pass retries (`home_git::ensure`, `retry_restores`), first fetching by ID from the remote the bundle's prerequisites the mirror lacks (`refs/lp-prereq/`), then fetching into `refs/lp-restore/` and creating only refs the mirror does not have (a differing restored branch tip goes under `refs/kept/`). A failed try never fails the mirror's use: it backs off (one minute doubling to six hours, `home_backup::claim_restore`) and shows in `BackupInfo.restore_errors`. Bundles leave out only the remote's default branch and tags (`home_git::bundle_revs`), never other remote branches, which a remote may delete. Test with a local folder destination, never a real bucket.
- Burst (`burst.rs`): the runner secret is derived, never stored, and a Burst lease carries no secret (`token_relay`). One job per session; stop it only after the final handoff and a complete Home backup newer than the stored handoff time (`handed_off_at`), or 15 minutes after the handoff without one (`burst::after_handoff`): the run then fails with the reason and a notice in its sessions, since the handoff is only on Home's disk until a backup succeeds. An hour before HF Jobs' 24-hour limit, Home stops the job's open turns once (claimed in the run record, `limit_stop_at`, before the requests) with a notice in each session, so they hand off, and messages to them move them elsewhere. Starts claimed before a Home restart are cancelled, never retried. A Burst runner without Home stops on its own only after 30 minutes (three hours while an agent works or its outbox waits, `home_client::burst_stops`), so its jobs outlive a Home update. Respect `[home.burst]`. Test with a scratch Home and scratch bucket (`LAUNCHPAD_BURST_IMAGE`, `_COMMAND`, `_VOLUMES`) and cancel every test job.

- Exit routes (`egress.rs`, `[[egress]]` in config.toml, Settings → Home and runners → Exit routes): the owner's routes send matching URLs (a GitHub organization's prefixes, `require`, plus GraphQL and search, `prefer`; or explicit URL prefixes, all `require`) out through one runner, the exit runner (`via`: one runner's name or ID, never Burst), for Home (its git through `http.<prefix>.proxy` and `proxyAuthMethod=basic` in `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` variables, never `-c`, so the bridge's secret stays out of process lists; the GitHub client, Burst relays, oracle tools) and machine runners (the runner proxy). Matching is pure (`egress::matching`: lowercase host and path on segment boundaries, query ignored, `require` before `prefer`, then config order; `matching_host` for whole-host prefixes only). Callers pick a routed client per request (`egress::Clients`, never `reqwest::Proxy::custom`, which sees only the origin); the loopback bridge (`egress::bridge`, Basic `<route>:<secret>`; CONNECT, and a plain `http://` request in absolute form, which it sends on in origin form with `Connection: close` both ways, so one connection carries one request), Home and the exit only carry TCP to `egress::targets` of the route, so a token never leaves the machine that adds it. Home dials the exit (`ToRunner::Dial`) and splices exchanges (`HttpTarget::Egress` from other runners, `HttpTarget::Dialed` from the exit) on the existing windows; Home and the exit both check the target, and the exit refuses its own loopback, link-local and metadata addresses (`exit_refuses`; validation refuses them in URL prefixes too), while private and tailnet ones are the point. A pending dial is dropped with its caller (`Forget`), so a cancelled exchange leaves nothing behind. A routed request that could not connect shows the bridge's refusal (`egress::refusal`), not reqwest's "unsuccessful tunnel". Home resolves the states (`egress::spawn`, on `config` and `runners` events; `egress`/`changed` when they differ) and sends them in `ToRunner::Settings`. An offline exit fails at once with one message ("<org or host> is reached only through runner <exit>, which is offline (route <name>)."; git's "from proxy after CONNECT" is rewritten from `egress::last_refusal`; the GitHub client fails before sending, never DeliveryUncertain; the proxy and Home's relay answer 503 with it; oracles raise OSError, class http); `prefer` prefixes go direct while it is offline. `egress.set` (`PUT /api/egress`, undo through `GET /api/egress`) is the owner's, never admin and never in `settings.set`; `GET /api/context/egress` (states only) is a Launchpad-wide read at every CLI level (`launchpad egress list`) and `tools.launchpad.egress.list()` in oracles. Access log entries name the exit (`Access.via`).

## Other machines

- Agents run only on runners (a machine's runner daemon, a Local VM or Burst); there are no SSH hosts and no single-process mode. Another Linux machine joins as a runner that pairs itself with Home (`launchpad connect`), never through a connection Home opens into it.

## Trace copies

- Home copies each session's native files from its latest handoff, unchanged, after each backup (`trace_copies.rs`): `<workspace>/traces/<folder>/<YYYYMMDD_HHMM>_<id>/`, one file per trace plus `launchpad.json`. Adapters export native traces unchanged (`Harness::native_trace`); never synthesize native traces from normalized events. Home never reads the copies back. What the copies already hold (`trace-copies.json`, `readable-copies.json`) is also kept in the destination (`home/copies/`, `home_backup::save_copy_state`), so a restored Home does not copy everything again.
- There is no peer trace sync between instances. Never log in or change bucket visibility; only a renamed workspace or folder deletes the old copies.
