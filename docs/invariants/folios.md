# Folios

The design invariants every change in this area must keep. Read this page before changing the area, and update it in the same commit when a rule changes or a new one appears. [AGENTS.md](../../AGENTS.md) keeps only the cross-cutting rules; index of all areas: [README.md](README.md).

- A folio (`launchpad_automation::folios`, routes `/api/folios/{workspace}…` in `crates/api/src/folios.rs`, Home-owned, runners forward them) is a workspace record (`folio`: slug, title, kind, state, author, rev, topic, thread) plus a plain store `folio-<id>` (`plain::folio_store`) that only Home writes, through `folios::write` (one writer at a time, `plain::write_files`; `plain::commit` refuses folio stores). Each write is one rev (`folio_rev`: the files it changed before and after, its author and problem counts), with diff and Restore (a new rev). An agent's `launchpad folio done` (`folios::done`, `folio.done`) squashes its own newest revs that no done closed yet (`open_revs`: back to another writer's rev, a closed one or a named version that is not the newest) into one closed rev (`sealed`) numbered like the first, labeled with its message; marks, links, render reports, a named version and a share that named a squashed rev name the new one. A write may name the rev it read (`base_rev`): a file changed since keeps both versions (`<name>.concurrent-<id>.md`; a patch whose section changed since goes on that rev's page, kept the same way), and a removal of a file changed since keeps the file. The check reads such kept versions as F108 warnings, not as pages. Runners forward a folio write whole up to `agent_auth::FOLIO_BODY_MAX` (8 MB). Hard limits refuse a write (a path outside the folio, a file over 2 MB, a page that is not UTF-8); otherwise it is saved and its problems listed, and only `strict` refuses a write with errors.
- The format: CommonMark and GFM, `:::` containers and fenced YAML typed blocks, defined once in `folio_catalog.rs` (containers, blocks with their fields, rules, kinds; `gen-types` writes `web/src/gen/folioCatalog.ts` and the block data types, a test keeps both in step). The line-based splitter exists twice, `folio_split.rs` and `web/src/lib/folioSplit.ts`, with the same rules and the shared fixtures; change both together. The check (`folio_check.rs`: F1, F2, F3, F5, F6 of `RULES`) runs on every write, on `folio check` (also offline with `--dir`) and for the reader's problem boxes; `--fix` applies only one-line fixes with one clear answer.
- The reader renders Markdown with markdown-it, raw HTML off, then DOMPurify; images load only from the folio's sandboxed raw route (`nosniff`, `CSP: sandbox`), never the network. Sketches (```sketch, `sketches/*.html`) are the only agent JavaScript: they run only in `<iframe sandbox="allow-scripts" srcdoc>` (opaque origin) whose document starts with `SKETCH_CSP` (`web/src/lib/folioSketch.ts`: no network at all, images and fonts as data: URLs; the reader inlines the folio's images), with the theme's variables, the built-in kit and the folio's `sketches/_kit.html`. Their only way out is `folio.data`, a postMessage bridge the reader checks (`event.source` is the frame's window, the token, the sketch's key prefix `folio_check::sketch_prefix` = `sketchPrefix`, read-only on older revs, 60 calls per 10 s, 64 KB per value) before calling Home. A frame's own navigation is not covered by its CSP: `web/index.html` and `web/folio-viewer/index.html` set `frame-src 'none'` (srcdoc frames are exempt), so a sketch cannot leave its frame to send data out, and a frame that loads a second time is replaced and reported as F701; never add a frame that loads a URL. Mermaid (`mermaid.tsx`, strict security level, no HTML labels, SVG through DOMPurify and `cleanSvg`: no images or foreign objects, links and `url(…)` only to its own `#ids`) and charts (`chart.tsx`, own SVG, series colors `--folio-series-N` in styles.css) are lazy chunks; keep them out of router, main and the shells.
- The data API (`folio_data.rs`, table `folio_data`, routes `/api/folios/{ws}/{slug}/data[/{key}]`, `launchpad folio data get|set|list|rm`): JSON values, last write wins, 64 KB per value, 1 MB and 2,000 keys per folio, keys of letters, digits and `_ . : / -`; every level reads, propose writes as the session's own write, the owner's window writes through a sketch's bridge. A shared snapshot has none. Rules F4 (sketch size, network use, keys outside the prefix, unclosed `<script>`/`<style>`) run with the check; render problems F701 (sketch errors, blocked requests, empty frames), F702 (Mermaid and chart errors) and F703 (sideways scrolling on a phone) are what the owner's reader saw: it saves them per rev and page (`folio.render-problems`, table `folio_render`, replaced by each report of that page), and `check` and the reader list them with severity `render`. Unknown blocks (```x-…) and containers are counted per folio at each write (`folio_block_use`) and listed as block requests on the Folios page.
- Access: every Launchpad CLI level reads (`agent_auth::folio_need`); propose creates, writes, fixes, replies and resolves as the session's own writes (Home takes the author from its session record); marks, Send feedback, Restore, Archive and Delete are the owner's (`folio.*` in the action list). The workspace boundary is the route's `{workspace}` (`Names::Workspace`).
- A writing session joins the folio's topic and gets a `folio_link` row; a new title renames the topic while it still has the name Home gave it; a bot's session also makes its thread the folio's thread when it has none. Marks (`folio_mark`: the owner's comments, verdicts, choices and ticks, agents' replies; `seq` orders every change for `feedback --since`, which also lists sent marks the owner removed since as `cleared`) are saved at once and unsent until Send feedback (`folios::send`), the owner's click, which sends one short message to the folio's bot thread (`bot_threads::Source::Folio`, key `folio:<id>`), a session that wrote it, or a new thread of a bot with the folio's topic as context (that thread becomes the folio's thread); the marks become sent only after the message went, one Send at a time, and only the marks it counted. Ask the author to fix (`folio.ask-fix`, the Problems panel) sends one line to the same first recipient and leaves the marks unsent. The reader's links of typed blocks take only http(s) and mailto addresses; a comment whose id is gone is placed again by its quote (`relocate`), else shown outdated. `renamed_from` on an item moves the owner's marks to its new id; rule F206 lists marks whose id is gone. A folio adds no Today row.
- Folios as context (`MessageContext.folios`, `LaunchSpec.folios`, `FolioRef`: a folio, optionally a page, a section, items and a quote) are references, never the text: Home resolves them in `folio_ref::resolve` (from `runners::launch_placed`, `runners::deliver` and the start preview; the core reads the `folio` table itself) against the session's workspace, freezing slug, title and rev (pages, sections and items are ids of letters, digits and `-_.:`, plus `/` in pages, so the read command holds nothing else); the prompt gets one line per folio with its `launchpad folio read` command and the quote fenced, labeled as agent-written reference material (`folio_ref::notes`); the receiving session joins the folio's topic and gets a `folio_link` row with role `attached`. The composer, message boxes, the bot chat and Ask take them through Add context → Folio… and `@` suggestions. The reader's selection offers Comment, Ask bot (`folio.ask`, the owner's question to the folio's thread with the folio as context, like Send feedback's recipients) and Launch (the composer with the reference); a prompt block's Launch with this prompt opens the composer filled in. The agents bar lists `folio_link` sessions with their role; a finished agent that created or edited a folio gets Open folio as its Today row's main action, after Fix merge and a Local PR.
- Named versions (`folio_version`: a rev's file list, `folio.version`, `launchpad folio version`, agents at propose access) are kept for good: `plain::live_blobs` lists their blobs and `files_at` reads them first; Unpin (`folio.unversion`) is the owner's. Home's readable copies (`home_backup::readable`) hold each folio at its latest rev under `<workspace>/folios/<slug>/`; never read back.
- Share (`folio_share.rs`, table `folio_share`, `folio.share` with its confirmation, also a ready card; `folio.unshare`, `folio.share-extend`) is the owner's click only: Home publishes a static snapshot of one rev (the folio-viewer build `web/dist/folio-viewer/`, built by `pnpm build` from `web/folio-viewer/` and `src/viewer/`, embedded with the UI and handed over by `crates/cli` with `folio_share::set_viewer`; `folio.json` with the rev's files, the owner's decisions only when asked; a card with `sdk: static` and tag `launchpad-folio`) as the Space `<owner>/folio-<slug>`, private by default, through the Hub's HTTP API with Home's Hugging Face login. It refuses a Space it did not create, and a create the Hub refused drops the share record, so Stop sharing, Delete and expiry only ever delete a Space Home created; an agent's ready card names only its own workspace (`proposals::check_scope`); it expires after 30 days unless kept (Extend, Keep); Home's hourly task deletes expired Spaces and those of deleted folios (a deleted workspace keeps its `folio_share` rows for that); Stop sharing and Delete delete the Space. `LAUNCHPAD_FOLIO_SHARE_DIR` writes snapshots to a local folder instead (the dry run checks use): never create, update or delete a real Space or bucket in checks. A snapshot has no comments, data API or live updates.
- A folio with no change and no open or unsent mark for 30 days archives itself (`folios::archive_stale`, hourly on Home); Bring back restores it as it was. A deleted workspace deletes its folios.
