# Ask Launchpad, the Launchpad CLI and proposals

The design invariants every change in this area must keep. Read this page before changing the area, and update it in the same commit when a rule changes or a new one appears. [AGENTS.md](../../AGENTS.md) keeps only the cross-cutting rules; index of all areas: [README.md](README.md).

- Ask Launchpad is a normal bot with no special code path: Home creates it once per workspace (`ask_bot::seed`, recorded in the `seeded` table) without a folder; the owner may edit, replace or delete it, and Home never recreates it. Never add Ask-only branches to sessions, crons, hooks, proposals or the UI. The top-bar Ask and the Ask panel send to `askTarget` (`web/src/lib/bots.ts`: the oldest admin bot of the workspace, else its oldest bot) or the bot the owner picks; the top-bar button names that bot and its ▾ picks another, both from `askRecipient` (`web/src/lib/askRecipient.ts`: a pick on a bot's page lasts on that page, other picks per workspace in memory), so the label and the recipient always agree.
- The Launchpad CLI is a tool of Home's registry (`vault::LAUNCHPAD_TOOL`), added once and granted to every workspace, with three access levels (`vault::LaunchpadAccess`): **read** (`/api/status`, `/api/context/*`, `GET /api/proposals`, bot channel list and read, the workspace's oracles: list, show, history and `oracle.run`), **propose** (plus `POST /api/proposals`, bot channel posts and DMs, and `launchpad ci approve`; the default for bots and every other agent) and **admin** (plus Launchpad's own records: exactly the `admin` actions of the action list, `crates/core/src/actions.rs`, through `launchpad do`, short verbs or `launchpad api`: bots, routines, schedules, workspaces, folder settings (`folder.set`, never the setup command), new empty Git folders of its workspace (`folder.create-git`: a name only, no path, URL, setup or clone), shared settings (`settings.set`), proposal start and dismiss, launches and session messages, Local PR discard and its undo (`local-pr.discard`, also a ready card, and `local-pr.reopen`, which restores the branch at its recorded tip, `Predraft.discarded_head`; `worktree.discard` stays the owner's), MCP tool switches, Home update check and install (`home.check-update`, `home.update` with optional `update_runners`, effect `Installs`: the only admin action that is also a ready card), runner updates to Home's build (`runner.update`, effect `Installs`, and `runner.cancel-update`); GETs of one record of its workspace; it never reads `GET /api/config`). `agent_auth::admin_allows` matches routes exactly (no trailing slash, no empty segment), and an admin request body may hold only the action's input fields. Accepting a card runs the action its kind maps to (`actions::for_card`), so an admin session may accept a card only when that action is an admin action; tool cards wait for the owner. Admin also reads diagnostics, never secrets: `agent_auth::diagnostic` routes (`/api/logs`, `/api/context/{health,failures,runners,burst,home,tools,connections}`, `crates/api/src/diagnostics.rs`) leave out tokens, vault values, runner secrets, webhook URLs and pairing codes, and log lines are redacted when written (`launchpad_http::logs::redact`); the owner routes of runners, Burst, the vault, connections and backups stay closed. On a runner, an agent's calls about Home's records (`home_client::goes_to_home`: Home's records, sessions it does not run, launches, Local PR records, folder settings, and every other read and admin action except `/api/status` and Local PR `resolve`) go to Home with the agent's session, and Home checks them itself (`runner_trust::agent`: a session Home placed on that runner; then `agent_auth::authorize` with the session's access from Home's own records, `vault::session_access`, and the activity list on Home), never as the owner. Workspaces are a boundary for agents (`launchpad_core::scope`): a session reads and changes only records of its own workspace, checked on Home, where a runner sends every agent read and admin action (`home_client::agent_to_home`), by `agent_auth::within_workspace` (one check per route family, `names`): lists are narrowed to it (`?workspace=` forced), a record of another workspace (session and its trace, bot, routine, scheduled launch, card, folder, Local PR, worktree, tool defaults, a repository of another workspace's folders) is refused, reads that span every workspace (`GET /api/sessions`, `/api/bots`…) are refused, and the folders, sessions, bots and traces a launch spec, a message context or a bot's settings name must be of the workspace (a spec without one gets it; `folder.set` never moves a folder to another workspace). An agent changes a Local PR's text only for its own session's Local PRs. `workspace.create` stays allowed; `workspace.rename` and `workspace.delete` only for its own workspace. Presets and the other shared settings, profile defaults, MCP switches, Home and runner updates, agent CLI update checks and diagnostics stay Launchpad-wide. The owner is never limited. Home records each direct admin action in the activity list (`launchpad_automation::activity`) with the values before and its undo call; the bot chat shows it as a Changed line (the record name links to its page). Bots set the level with `launchpad` in `bot.toml`; Ask Launchpad is created with admin. Home puts the level in the lease (`Lease.launchpad`); `agent_auth` enforces it on the session CLI token (on the runner, and again on Home with Home's own reading of the level for the calls a runner forwards), and `launchpad_cli::cli_reference` tells the session what it may do. A session without a lease on its machine gets propose. Admin never grants a permission (see [Harnesses and sessions](sessions.md)), never reaches GitHub, the Outbox, connections, credentials, devices, terminals, hosts, runners (except `runner.update` and its cancel), setup fixes, backups, Burst, config.toml (except the closed shared-settings list of `settings.set` through `/api/settings/shared`: presets, worktrees kept; and `profile.set` through `/api/settings/profiles/{id}`: a profile's `model` and `effort` only, validated like the owner's form (`defaults_problem` in `crates/server/src/routes.rs`), Launchpad-wide; never env, login, billing, limits or `models_url`), folder setup commands or paid usage (`agent_auth::admin_allows`); keep that list closed. Every config.toml write, the owner's or an agent's, goes through `ConfigHandle::update` (read, change and save under one lock).
- Proposals are inert. Every start needs an owner click, except one-time launches, messages and schedules of a bot whose `bot.toml` says `proposals = "auto"` (automatic work: they need confirmed quota, see [Profiles, quota and costs](quota.md)), and what an admin session does directly; proposed crons, routines, presets, bots, tools, bot file changes, channels and join requests always wait (an admin session may accept preset, channel and join cards). Ready cards (`ProposalBody::Ready`, actions with `ready: true`: merge, publish, post, send, run CI, push to a PR, Home update, Local PR discard) prepare an owner action: they run only from their own button, with the action's call and confirmation, then `POST /api/proposals/{id}/ran`; accepting never runs them, and Start all and auto mode skip them. Paid usage is forced off. A session proposes only in its own workspace (`proposals::check_scope`): the card's workspace is the author's, and the folders, sessions, bots and traces of its launch specs, the session of a message or status card, the sessions a schedule waits for, the session, Local PR or worktree of a ready card, the bot of a bot-files card, the channel and bots of a channel or join card (checked by `launchpad_channels::cards`) and the repository of a report or ready card (when another workspace's folder holds it) must be of that workspace; an admin session starts only cards of its workspace. Auto mode never starts a message to a session with admin access: it waits for the owner's click. Preset proposals create or update presets and never delete them. Reports (`ProposalBody::Report`) start nothing: Mark read dismisses them, Reply (`proposals::reply`, claimed like a start) messages the author's thread (its bot's thread of the reporting session, else its session); a new report replaces the waiting one of the same author (bot, else session), workspace and GitHub item; `needs_you` reports list under Answer, the others under Review.
