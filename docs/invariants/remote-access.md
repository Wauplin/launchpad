# Remote access and devices

The design invariants every change in this area must keep. Read this page before changing the area, and update it in the same commit when a rule changes or a new one appears. [AGENTS.md](../../AGENTS.md) keeps only the cross-cutting rules; index of all areas: [README.md](README.md).

- `[server] bind` defaults to `127.0.0.1`. `public_origin` (explicit) or Tailscale discovery (`auto_tailnet`) defines the exact allowed Host/Origin. Never infer allowed origins or Secure cookies from forwarded headers. Startup discovery is read-only; never adopt Funnel routes or another daemon's port.
- Owner-clicked Tailscale setup runs only a fixed `tailscale serve` root proxy for this daemon; it never runs arbitrary input or overwrites routes.
- Pairing links are single-use and expire after five minutes. Reverse pairing binds approval to a separate tab secret; never exchange the short code alone for a credential. Every paired browser has full access.
- Devices (`browser_device`, with `kind` browser, extension, desktop or phone; Settings → Devices lists each with its kind and last activity, and Revoke is `device.revoke`). Browsers sign in with a cookie. The Chrome extension (origin `chrome-extension://<EXTENSION_ID>`, the only origin that gets CORS headers and preflights) sends its device secret as `X-Launchpad-Device` instead: accepted only with that Origin or with no Origin (Chrome sends none on an extension's GETs to a host it has permission for; a web page of another origin always sends one), never falling back to a cookie, so Disconnect in Settings → Devices cuts it off. It gets the secret from reverse pairing on a dev or local Home (`/auth/reverse/poll` answers `device` to the extension origin and sets no cookie) or from the Space gateway's `POST /_home/extension/connect` (the Hub's private-Space check stands for pairing; the gateway calls `POST /api/devices/extension`, owner bearer only); `POST /api/extension/disconnect` deletes its own device. The gateway (`deploy/hf-home/gateway/proxy.py`, `main.py`) adds the daemon credential only to Space-origin calls; extension calls (its Origin, or no Origin with the device header or `Sec-Fetch-Site: none` outside a navigation) go through without it and need the device header, except `GET /_home/status` (a reduced answer for discovery) and the connect route, and reach no other `/_home/` route. The desktop companion (`desktop/`) names itself with `X-Launchpad-Client: desktop/<version>` and never sends an Origin: its device (kind desktop) is accepted only without an Origin (never a page's or the extension's), and neither its secret nor the extension's works as a cookie (only a browser's does). It gets its secret from reverse pairing (`/auth/reverse/start` with `kind: "desktop"` and that header, approved in a signed-in window like a browser's; `/auth/reverse/poll` answers `device` as JSON only to that client, never a cookie, and a request of one kind is never collected by another) or from the gateway's `POST /_home/desktop/connect` (the gateway calls `POST /api/devices/desktop`, owner bearer only); the gateway recognises it by that header alone (`from_desktop`, checked before the extension's heuristic), passes its calls with its device header and without the daemon credential, Origin or CORS, and gives it only `GET /_home/status` and its connect route of `/_home/`. A device-header call (extension or desktop) never reaches device management, on the daemon (`auth::device_header_path`) and the gateway (`blocked`), except `DELETE /api/devices/self` (any device deletes its own; the extension's `/api/extension/disconnect` stays). On a Space the owner's Space-origin window lists and revokes devices (`GET /api/devices`, `DELETE /api/devices/<id>`); `/auth`, pairing and the other blocked routes stay closed. `GET /api/version` (`routes::API_VERSION`, `MIN_CLIENT`, `CAPABILITIES`, the commit and role) answers every signed-in client, so separately released clients test capabilities. Keep `EXTENSION_ORIGIN` in the gateway, `EXTENSION_ID` in `crates/server/src/auth.rs` and the manifest key in sync, and `CLIENT_HEADER` in both. The Space card carries `tags: [launchpad-home]` (`deploy.sh`, `home_update::card`) for the extension's discovery.
- `GET /api/events` is the bus of `/ws` as server-sent events (same `hello`, replay by `?boot=&since=` or `Last-Event-ID: <boot>:<bus>`, `resync`; a `: keepalive` comment every 15 s; no presence), for the extension, whose headers a browser WebSocket cannot carry; the gateway streams it unbuffered.
- There is no native shell for the UI: browser tabs (or the installed PWA) open links and other workspaces in new tabs; the daemon never opens windows or links and shows no desktop notifications. The optional desktop companion (`desktop/`, Linux) is a thin separate client like the extension (shortcut, status menu, its own notifications, browser handoff), never a window of the full UI. The Android app (`android/`, device kind `phone`) is one too: it follows the desktop companion's rules (`X-Launchpad-Client: android/<version>`, no Origin, its secret accepted only with that header, JSON answers, never a cookie), connects only with Sign in with Hugging Face through the Space gateway (`POST /_home/phone/connect`, no pairing link, QR code or pasted token), reaches only its own records under `/api/devices/self/` (push token, presence), reads the live bus over `/api/events?topics=`, renders folios in Home's own embed reader (`/folio-embed/`, writes through its native bridge), and hands everything else to the browser.
- Session lists and bus events carry `Session::light()` (no attachment bytes, prompt cut at 4,000 bytes); fetch `GET /api/sessions/{id}` for the full record. Sessions open tail-first.
