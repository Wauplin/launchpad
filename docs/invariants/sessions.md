# Harnesses and sessions

The design invariants every change in this area must keep. Read this page before changing the area, and update it in the same commit when a rule changes or a new one appears. [AGENTS.md](../../AGENTS.md) keeps only the cross-cutting rules; index of all areas: [README.md](README.md).

- `crates/core/src/harness/mod.rs` is the common contract and `crates/harness/src/lib.rs` the registration list; each adapter owns startup/resume, discovery, monitors, markers, terminal commands and title hooks. No harness identity branches in core, server or React (UI metadata: `GET /api/harnesses`). See `docs/harness-adapters.md`.
- Adapters start processes with `procs::child_command(&app.env, …)` and `spec.cwd`. `exec::is_lost` exits are Interrupted.
- A session's native files live in its own harness home (`contain::harness_home`; adapters find it with `trace::root`, `project_moved` takes the session). Adapters never read the machine's own harness settings or history (`~/.claude`, `~/.codex`) for sessions or defaults; only the owner-clicked memory import on a runner reads them.
- A live process may be released between turns only when its adapter asks (`LiveSession::idle_release`; Codex: a session's own app-server after 10 idle minutes) and nothing runs or waits (no open question, quota pause, capacity retry, turn or background command): the 1 s guard calls `Sessions::release` and the next message resumes the conversation. Codex runs one app-server per contained session, shut down when the session's process is dropped (release, Archive, move, an exit), and delivers its messages to the router through lossless queues, never a channel that drops on lag.
- Initial titles (`titles.rs`): one request at a time per session, retried after 1, 4 and 16 minutes, then the prompt title stays; a multi-line reply keeps its first line. Every cost a title request reports counts (session usage and spending ledger), also when it failed. Auto in a rename (`session.auto-title` on the session's runner, `titles::regenerate`; `bot.thread-auto-title` on Home, `bot_threads::auto_title`, which asks the thread's session and sets the thread's title) is the owner's on-demand request only, never automatic: it names the conversation as it is now and applies the title only while the title is still the one it started from (a rename made meanwhile wins); the window closes its editor at once (the agent's title editor, the chat header's inline editor) and shows a failure as a toast.
- Shared session states: Done means waiting for input; Running includes starting, working and background commands (including Codex background commands until real completion); never infer Done from a silent command. Stopped differs from Interrupted and Failed. Idle checks for publication, merge and root Stop include child turns and commands that outlive a turn.
- Status changes of a session go through `Sink::set_status`, one at a time per session (its status lock, held from the read through the Git and save-mark awaits to the side effects, never across a call to Home or a harness write) and decided by the pure `sessions::transition`, checked again against the record at the write (compare and set), so a turn end never overwrites a newer state and its save, notification and routines run once per accepted change. A message sent to a running turn that ended on its way makes the session Working again (`set_status_when`). A quota pause changes the status only at the turn's real end (the harness's final status becomes Quota paused), or when the guard finds the turn over; a turn the harness starts on its own while Quota paused keeps that status, but its end is saved like any (`paused_turns`); the owner's Stop of a pausing turn never notifies. A runner restart ends an interrupted turn like any turn end (heads, `unsaved` mark, notification once that turn is saved on Home, never for a session whose status changed or that Home moved on).
- Needs you = an open question, or Done/Failed/Interrupted and unseen. `Session::needs_you()` and `needsYou`/`isUnseen` (`web/src/lib/sessionStatus.ts`) are the only predicates. A session's list group (needs you, running, quota paused, sleeping, done, stopped, interrupted, failed, in terminal, archived) is decided only by `Session::group()`, sent as `group` on light records and `sessions` bus events; the web reads it through `sessionGroup` (same rule for full records and the demo), and both languages check `web/tests/session-groups/cases.json` (`cargo test shared_group_cases`, `pnpm test:sessions`). A session becomes seen only after a focused, visible, recently used window showed it for 1.5 s (notification suppression uses the same rule); a bot page counts as showing its current session.
- Today is the decision list: Home computes it once for every window (`today::compute`, the core's items plus `ext::Extensions::today` for the feature crates), serves it at `GET /api/today` (Home-owned; runners forward it) and announces changes with the `today`/`changed` bus event; session updates recompute only when the set of sessions that need you changed. Every attention count (sidebar, workspace menu, phone, window title, app badge, the Chats item and tab: `useChatsNeedCount`, its bot sessions' cards and channel asks) reads only this list; agents join it through `Session::needs_you()`. Each item names its main action from the action list. One card per session, except one per conversation of several bots (the most urgent); a bot session's card is titled "Bot · thread title" (`bot_threads::all`), recomputed on `bots` events. The Local PRs of an agent that needs you go inside its card (`Item::grouped`; a finished agent's main action is then the Local PR's), so they count once; other Local PRs are cards of their own. Bot channels add an item only where a bot asks the owner (`--ask-owner`) or mentions `@owner`, one per channel (`launchpad_channels::today`, kind `channel_ask`: the newest unanswered ask with the count, main action Reply = `channel.post` with `reply_to`), until the owner posts there or reads past it (`channel.read`, also ⋯ Mark read). An item whose place resolves to no workspace is not listed (repositories without a folder never show); only shared things show in every workspace (outdated runners, tool or preset proposals without a workspace, Outbox messages without a session). A Merge from a Today card needs the session Done and saved on Home (no `unsaved` mark), its runner present (its folder there, or removed and merged from Home) and a safe branch; the card stays until the merge completed. Every worktree Merge sends the head the window showed (`worktree.merge` input `head`) and is refused when the branch moved past it.
- `Sink::child` (subagents) never changes root usage, model, identity, status or previews.
- Permission modes (YOLO default, Ask for approval, Auto) use native mechanisms only; never implement Auto by accepting requests blindly. Typed replies cannot grant permissions. Only the owner grants permissions: an agent, whatever its Launchpad CLI access, never answers a permission request (`session.answer` of an `AskUser` with a `permission` question) and only makes a session's permission mode stricter (YOLO → Auto → Ask for approval, `PermissionMode::strictness`; `agent_auth::permission_guard`, on Home and on the session's runner), and the same for a bot's `bot.toml` and a scheduled launch's spec (`schedule.update`); a new launch, schedule or routine of an agent keeps the mode it names.
- Only the initial prompt gets `compose::append_initial_summary_instruction`; follow-ups stay verbatim, typed text first in `render_prompt`. The one addition: a message to a bot session whose BOT.md changed since it started or last received it carries the new BOT.md after the typed text (`bots::changed_block`, added by Home in `runners::deliver` for every `input` it sends to a runner, also the requests a starting Burst job queued; the session records the version it received in `BotLaunch.version` once the message is delivered); the chat shows it as one line. Trace context is referenced (`launchpad trace <id> --through <seq>`), never inlined; missing traces fail visibly.
- What a session sees at start (its instructions file and first prompt) is built in labelled parts by `start::instruction_parts` (knowledge base and INDEX.md, bot memory, CLI reference, attribution, memory cut line) and `Sessions::resolve` (`start::slices`). The real start (`contain::apply`) and "What it sees at start" (`preview` in `crates/api/src/bots.rs`, Home's `GET /api/bots/{id}/start-preview` and `POST /api/launch/start-preview`, action `launch.start-preview`) call the same functions; never copy their text.
- Schedules and routines (code: crons) claim before launching (advance `next_run_at` or the trigger's watermark, write the history entry first) and never catch up: runs over one hour late or with unmet conditions (all must hold; quota needs a fresh reading; dependencies use `dependency_done`) are skipped, with the true reason (`crons::late_reason`: Home not running, or the quota hold of `quota::hold_reason`); a run skipped after a quota hold is `missed` and counts as a failure. Claimed but not started at shutdown becomes Failed, never retried. A bot routine's definition is its file `routines/<name>.toml` in the bot's store (see [Bots](bots.md)); a changed schedule recomputes `next_run_at` from now, never from the old due time.
- Routine triggers: schedule, another agent's turn ending Done (an agent of the routine's workspace, even when the trigger names a folder; once its work is on Home: a turn that ended with the `unsaved` mark triggers when the mark clears, at most an hour later; `crons::turn_saved`; turns of bot threads only with the trigger's `include_bots`, off by default), Launchpad failures (`failures.rs`: Home's 30-second check; one run per check, claimed by advancing `failure_seen`, waiting while the bot is at its thread cap, skipped after one hour), new messages in a bot channel or DM (`channel_trigger.rs`, bot routines only, the bot a member of a channel of its workspace, checked when the file is saved; the file stores the channel ID, the editor, `create_for_bot` and routine cards also take `#name` or `@bot` and store its ID; same 30-second check, one run per check for the new messages after `channel_seen` (a message ID, started at the newest message when the trigger is created or changed), claimed by advancing it, never for the bot's own messages, with `mentions_only` only for messages that mention the bot, never for messages the channel already delivered to the bot (a message delivery sent, queued or combined; a check reads only messages at least 5 s old, `SETTLE_MS`, since a post writes its delivery rows after the message), so one message never wakes a bot twice; a check with no message left starts no run and only advances the watermark; waits while the bot is at its thread cap or its quota is unconfirmed, skipped after one hour; the run's message lists the message IDs and the `launchpad channel read <name> --since <id>` command, never the text; its hop is the highest hop of those messages plus one, so a ping-pong of channel routines meets the loop guard; read straight from state.db, since automation never depends on the channels crate); a routine's own runs never trigger routines, and a failure routine never runs for its own runs or its bot's sessions. Each run of a bot routine is a message (`crons::bot_message`) to a new thread of the bot (key `routine:<file>`), skipped with the reason while the bot is at its thread cap (`bot_threads::at_cap`); other routines launch their spec. Pausing a bot pauses its routines and hooks, never the owner's messages. A scheduled bot message (`bot.message` with `in` or `at`, `hooks::schedule`) is a `queued_message` entry under `bot:<id>:scheduled` with its `Due` (time and the `bot_threads::To` routed when it was scheduled, sender stamped then with its hop count; at most 50 waiting per sender, a year ahead): once due, the queue resolves its thread and moves it to that thread's queue in one transaction (`hooks::release`), where it is sent like any queued message; while the bot is paused it waits, before and after it moves (`Queued.hold_while_paused`), and a deleted bot drops it; `launchpad bot scheduled` (`GET /api/context/scheduled-messages`, the caller's bot's or session's) lists them and `bot.cancel-queued` cancels one. A final `no_update` message (`routines::is_no_update`) never notifies and is marked seen; a bot routine's quiet run also archives its thread while that thread still holds only that run's session, Done and without an open question. Loop limits (`crons::limit_reason`, checked before the claim, recorded as a skipped run with the reason): a run whose message would pass the loop guard ("loop guard: N hops", see [Bots](bots.md)), and an event-triggered routine (session done, failure, channel) that already started `crons::EVENT_RUNS_PER_HOUR` (6) runs in the last hour ("rate limit: …"); schedules follow their cron.
- Routine auto archive (`auto_archive`, off by default and for older records and files; `RoutineFile`, `CronPatch`, `BotRoutine`, `routine.create`, cron and routine cards): `crons::auto_archive` archives a run's session only after the run ended Done (Report or No update) and while the session keeps that Done state (`RoutineRun.done_since` = its `status_since`; no question, sleep, quota pause, capacity retry or `unsaved` mark; within 24 hours) and `away::unfinished_work` finds nothing waiting (a merge waiting, in conflict or failed, commits not on Home, leftovers, commits ahead of the base branch outside a Local PR or pull request). Failed, interrupted, stopped, sleeping and waiting sessions stay. A bot routine archives the run's own thread (key `routine:<file>`, holding only that session, never Main) with its run group (`run_groups`, see [Bots](bots.md)): only once the run's session also passes `task_archive::waits`, has been Done for `task_archive::SETTLE_MS`, nothing of the run waits in `queued_message` (by thread, or by `from.run`) and every open thread of the group passes `run_groups::member_blocks` and `task_archive::waits`; the group's threads outside the run's conversation are archived first, each claimed in `task_archive`, then the run's thread with its conversation. Threads of an archived run's group that settle later go on their own (claimed the same way, so Bring back is never undone). A turn of the run's thread that answered a message of its group (`MessageFrom.run` = its root) moves `done_since` on (`crons::group_answer_ended`); any other message keeps the run. Other routines only a session whose `LaunchSpec.routine` names them. Each run is claimed (`RoutineRun.archived`) before its archive and never retried.
- Bots' task sessions archive themselves (`task_archive.rs`, Home only): a session a bot started on its own (`task_archive::bot_origin`: `LaunchSpec.from` of kind Bot and not `accepted`, or a run of a routine whose `CronAgent.created_by` is a bot, stamped by Home at creation, never from a body; never a bot's thread, the owner's launch or click, or a routine with its own `auto_archive`) is archived once `settled` (clean saved Done for 1 minute to 7 days) and `waits` finds nothing (the owner took part, a scheduled follow-up, its waiting cards, Suggestions and Outbox messages through `ext::Extensions::waiting_on_owner`, Local PRs not merged, discarded or published at Home's commit, `away::unfinished_work`); every check that fails keeps it. Claimed once per session (`task_archive` table) before `runners::archive_if_done`, which the runner checks under the action lock (`Sessions::close_if_done`, close route `if_done_since`, 409 drops the claim); an uncertain archive is never retried and Bring back is never undone. It never publishes, posts or pushes anything.
- Archive automation threads (`bulk_archive.rs`, Home only) is the owner's bulk archive of one workspace, preview first (`GET /api/context/archive-done`, changes nothing), then `session.archive-done` with the previewed session IDs, which recomputes eligibility and archives only those still eligible. Eligibility lives in `bulk_archive` alone: `origin` (a bot thread whose key is `routine:`, `channel:`, `agent:` or `hook:`, or a `conversation:` thread judged by its conversation's first thread; a non-bot session of a routine run or of a non-accepted Bot, Session, Hook or Channel sender; never the owner's threads or launches), `blocker` (clean Done settled for a minute, older than the filter; never asking, sleeping, working, failed, stopped, quota paused, retrying or unsaved) and `task_archive::waits`. A conversation is archived whole only when every open thread of it is eligible. Each session goes through `runners::archive_if_done` at the Done state the checks saw, then `bot_threads::archive` marks its thread rows; an uncertain archive is reported, never retried. Admin sessions run it within their workspace and it lands in the activity list.
- Sleeping (`launchpad sleep --in|--until|--agents [--state]|--quota [--timeout] [--note]`, `POST /api/sleep`, an own write of the session's CLI token at every access level, Home only; `schedules::sleep`): an agent asks to be woken later instead of waiting or polling in its shell. Its conditions are a scheduled launch's (`LaunchDelay`, all must hold; `agents` takes optional `states`, `AgentState::of`, none = `dependency_done`), only agents of its own workspace (`scope::of_session`, checked in `schedules::sleep` since the route names no record), never itself, never an agent that already sleeps until it changes state (`sleep_cycle`, unless the edge waits for `sleeping` or a wake-up has a timeout); `--timeout` is the record's `deadline` (`ready`: conditions hold or deadline passed; the wake-up then says so, `wake_early`, also for the owner's Wake now); conditions that already hold are accepted (`already_met`) and wake it at its turn's end. Home records a scheduled follow-up to the same session (sender kind `Wake`: no header, the hop count of the turn that slept; one per session: a new sleep replaces an earlier wake-up and is refused while the owner's follow-up waits) and sets `Session.sleep` (until or none, `waits` in words, deadline, note, schedule ID). `sleep` is Home's: `apply_replica` keeps it over runners' records. `Session::sleeping()` (Done, no open question, `sleep` set; `isSleeping` in `web/src/lib/sessionStatus.ts`) is not Needs you, not `dependency_done`, settles no routine run and triggers no routine (`crons::turn_ended`, `turn_saved`), and gets no Done notification. The wake-up and `Session.sleep` are stored in one transaction (`Sessions::set_sleep_with`, replacing an earlier queued wake-up in it). The usual scheduler sends the wake-up (quota hold, claim once) through `run_follow_up`: its text is fixed at the first try (`sent_text`) and each attempt has a stable idempotency key (`delivery_key`), so a retry after a lost answer, a Home crash (`recover` requeues keyed claims) or a restore is answered by the runner's stored result; a busy session starts a new attempt, failures before delivery retry for an hour (`RETRY_FOR`), and an uncertain answer is recorded, never repeated; sending, failing or cancelling it clears `sleep` (`schedules::wake`); a turn that starts while asleep (a message woke it) clears `sleep` on Home and cancels the wake-up (`ext::Extensions::woken`); an archived session's wake-up is dropped. The Agents list groups Sleeping sessions; the session page shows Wake now (`schedule.start`) and Cancel wake-up (`schedule.cancel`).
- Attachments upload once (`upload:<mime>;<sha256>`). Session records, events and tunnel messages carry only these references, never bytes: Home turns data URLs into references before a launch or message goes to a runner or Burst (`attachments::to_refs`), a runner fetches the bytes it lacks from Home (`attachments::fetch_missing`, runner call `upload`: only for a session Home placed on that runner, and only references Home sent it or that Home's record of it names, `attachments::read_for_runner`), and harnesses get data URLs only at delivery (`attachments::for_harness`); a runner replicates its records without inline bytes (`Session::without_bytes`). Non-image files go to `<data_dir>/attachments/<session-id>/`, never into the checkout, and travel in the session's handoffs (restored on the adopting runner; files Home already has for the session go by hash only).
- Capacity retries: terminal capacity/overload failures only, persisted five-minute deadline, at most five per session, cancelled by Resume, input, Stop or Archive.
- The owner's bot messages are stored on Home before any work (`launchpad_channels::sends`, table `bot_send`, keyed by the window's Idempotency-Key): `bot.message` with `accept` answers the receipt at once (thread resolved, a new thread created), without waits for the session; one task per thread sends them in order through `bots::message_with` (waiting while its session starts or a harness without messages during a turn works), claiming each (`sending`) before its send. A claim left by a Home stop becomes `sent` when a session has the message's ID, else `uncertain`, never resent on its own; Retry (`bot.retry-send`) reuses the ID. A launch's first `user_message` has the session's ID as `client_id` (also when its start fails, before the failure), and an input keeps its key as `client_id`, so the chat (`pendingRows`) replaces the pending bubble by the session's message: never two. The owner's messages bypass `max_threads`; agents' messages keep the direct path (automatic, cap and quota rules unchanged); callers without `accept` (the extension) wait for the session.
- Launch, session input and bot messages (`POST /api/bots/{id}/message`) use `Idempotency-Key` headers and durable `browser_operation` claims; keep authentication before retry middleware. A bot message's key becomes its message or new session id, and one lock per bot (`bots::message_with`) covers the choice of session and a new session's launch, so concurrent messages never start two sessions of one bot. Completed claims go after 7 days (`operations::prune`); a claim without a result (in flight or uncertain) is never pruned. `crates/server/src/retention.rs` prunes the growing `state.db` tables once a day, on Home and runners: those claims, raw harness lines (`session_raw`: capped per session in lines and bytes, each line cut, deleted at Archive and after 14 days) and proxy access entries after 30 days.
- Notifications go only to the Android app (`launchpad_channels::push`; the daemon shows no desktop notifications): content-free FCM wake-ups, after which the phone reads its list from Home. They cover questions, failures and interruptions, channel asks, bot answers, cards, finished agents, routine reports, and automatic quota/cost stops and resumptions, never with code or messages in the push. The PWA has no Web Push.
