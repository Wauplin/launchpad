# Bots

The design invariants every change in this area must keep. Read this page before changing the area, and update it in the same commit when a rule changes or a new one appears. [AGENTS.md](../../AGENTS.md) keeps only the cross-cutting rules; index of all areas: [README.md](README.md).

- A bot is files on Home (`BOT.md`, `bot.toml`, `routines/<name>.toml`, `memory/`, store `bot-<id>`) plus several threads, its parallel conversations: a thread is one session, the one whose `LaunchSpec.bot` names the bot and the thread (`BotLaunch.thread`; empty in sessions from before threads = the legacy thread `main`; older threads may hold several sessions and only the newest counts, `bot_threads::session`), with a row in `bot_thread` on Home (bot, id, routing key, title, created, archived; `bot_threads.rs`). `bot.toml` is the only source of its settings (profile, model, folder, permission mode, proposal mode, Launchpad CLI access, `max_threads`, `starters`: the chips over its message box, seeded for Ask Launchpad as data, never per bot identity); no profile means the first subscription profile (`bots::profile_of`). Only the owner and sessions with admin Launchpad CLI access write `BOT.md`, `bot.toml` and `routines/`, and an agent never raises a bot's `launchpad` access or loosens its `permission_mode` (`bots::agent_refusal`, for `bot.update` and a Restore of bot.toml; a broken bot.toml counts as the strictest; an agent's `bot.create` gets at most propose access); other sessions propose a `bot-files` card (`ProposalBody::BotFiles`: BOT.md and routine files, one diff per file, each with its hash before; accepting writes them all at once and fails when one changed since; `routine` and `bot-instructions` proposals become such a card); `memory/` holds the bot's own notes (`bot_memory.rs`), written only by Home through `kb::apply_to` (like the knowledge base) and by the bot's own sessions with `launchpad bot memory` at every access level, like the knowledge base (`/api/bot-memory`, an own write; Home takes the bot from its own session record). Runners mirror the store read-only into the bot's sessions (`$LAUNCHPAD_BOT`) and remove a copy an hour after the bot's last open session there. Bot history, diff and Restore cover every file; deleting a bot deletes its memory. Its folder is optional and only a Git folder: without one, each session runs in a temporary folder and adds worktrees with `launchpad work add-project`. Bots never run in plain folders: setting one is refused (form, `bot.update`, `bot.create`, cards); a `bot.toml` that already names one keeps it, but its sessions run in a temporary folder (`bots::effective_folder`) and its settings (Access) say so (`Bot.folder_unused`).
- A bot's routines are defined by its files `routines/<name>.toml` (`crons::RoutineFile`: title, trigger, schedule, time zone, conditions, instructions, paused); its `cron` records keep only what files do not (runs, next run, failure and channel watermarks, claims), keyed by bot and file (`CronAgent.file`). Saving a bot routine (create, edit, pause, delete) writes its file through `bots::write_files`; every write of a bot's files (`bots::write`: owner saves, Edit as file, Restore, accepted cards) calls `ext::Extensions::bot_files_changed`, which runs `crons::sync_bot_files`: a new file creates its record, a changed one updates it (a new schedule, time zone, trigger or pause recomputes the next run from now, a new trigger starts its failure and channel watermarks from now, so no run covers earlier activity), a removed one deletes its record and its runs. A file with an error keeps the record's last good definition and shows `file_error` (a new broken file gets a paused record without instructions, which Run now refuses); the API refuses saving one, so errors come only from Restore or a changed bot (a quota condition its new harness cannot read). An admin `bot.update {files}` gets its Undo in the activity list from `Bot.routines` (each file before, null for a new one). Home wrote the files of older bot routines once at start (`crons::files_from_records`, claimed in `seeded`). Routines of other agents (with a launch spec) stay records only.
- Routing (`bot_threads::route`, pure; `resolve` creates the row under one lock per bot): there is no default thread. The owner's messages (bot page, Ask panel) go to the thread they name (`bot.message` `thread`), else to a new one (also `new_thread`: New thread, the extension's New conversation, every top-bar Ask, also on the bot's page), and `item_thread` (the extension's page buttons and This item) to the open thread keyed `github:<repo lowercase>#<n>` of the one GitHub item named (several items: a new thread); a channel's or DM's deliveries and digests go to `channel:<id>`, an incoming hook's to `hook:<id>`, another agent's messages to `agent:<sender session>` (from another bot's thread: this bot's thread of the sender's conversation, below), each routine run to a new thread (`routine:<file>`); a report's Reply goes to the reporting session's thread. Keyed sources take only open threads, so after an Archive they start a new one. A thread whose session is archived lists as archived (`bot_threads::list`). Threads are renamed (`bot.thread-rename`) and archived (`bot.thread-archive`, which archives its session and brings it back with the thread; refused while it works). Cap (`bot_threads::at_cap`, checked under the bot's message lock with the thread choice and the launch): at most `max_threads` (default 16, 1–64) threads work at once; a thread that already works takes no new slot; the owner's messages bypass it; automatic messages (hooks, channels, agents) wait in `queued_message` under `bot:<id>:<thread>` (checked every 3 s; an agent's `bot.message` answers `{"queued": true, "thread", "status"}`), routine runs are skipped with the reason; quota holds and the loop guard still apply. Pause, Delete and a workspace delete cover every thread (a delete is refused while one works).
- Conversations of several bots (`bot_threads`: `bot_thread.conversation`, `<main bot>:<first thread>`, none = its own; `launchpad_channels::conversation`): an agent's `bot.message` from a bot's thread to another bot goes to that bot's thread of the sender's conversation (`bot_threads::joins`, `To::Conversation`, created with key `conversation:<id>`); the owner's `bot.message` with `conversation` goes to that bot's thread of it (a bot that is not part of it joins). Each bot keeps its own session and sees only what is addressed to it. When a turn that answered another bot's request of the conversation ends Done (not sleeping, no question), its final answer goes to the asking bot's thread of the conversation (`conversation::owed`: the turn's message is the request, or an answer or wake-up that names it with no owner message after it; correlation is explicit: `senders::agent` stamps a bot's message with its own `MessageFrom.request` ID and `serves`, the request its turn works on (`senders::serving`), an answer carries `reply_to`, `resumes` (the request's `serves`) and `turn`, and a wake-up its `resumes`; messages without IDs keep the older rule), claimed once per message in `conversation_reply` before it is sent, never retried, queued like an agent's message (`hooks::deliver_reply`), with `MessageFrom.reply` and one hop after the request (past `MAX_HOPS` it is recorded and not sent); a reply is never answered. `launchpad conversation read` (`GET /api/context/conversation`, the CLI token's own session) lists the timeline; nothing else is pushed. A follow-up thread keeps its conversation; `bot.thread-archive` archives (or brings back) every thread of it. Today keeps one card per conversation (`today::one_per_conversation`), the Chats list one row (`buildChats`), and the bot page merges the threads (`mergeConversation`, leading @-mentions route the owner's message: `routeMentions`); an answer that names a loaded request shows once, folded under it (`linkReplies`, `web/src/lib/replyGroups.ts`: one level, never inferred from adjacency; others stay at their time), and channel pages fold bots' `reply_to` replies the same way. The extension's panel keeps its own thread.
- Run groups (`bot_threads::note_run`, `run_threads`, column `bot_thread.run`: NULL undecided, '' none, else the root `<bot>:<thread>` of a routine run's own thread, which names itself): Home stamps `MessageFrom.run` from the sender session's thread only (`senders::agent` for `bot.message` and scheduled messages, `delivery::send` from the channel message's author session for channel posts and DMs, `conversation::answer` for answers; a combined channel delivery keeps it only when all its messages share it, `hooks::join`), never from a body. `bots::message_with` applies `next_run` (pure, tested) to the thread it resolved, before any `follow_up` (which copies it): a routine run's thread is its own root for good; a thread takes the run of the message that starts it; any later message of another run, of the owner or without one detaches it for good. Today drops the Finished card of a group's handoff and keeps one card per group (`today::core_items`); Chats folds handoff conversations under the run's row (`foldRuns` in `web/src/lib/chatList.ts`, tested), where only their questions, failures, work, sleeps and quota pauses count. `bot.thread-archive` of a run's own thread covers its group; the routine's auto archive of the group is in [Harnesses and sessions](sessions.md). `sessions show` (`/api/context/sessions/{id}`) adds `run`.
- A thread's session starts on its first message. When it cannot go on (`bots::rotation`: an archived session, or a change of profile, folder, model, effort or permission mode against the values it started with; the bot's model and effort fall back to the profile's; a permission mode the owner set on the session in Agents keeps the thread, `BotLaunch.permission_mode`), the next message closes it and continues in a new thread with the same key and title (`bot_threads::follow_up`, which archives the old thread); the returned session names the new thread and the windows follow it. The reason is recorded in `BotLaunch.reason` and shown with the continued thread's title in the chat's divider. The new session references the previous trace (`BotLaunch.previous`, `launchpad trace`), never inlines it. There is no Start a new session: New thread replaces it. Harness compaction handles a full context. A BOT.md edit starts no session: the next message carries it (see [Harnesses and sessions](sessions.md)), and the message box says "Instructions updated · applies to your next message" while the current session runs an older version (`Bot.instructions_version`).
- Messages that are not the owner's (`senders.rs`): Home stamps the sender of every message from Home's own records, never from a request body (`senders::set_from` replaces any `context.from` a body names; a runner's input route drops it unless Home relayed the request). An agent's message (`bot.message`, `session.message`: a runner forwards an agent's input to Home with its session, `FromRunner::Req.session`, which Home accepts only for a session it placed on that runner, `launchpad_http::AgentSession`), a message card (its author's bot or session; "accepted by you" only for the owner's click), a routine run and an incoming hook (`hooks::hops`, see [Connections and the Outbox](connections.md)) carry `MessageFrom` (`context.from`, `LaunchSpec.from` for a new bot session, recorded on the `user_message` event). An agent messages only bots and sessions of its own workspace (directly or through a card), and an auto-mode card never messages a session with admin access without the owner's click (see [Ask Launchpad and proposals](proposals.md)). A bot's or agent's message arrives under a fixed header naming it as not the owner's, with its text fenced (`senders::wrap`, applied once at delivery by `runners::deliver`, or in the launch); owner messages (the UI, the phone app, report replies, the owner's private note `note.write`) stay unchanged. The chat and the trace show such a message on the left under its sender (`from` rows, `fromOther` in `web/src/lib/senders.ts`; a routine run shows as its routine), never as the owner's bubble. Each automatic message counts its hops (`MessageFrom.hops`: the hop of the message its sender's turn answered, from Home's last `user_message` event of that session, plus one; owner messages and clicks reset it to 0); past `senders::MAX_HOPS` (3) it is not delivered (`senders::guard`: "loop guard: N hops"), so the agent's call, the card (Failed) or the routine run (skipped) shows why. An agent's scheduled follow-up carries its sender too (`ScheduledLaunch.spec.from`, header added when Home delivers it). Launches by an agent (`session.launch`, `schedule.create`, launch and schedule cards started automatically or by an agent) name it in `LaunchSpec.from` with its hop count but get no header (the new agent's task is its own); Home sets that field on every launch or schedule request (None for the owner's), never from the body.
- Chats (`web/src/features/chats/`, pure model `web/src/lib/chatList.ts`, tested): one layout route (`ChatsFrame`, id `chats`) holds `/chats`, `/bots/$id`, `/bots/$id/settings`, `/channels/$id` and `/channels/$id/settings`, so on the laptop the resizable list (`useColumn("chats-list")`) stays mounted beside the main frame, like Agents; the phone shows one page at a time (`/chats` is the list, `?view=start` the tiles, `?new=true|channel` the New bot and New channel forms; `/bots` redirects to `/chats`). With nothing open, the main frame is the landing grid: bots, then channels and DMs, alphabetical (`byName`); a bot's tile starts a new chat (`?thread=new`), a channel's opens it, an unread channel has a bold border, and each tile's gear opens its settings. The list (`ChatList`): search (titles, last answers, names, and messages through `/api/sessions/search`) and a multi-select Bots filter (a chat shows only when every chosen bot takes part: a conversation's participants, a channel's members; `filterChats`), then sections Needs you, Unread (unseen turns and unread channels), Running, Quota paused, Sleeping, Failed, Done, Channels, Archived (collapsed per device in `stores/chats.ts`, Archived folded by default). One row per conversation (`BotThread.conversation`, which a follow-up thread keeps), from one request (`GET /api/chat-threads`, `bot_threads::for_chats`: open threads, archived threads of open conversations, and a page of archived conversations, Show more adds 50; refreshed by `bots`/`threads` with the changed bot's own lists, `refreshThreads`), computed once per input change for the window (`sharedChats`); channel messages search on Home (`GET /api/chat-search`); rows styled like agent rows: bot marks for conversations, a grey #/↔ mark and a Channel/DM tag for channels, a repeat icon for routine threads, the title from `chatTitle` (the automatic name of the chat's first session, else its current one, routine and source chats included; the thread's title until one is named or once the chat was renamed, `BotThread.renamed`, by hand or with Auto). Row ⋯: Pin/Unpin, Rename, Archive/Unarchive (threads only; channels are archived from their settings, never from the list), Open in Agents. Pins (`chat.pin`, `POST /api/chat-pins`, table `chat_pin`, owner only, Home-owned, bus `chats`/`pins`; targets `conversation:<id>` or `channel:<id>` of the pin's workspace, checked on Home; deleting the conversation's main bot, the channel or the workspace deletes its pins) are the only chats the laptop sidebar lists (open ones, alphabetical; the phone lists them first, in Pinned), under its Chats item (below Agents); there is no Bots group or Active threads. Every list of bots or channels (sidebar pins, the Channels and Pinned sections, tiles, pickers, filters, members) is alphabetical by displayed name, ignoring case (`byName`/`compareNames` in `lib/channelRows.ts`; `useBots` and `useChannels` sort in their `select`, members too); a list may group first (participants first, channels before DMs), and the state sections of Chats stay newest first. There is no pin of agent sessions. No Topics in Chats.
- The bot page is a chat over one thread, built from session events by `chatRows` (`web/src/features/chat/`) with no Ask-only code, centered up to `max-w-text` with no side panel. Without `?thread=` it opens the thread the owner looked at last (`landingThread` in `web/src/lib/bots.ts`: this device's last one in browser storage, else the thread whose session has the newest `seen_at`, else the most recent, else a new chat). Its header shows the chat's title (`chatTitle`; "New chat" before the first message), its participants in the order they first appeared (`participantOrder`: each bot at its first thread of the conversation, each name opening its settings) and one status line in words (`statusOf`: the conversation's states most urgent first, working with its step and time, waiting for you, idle with the next routine run), then Open in Agents (secondary), Archive (primary, one click, no confirmation) and × (closes the chat to the Chats landing, archiving nothing); the title has a pen (edits it in place with Save, Auto and Cancel, `ChatTitle.tsx`; the list's Rename opens the chat and asks its header for the editor, `useRenameRequest`) and a star (pin or unpin); no About, no ⋯, no settings in the header. `?thread=` (a thread ID, a routing key such as `channel:<id>`, or `new`) is the only source of the selected thread; the Chats list is the navigation. Archive (`ArchiveThreadButton` and the list's ⋯, both `useArchiveThread` in `BotThreads.tsx`, `bot.thread-archive`, disabled while the thread works) of the chat shown goes to the Chats landing (the phone back to the list), never to another chat (`useShownThread` names the shown thread); on the phone the bar shows the title over its bots and status, with the star, an archive icon, a gear (the bot's settings) and ⋯ (Rename, whose editor opens under the bar, and Open in Agents); the Ask panel has + in its header and keeps its conversation bar (`BotChat conversationBar`). A bot's settings (`BotSettingsPage`, `/bots/$id/settings`, a spacious page of the Chats frame; older `?panel=` links redirect there) hold the bot's whole definition, each fact once: BOT.md, Triggers (routines with their last runs and Open its last chat, incoming hooks that message the bot with Open its chat, one Pause all for every trigger, shown even without routines, New trigger), Profile and model (`BotModelChoice`), Access (one sentence; Edit opens the compact form with Chats at once; the plain-folder note; What it sees at start), Memory (loaded at start), Versions, Edit as file (bot.toml and routine files), New chat and Delete; the message box keeps its unsent text in `keptDraft` per bot and thread. Proposals show in the chat and Today, never in a tab of the bot page. The chat shows messages, not traces: per turn the message, the bot's last answer and one quiet steps line ("12 steps · 3 min"; a tap lists the step titles, never a trace link) with a receipt per change of the turn (knowledge base, the bot's own files, direct admin changes; each links to its record, the full line with the values before shows when the steps are open). A proposal is one compact line (`ProposalLine`: icon, title, its main button, ⋯ with Details, Dismiss and Edit; a second line in plain words, `proposalPurpose`); Details shows the full card in place, and a handled card is a one-line receipt (`proposalReceipt`). Today and the Proposals list keep the full card. A ready click of the turn (Outbox message, Suggestion, Local PR) is the same kind of line with Review, which shows its full card in place (a Local PR opens its page). One message box: an open question shows its options as chips, and typed text answers it ("Answering: …" over the box; Cancel, only for a harness that takes messages while it works, makes the next message close the question as skipped through `session.answer` before it is sent, so the harness never holds the message behind it); a question report's Reply aims the box at it (`proposal.reply`). Approval requests keep Allow and Deny and disable the box: typed text never grants a permission. While a turn runs, the header says what it works on and the chat's working row shows only the spinner, View running agent (the selected thread's session in Agents) and Stop.
- Bot publishing (every bot, no setting; an older `publish_drafts` key of `bot.toml` is ignored): the only GitHub write an agent starts itself. `launchpad pr publish` (`POST /api/predrafts/{id}/publish`, propose access) is checked on Home by `predrafts::agent_publish_refusal`: a bot's thread, a Local PR of one of that bot's sessions, `draft: true` without fork; who asked is not checked (when to publish is the bot's call, from its BOT.md), then `publish` checks the reviewed head like the owner's Publish. Never Publish all, ready for review, fork or merge.
- Seeded bots (Ask Launchpad, the Librarian) are normal bots: Home creates each once per workspace, existing or new (`ask_bot::seed`, `workspace::create`), records it in the `seeded` table and never recreates it; their BOT.md, starters and routine files are data, and no code branches on them except the page that links to one (the top-bar Ask; the Knowledge page finds the Librarian by its slug `librarian`, so an owner's own bot of that name counts as it, and its hints name the gardener once no Librarian is left). The New bot form offers them as templates (`GET /api/bots/templates`).
- Bot sessions are normal sessions (counted once, in Today); the sidebar lists no bot, only the Chats item and the pinned chats; the Agents session bar links to the session's thread. A rename gives a new slug (unique in the workspace). Notes once kept in the knowledge base's `bots/<slug>/` moved once into `memory/` at a Home start (`bot_memory::move_from_kb`, claimed per bot in `seeded`; a new bot claims it at creation, so it never takes a deleted bot's folder); the Knowledge page lists each bot's memory read-only, linking to the bot's settings. Creating a bot (form or proposal) starts nothing; bot proposals never auto-start.
