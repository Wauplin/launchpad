# Connections and the Outbox

The design invariants every change in this area must keep. Read this page before changing the area, and update it in the same commit when a rule changes or a new one appears. [AGENTS.md](../../AGENTS.md) keeps only the cross-cutting rules; index of all areas: [README.md](README.md).

- Connections (Settings → Connections: outgoing webhooks and incoming hooks) live on Home (`crates/channels`: `connections.rs`, `hooks.rs`; table `connection`); runners forward `/api/connections`, `/api/outbox` and `/api/suggestions`. "Channel" means bot channels only. Webhook URLs and the phone notifications' Firebase key (`channel-push-fcm`) are `channel-…` vault entries (the stored name stays): never listed, lent or returned by an API. Connections are never admin actions (the `push.*` actions are the owner's).
- Messages to other people (webhooks, GitHub suggestions) wait in the Outbox for an owner click (shown in Today → Send and Today → GitHub; "Outbox" stays the concept and code name, there is no Outbox page); a send is claimed (`sending`) first, never retried, and `uncertain` if incomplete. Automated checks never send real Outbox messages or real FCM wake-ups.
- Phone notifications (`push.rs`, Home only) go only to the Android app, as FCM data messages that hold `{kind, ws, n}` and never a title, text, repository or code; the phone reads its list from Home (`GET /api/phone/notifications`: Today's waiting items that concern a phone and the automatic quota stops and resumptions of the last 12 hours). A wake-up goes out only when that list gains or loses an item, high priority only for an item that needs the owner; an item that appears while a window or the phone shows its session never notifies. The sender is inert without the vault key and a registered phone token; a revoked device loses its token; FCM calls follow the exit routes. Actions from a notification are answers, replies and Seen, never Merge or Publish.
- Incoming hooks (`POST /hooks/<id>`) need `X-Launchpad-Hook-Secret` (SHA-256 stored, constant-time compare), one message per 10 seconds, an HF token on a private Space; the body is a fenced (`senders::fence`), size-limited block marked as outside data. A hook message carries its hop count (`MessageFrom` of kind `hook`, `hooks::hops`): `X-Launchpad-Hops` gives it (at least 1), 1 without the header; past `senders::MAX_HOPS` the hook answers 409 "loop guard: N hops" and delivers nothing. The runner proxy does not see these requests (Home's host is a plain tunnel), so agents send the header themselves with `launchpad hops` (`GET /api/context/hops`: `senders::hops_of` of the CLI token's session plus one), as `cli_reference` and SKILL.md tell them. Each hook has its own thread of the bot (`hook:<id>`). Hook messages to a busy thread wait in `queued_message` (key `bot:<id>:<thread>`), a hook message also while the bot's quota is not confirmed or it is at its thread cap ("waiting for a free slot"); its chat lists them (`GET /api/bots/{id}/queued`, bus `bots`/`queued`) with Cancel (`bot.cancel-queued`).
