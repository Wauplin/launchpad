# Home and runners

Launchpad runs as one **Home** and one or more places where agents run:

- **Home** (`launchpad daemon`) keeps every record, credential, folder and branch, and serves the app. It runs no agents and no terminals: terminals opened from its window run on runners, relayed through their link. Run it in a private Hugging Face Space ([deploy/hf-home](../deploy/hf-home/README.md)) or on your own Linux machine (`packaging/install.sh`).
- **Runners** (`launchpad daemon --role runner`) run agents, on Linux only: your machines, a [Local VM](#local-vm), or [Burst](#burst) jobs. A runner keeps its own folders (`~/.local/share/launchpad-runner`, `~/.config/launchpad-runner`) and port (7320), so it can sit next to a Home on the same machine. It holds no records of its own: it keeps copies and sends everything to Home.

There is no single-process mode: a machine that runs agents always runs a runner, paired with a Home.

## Pair a runner

On a Home in a Space, open **Settings → Home and runners**: the Runners card lists the runners and requests waiting for approval, and **Add a runner** shows the steps and the install command (one line, with Copy). Run `hf auth login` on a Linux x86_64 machine (or set `HF_TOKEN`), then run the command there: without a Hugging Face sign-in, it says so and stops. It checks the machine, installs Home's own build next to any other Launchpad, starts the runner as a user service that keeps running after you log out, then asks for approval. Agents use the machine's own tools and cannot use `sudo`, so the command also lists the common tools this machine lacks (compilers, `jq`, ripgrep, Rust, pnpm, Chromium…) with the `apt install` line that adds them; it installs none itself. On a Mac or an ARM machine, use Burst. Run it again to update the runner. See [Add a runner](../deploy/hf-home/README.md#add-a-runner).

On a self-hosted Home, pair by hand:

1. Install Launchpad at Home's commit on the machine and start the runner daemon: `launchpad daemon --role runner`.
2. Run `launchpad connect <Home address>` there. It prints a code such as `34Z-K9Z` and waits. For a Home in a private Hugging Face Space, the runner sends your HF token (`HF_TOKEN` or the `hf auth login` token) to pass the Space's sign-in.
3. On Home, open **Settings → Home and runners**, check that the code matches and click **Approve** (**Refuse** is in **⋯**). Requests expire after ten minutes.

Runners run only on Linux. `launchpad daemon --role runner` and `launchpad connect` refuse other systems, and Home refuses to pair, approve or connect a runner that reports another system: Settings → Home and runners shows it as **refused**, with the reason. On a Mac, use a [Local VM](#local-vm) or Burst.

The runner keeps one outbound WebSocket to Home (no inbound port) and reconnects on its own. Large transfers share it fairly: pings, session actions and terminal output always go first, and each download or upload sends at most 4 MiB ahead of what the other side has read. A transfer that one side drops stops on the other side too. **Remove** on Home disconnects a runner; it must pair again.

## The runner's own window

A runner's own window shows only its status:

- **Home**: Home's address, with **Open Home**, and whether the runner is connected.
- **Takes new sessions**: **Yes**, or **Paused**: Home starts no new session there, and its running sessions continue. Home shows the state next to the runner.
- An update notice, with **Update**, when its build differs from Home's (see [Versions](#versions)).
- **Setup**: the runner's checklist: the link to Home, the agent jail, the network capture, the agent CLIs, the agent logins in Home's vault and the Git identity of agents. A missing part shows a fixed command: copy it, run it in a terminal on that machine, then click **Check again**. Launchpad never runs these commands.

Everything else (launches, sessions, settings) happens in Home's windows. A runner starts only the sessions Home sends it: its own window and the `launchpad` CLI of that machine cannot launch there, and that CLI cannot change Home's records through the runner either. On Burst and on a [Local VM](#local-vm), agents run as the runner's own user, so the runner keeps its sign-in token in memory only: there is no runner window sign-in (`launchpad url`) and no owner CLI there. Use Home's window. Agents' own CLI calls work as everywhere.

## Where a session runs

Every folder is stored by Home, so a launch can go to any runner: the runner clones a Git folder from Home Git and syncs a plain folder on first use. No folder belongs to one runner's disk. The composer's **Runner** option chooses one runner, or Burst; by default, the line under the prompt says "Runs on a runner, else Burst". A launch on a runner you chose never goes elsewhere: when that runner is away or paused, Home says so and starts nothing.

When a session continues (your message, **Resume**, an answer to a question, a bot or proposal message, a reply to a report, a scheduled follow-up, a Local PR review request), Home picks where it runs, in this order:

1. Its own runner, when it is connected.
2. Between turns, another runner that takes new sessions: the session's previous runner first, else the least busy one. The session moves there first (see [Move a session](#move-a-session)).
3. Burst, on a Home in a Space.
4. Otherwise, a clear error, and nothing is sent.

**Launch here** and **Run in** an existing worktree, and a new agent in an existing temporary folder, follow the same order: when the runner of that session is away, paused or needs an update, its sessions move first to another runner, else to a Burst job, which then starts the new agent. Accepted proposals, routines, scheduled launches, bot messages and Ask Launchpad use the same order. Each is sent once and never retried after a failure.

While a session runs, Stop, answers and the other session actions go to its runner. Home serves the record, the events and the trace itself. Worktree actions (Merge, Discard, Create Local PR, Restore folder, Fix merge) go to the runner of the worktree's session too. The merge itself runs on Home: when it takes more than about 40 seconds, the runner shows it as waiting and asks again, so a slow merge is never reported as failed.

Terminals and **Continue in TUI** follow the session but never move it: they open on its runner, through Home, and only while that runner is connected. When it is away, or runs an older build, the buttons are disabled with the reason; Home starts no Burst job and moves nothing for a terminal. A Git folder without an agent opens its shell on a runner picked like for a launch. See [Terminals and files](agents.md#terminals-and-files).

Home sends its profiles and the settings runners apply to their own work, such as the number of worktrees kept (**Settings → Disk cleanup**), to every runner when it connects and after each change.

## Saved on Home

At the end of every turn, the runner saves the session's work on Home: it pushes each worktree branch, syncs plain and temporary folders, and sends the conversation (the handoff). Until Home has all of it, the session shows **Saving** next to its status. When a save fails, it shows **Not on Home** in amber, with the reason in its tooltip. The runner retries every three minutes and when its link to Home comes back. The conversation is sent in full only the first time: after that, the runner sends only what was added since the last turn, and Home checks that the rebuilt file is complete. If Home refuses the short form, the runner sends the full conversation at once. After a move or a Burst start, the new runner knows what Home holds, so its first save is short too. While a session is not saved, Today shows no **Merge** for it, and a routine that waits for that agent to be Done starts only once the save is complete (at most an hour later).

A runner restart cuts the running turns short. When the runner starts again, it treats each of them as a turn end: the session shows Interrupted (or Quota paused), its work is saved on Home once the link is back, and the Telegram notification goes out after that save. A session that Home moved to another runner meanwhile is not notified.

The runner also snapshots every file of each worktree to Home, committed or not, at each turn end and every five minutes during a turn. A snapshot never touches the worktree's files, index or branch.

When the runner is away (a sleeping laptop, a stopped Burst job), or its folder was removed, Home answers from what it holds:

- **Changes** and **Files** show the branch on Home Git. When the last snapshot is newer, Changes also lists the uncommitted files "as of" that snapshot. Newer changes stay on the runner.
- **Merge** and **Create Local PR** run on Home, from the branch Home holds. A Merge sends the commit the window showed, and Home refuses it when the branch moved since.
- Discard, Restore folder and Fix merge wait for the runner, or for a message that continues the session elsewhere.
- When Git cannot be read, the session's primary button is **Review work**, never Archive.

## Burst

When a launch finds no runner that takes it (your laptop is off or asleep), Home starts it on **Burst**: an HF Job in Home's namespace, from Home's own Space image, so it runs the same build. Choose **Burst** in the composer's **Runner** option to use it on purpose. Crons, scheduled launches, bots and Ask Launchpad use it the same way when no runner is online. A message to a session whose runner is away and no other runner takes it (yours, a bot's, a routine's, a hook's or Telegram's) moves the session to Burst first, then sends the message there. Messages sent while that Burst job starts wait for it and follow in order (a retry of the same message is sent once).

Each HF Job has the labels `launchpad-burst=1` and `launchpad-burst-id=<burst id>` to identify Burst jobs and their runs.

- **No token in the job.** Home dials the job's runner through the HF Jobs proxy (the job cannot reach a private Home). The job holds no credential: its proxy sends every request that needs a token through the tunnel, and Home adds the token, sends the request and records it in the session's access log. Home Git and plain folders go through the tunnel too. Agents run without a jail inside the job: the job is the boundary. They run under the same [network capture](#network) as everywhere, and all their connections leave from Home. The job's runner cannot be read or attached to by its agents, and they never receive its credential.
- **Stopped when done.** One job runs one session. When its turn ends, the runner pushes the branches, saves uncommitted files to a scratch branch and sends the conversation to Home. After Home's next complete backup of its database (within about 10 minutes), Home cancels the job. When no backup completes within 15 minutes, Home stops the job anyway: the run shows as failed with the reason, and the session gets a note. The conversation is then only on Home's disk until a backup succeeds. Your next message starts a new job, which takes over the session and resumes its conversation (about 30 seconds); a message sent while the job is stopping does the same. If that job fails, the session shows Failed with the reason, and the message was not sent. An hour before HF Jobs' 24-hour limit, Home stops the turns still open in the job, once, with a notice in each session, so the session moves off with its files; your next message continues it elsewhere. A job without Home for 10 minutes stops on its own. A job that waits for your answer to a question keeps running, and the session says so after an hour. A job that cannot hand its session off (for example, a merge in conflict) says why in the session and stops after two hours; files not committed there are lost.
- **Tools ready.** The image holds the tools agents use most, so a session does not install them first: C and C++ compilers, `make`, CMake, `pkg-config`, binutils, Rust 1.93.1 with Clippy and rustfmt, Node 24 with pnpm, Python 3 with `uv` and `uvx`, `jq`, ripgrep, SQLite, ShellCheck, archive tools, process and network tools (`ps`, `lsof`, `strace`, `ss`, `dig`) and Chromium for screenshots (`deploy/hf-home/agent-tools.sh`). Agents cannot use `sudo` or `apt` in the job; they install other tools in their session (`uv`, `npm`, `cargo`).
- **Cost.** Settings → Home and runners shows this month's Burst cost, the cap (20 USD by default) and recent runs, with **Stop**. At the cap, Home starts no new job. Home also starts no job for a launch or message whose profile has reached a spending limit. The hardware is `cpu-basic` by default (0.01 USD per hour).

Burst needs Home to run in a Hugging Face Space, with its Hugging Face login, and an account that can run HF Jobs: a PRO account or credits (a Team or Enterprise plan, or credits, for an organization). Home checks it, and the setup page and Settings say when Burst is not available and why.

## Logs and failures

Home and every runner keep a log of their recent lines in `<data folder>/logs/launchpad.jsonl` (two files of up to 8 MB, kept across restarts). Secrets are redacted before a line is written. Home records each of its starts, and whether the run before stopped cleanly. Every 30 seconds Home notes new failures: failed or interrupted agents, failed Burst jobs, routine runs that could not start or were skipped after waiting an hour for a quota reading, failed scheduled launches, runners that went offline while agents ran on them, quota readings that held automatic work for 15 minutes, and Home restarts. Bots with admin access to the Launchpad CLI read all of this (`launchpad health`, `launchpad logs --session <id>`, `launchpad failures`; see [Bots](bots.md#diagnose-launchpad)), and a routine **When Launchpad fails** tells a bot about new failures. A runner's log is read through Home while it is connected; a Burst job that never connected has its HF Job log instead (`launchpad burst job <runner id>`).

## MCP servers

Settings → Credentials and tools → **MCP servers**: add a remote MCP server (Streamable HTTP) with its address and token. Home reads its tools. Every tool starts off, also tools that a later **Refresh tools** (in the server's **⋯**) finds: turn on each tool agents may use (the server's read only and destructive labels help, but they are hints, not guarantees). Choose where the server is granted when you save: the current workspace by default, chosen workspaces or every workspace. Which sessions get it by default is set by the [default tools](#default-tools).

Agents on every runner, Burst included, reach a granted server at a local address on their runner proxy. Each request goes through the tunnel to Home's gateway, which checks the session's lease, refuses a body that is not JSON-RPC, hides and refuses the tools that are off, adds the token and forwards the request. The token never leaves Home. Each tool call appears in the session's access log. A tool that is on acts directly with the server's token.

## Default tools

A grant decides where a tool or an MCP server can be used. The default tools decide which of the granted ones a new session gets without a click. There are three levels, and the most specific one wins:

- **Workspace:** Settings → Workspace → **Tools and MCP servers**, On or Off for each granted item. Without a choice, an item is on.
- **Folder:** the folder's Settings tab → **Default tools**: Inherit (the workspace's choice), On or Off.
- **Bot:** the bot's About → Access → **Edit** → **Default tools** (`[tools]` in `bot.toml`, for example `gh = false` or `"mcp:gmail" = true`), over the workspace and the bot's folder.

The composer's **Tools** option starts from these defaults for the chosen folder and switches any granted item on or off for one launch. Home applies the defaults each time it builds a session's lease, so a changed default applies at the session's next start or resume. An admin session can set the workspace and folder defaults with `launchpad do tools.defaults workspace|folder <id> --tools '{"gh": false}'`.

## Notifications and routines

Home sends notifications through the Telegram chat of each session's workspace, wherever the session runs: a runner forwards the notification of a session that finishes, fails or is interrupted to Home. There are no desktop notifications. Routines, scheduled launches and the morning brief run on Home's schedule, on a runner when one takes the run, otherwise on Burst ([Routines](bots.md#routines)).

## Move a session

Between turns, a session can move to another runner: in its Summary, **Runs on** → **Move to…** lists the connected runners and Burst. Home also moves a session on its own when it continues and its runner is away (see [Where a session runs](#where-a-session-runs)). The new runner clones the worktrees again from Home Git, puts back the uncommitted files of the last snapshot, and resumes the same conversation (Claude Code, Codex and OpenCode). A snapshot it cannot apply goes to an `lp-scratch/<branch>-snapshot` branch, and the agent is told where. Attachments of the session move with it. The move increases the session's generation, so the old runner can no longer push its branches or get a lease. Home records the runner of each turn end it receives, so the Summary's **Turns ran on** shows which machine ran which turns.

When the old runner is connected, it pushes the branches, saves uncommitted files to a scratch branch and removes its folders first. Home waits up to 30 minutes for that save. After that, the move fails with “still saving” and the save goes on: try again later. A session moves once at a time, and messages to it wait for the move. If the new runner cannot take the session over at once, the move still holds: the runner takes it over with the next message. When the old runner is away, the session continues from what Home holds: the last turn's branches, snapshot and conversation. Home tells the old runner to release the session, now or when it comes back. Home keeps that request, like an **Archive** made while the runner was away, until the runner has answered it, also across Home restarts. On release, the runner stops what it still runs of the moved sessions, pushes their commits and uncommitted files to `lp-scratch/<branch>-gen<n>` branches, and removes their folders once Home has confirmed them.

A session in a temporary folder (a bot without a folder, such as Ask Launchpad) keeps it when it moves: Home holds the folder's files as of the last turn end, and the new runner puts them back in a folder with the same name. A temporary folder that holds a Git repository stays on its runner: Launchpad refuses to move it, and **Keep as folder** while that runner is away is refused too. Keep it as a folder while its runner is connected.

Home is the place that keeps conversations. Agents save their conversation files normally, in the session's own folder. About an hour after a session is archived, its runner sends that conversation to Home one last time. When Home has confirmed it, the runner deletes the session's folder (`<data_dir>/sessions/<id>`). Resume gets the conversation back from Home before the agent starts. Traces (`launchpad trace`) always come from Home, which holds every turn of every runner.

## Sessions on Home

Every session a runner runs is saved on Home: its record and every event, in order. The runner writes them to a local outbox in the same transaction as its own copy and drops them only after Home has saved them. The runner sends the outbox in batches of up to 4 MiB, one at a time, and sends the next batch from the last item Home saved. An item that fails on Home is sent again. Home skips it only after it kept failing for 10 minutes, and logs an error. While Home is unreachable, sessions keep running on the runner; the outbox is sent when the link is back.

Attached images and files are stored on Home. Records and messages only name them (`upload:` references), so a large screenshot never slows down replication. A runner fetches the files from Home when a session it runs needs them, and the agent gets the images when the message is delivered. Chat images stay viewable as long as a message names them. Home never marks a runner's session Interrupted when Home itself restarts.

While a runner is disconnected (a sleeping laptop), Home shows "<runner> offline" next to its sessions' status: the status is the last one Home received. Seen and unread are kept on Home, so a finished session leaves Today even while its runner sleeps. **Archive** works too: Home closes the session at once, and the runner archives it (and stops it, if it still runs) when it reconnects.

A session that was running, asking a question or paused for quota on a runner that has been away for 10 minutes becomes **Interrupted** on Home, with a note as its last message. Send it a message to continue it elsewhere from its last saved turn. If the runner comes back first, its own record replaces the Interrupted one. When you **Remove** a runner, its open sessions become Interrupted the same way.

Each session has a generation number, which grows when a session moves to another runner. Home ignores records and events of an older generation, and late events of an older generation are kept in the trace, before the new ones.

## Home Git

Home keeps a mirror of every Git folder: every branch of the folder's remote, plus Launchpad branches (`lp/…`), which only agents push. An agent's Git credential pushes only its own branches, their `lp-scratch/…` leftovers and its worktrees' snapshots, and only in folders of its workspace (or folders you named in its launch). Runners clone from Home, fetching most objects directly from the remote first.

- Every session starts in a fresh worktree of its branch, cloned before the agent starts. A worktree is removed only after Home confirmed its branch; uncommitted files are saved to an `lp-scratch/…` branch first. An `lp-scratch/…` branch is kept 30 days after its last push (or its commit date, when that is later). Before Home deletes it, it keeps its tip under the previous tips for 30 more days, so **Restore** still works.
- A runner pushes a branch only over the tip Home last confirmed for it. If the branch changed on Home in the meantime (you clicked **Restore**, or another runner pushed commits), the push is held and the session gets one notice. The agent then fetches and resets to Home's tip (after a Restore) or rebases onto it (after another runner's commits). New commits on top of the held ones stay held too, so they never undo a Restore. Until then the session stays marked as not saved, with the reason, and a move saves the held commits to an `lp-scratch/…` branch.
- `origin` in an agent's worktree is Home Git, through its runner: agents never hold a credential for it. A runner that lost a session to another runner can no longer push its branches.
- Only Home changes base branches, through **Merge** (a push to the folder's remote, then a fast-forward on Home; a refused push merges nothing) and **Publish** (the reviewed commit). A base branch that moved goes back to the agent for a rebase; after your own **Merge**, Home merges the rebased branch once the agent's turn is saved. Home checks every merge a runner asks for against its own records. An agent's own merge (`launchpad work finish`) needs a launch with **When done** = Merge, in a folder of its workspace. A merge counts as yours only for the folder, branch and commit of a **Merge** you clicked; a Merge that still waits when Home restarts must be clicked again. Home records each merge, so a branch shows as merged on every runner; new commits after a merge show **Merge** again.
- Home keeps every previous tip of a Launchpad branch for 30 days, also after force pushes and deletes. The folder page lists Launchpad branches and their previous tips, with **Restore**.
- Every six hours, Home cleans up each mirror that has many loose objects or packs (`git gc`). It keeps every object a branch, tag, previous tip or snapshot still uses, and every object written in the last day, so a push that runs at the same time is safe. It first drops the Files copy of that folder, which Files builds again when it next opens.
- Local PRs live on Home: diff, review, Merge and Publish work from the phone while the laptop sleeps. Local PRs opened by one agent form a change set. **Publish all** checks every Local PR's reviewed commit first and publishes nothing when a branch moved.
- Sessions that continue a GitHub pull request push to Home; Home pushes the branch to the pull request after each push by a session that works on it, never forced. Published Local PRs work the same way. Until GitHub has the commit, the branch and the Local PR show **Not on GitHub yet**, with the last error; each refresh retries.

## Files on Home

Home keeps each Git folder as a bare mirror. For **Files**, it keeps a read-only copy of the default branch next to it, which borrows the mirror's objects and lists every branch as `origin/<branch>`. The copy is refreshed when Files opens, at most every 30 seconds, and at once after a push or a merge. Plain and temporary folders get a read-only copy of the files Home holds. Files of a session that runs on a connected runner (its worktrees, plain copy or temporary folder) are read on that runner. When that runner is away or its folder is gone, Home shows a worktree from its branch on Home Git (or the last snapshot, when it is newer), and a plain or temporary folder from the files of the last turn.

## Plain and asset folders

A **plain folder** has no Git: Home stores its files (Add folder → **New plain folder**, or **Keep as folder** on a temporary folder). Runners work in a synced copy: it comes down from Home before a session starts and goes back at the end of every turn. One agent works in a plain folder at a time; another launch fails until the first agent is archived. Changes compares with the start of the session. Files shows the files Home holds (the state at the end of the last turn), read-only. Home keeps every overwritten version and every deleted file for 30 days: the folder page lists them under **Versions and trash**, with **Restore**.

Symbolic links are not stored. When a runner sends a plain or temporary folder to Home, it leaves links out and logs one line per sync. When it downloads files, executable files get mode 755 and other files the default mode of new files.

A plain folder can become a Git folder: on its folder page, open **Settings** and click **Turn into a Git folder**. Its current files become the first commit of `main` in a new Home Git folder without a remote; agents then work in worktrees and branches.

An **asset folder** holds large or generated files of a Git folder (datasets, media, model files) outside Git. An agent runs `launchpad assets create <path> --session-id <id>` in its worktree: the path is mapped in `.launchpad/assets.toml` (committed), kept out of Git, and synced like a plain folder, so later sessions on that branch get the same files. Assets are shared, not pinned per commit. An asset folder that is a symbolic link, or that a link leads to, is never synced: the runner skips it with a warning.

The folder page of a Git folder lists its asset folders with their size. An asset folder that no branch, kept tip or knowledge base note names, and that nobody changed for 14 days, goes to the trash: its files are removed and **Restore** puts them back for 30 days.

Contents are stored by hash and included in Home backups. Home deletes a content that no file lists only when it is at least an hour old, so an upload that waits for its file record is never lost.

## Backups

Home backs up its database, `config.toml`, the files attached to drafts, scheduled launches and routines, and a Git bundle of each mirror's Launchpad branches and kept tips (only what the folder's remote does not have) to `[home] backup` (`hf://buckets/<you>/launchpad` or a folder) when something changed, and before a planned stop. Each backup holds a full copy of the database, so Home copies it at most every 10 minutes; new Git refs and attached files are backed up every minute, together with the last database copy. Objects are stored by content hash under `home/blobs/sha256/` and never overwritten; each backup is a manifest under `home/backup/<time>/`, written last, so a backup is complete only when its manifest exists. Settings → Home and runners shows the last complete backup and has **Back up now**. A plain-folder file whose content is neither on Home's disk nor in the destination cannot be backed up. Home leaves it out of the backup, so the backup stays complete and can be restored. It reports the missing contents in Settings → Hugging Face, `launchpad home` (`backup.missing_blobs`) and `launchpad failures`.

Retention: after each complete backup, Home keeps only the newest backup, the one before it, the newest backup at least an hour old, and the newest backup at least 1, 2, …, 10 days old (so at most 13), dated by the time in their path. It deletes the other manifests first, then the objects no remaining manifest lists, except objects uploaded in the last hour. The destination so holds about 13 kept database copies plus those of the last hour (at most 6). It prunes only when the newest backup is complete (every object present with its size), never deletes the two newest backups or a backup it cannot date, refuses when it would keep fewer than two backups, runs one pass at a time and never during a backup, and touches nothing outside `home/backup/` and `home/blobs/`. A listing or download that fails is an error, never an empty list: the pass then deletes nothing. It also deletes nothing when the listing misses the backup just written, or while a backup of the last day cannot be read. A skipped or failed pass never affects the backup: its reason shows in Settings → Hugging Face, `launchpad home` (`backup.prune_error`, with `pruned_at` and `prune` for the last pass) and `launchpad failures`. The first pass after an update also removes the older backups already in the bucket. After each backup, Home writes readable copies of each workspace's knowledge base and bots (`<workspace>/kb/…`, `<workspace>/bots/<bot>/…`) and removes the copies of deleted files; restores never use them. Home also keeps a list of what the trace copies and readable copies already hold, on its disk and in the destination under `home/copies/`. A restored Home reads that list, so it does not copy every trace again.

When Home starts on an empty data folder, it restores the newest complete backup (every object present, hashes checked) before it opens the database. Plain-folder files download when first needed (on a first boot without `config.toml`, `LAUNCHPAD_HOME_BACKUP` names the destination). If the destination cannot be read, Home tries again for about a minute, then fails to start with the error. It also fails when the destination holds backup objects but no readable backup, or when the newest backup misses objects. Only a destination with no backup objects starts a new, empty Home. To start fresh on purpose, empty the `home/` folder of the destination (or choose another destination).

Each Git folder's bundle (Launchpad branches, kept tips and snapshot refs) stays pending after a restore. Home applies it the next time the folder's mirror is used, after it fetched the remote again, and retries at each use and each backup until it works. Until then the bundle stays in every backup. A bundle only adds the refs the mirror does not have: it never overwrites a branch that changed since. Runners then reconnect with their existing credentials and resend what Home has not acknowledged. After an unplanned restart, up to about 10 minutes of database changes (events acknowledged since the last database copy) can be missing.

### Database cleanup

Once a day, and at each start, Home and every runner remove old rows from their database:

- Retry records of launches and messages (they make a repeated click or a retry run only once) go 7 days after they completed. A record without a result, because the request was still running or its outcome is uncertain, is never removed, so it still blocks a second run.
- Raw harness output (kept for debugging, never shown) goes after 14 days, and at once when the session is archived. Each line is cut to 64 KiB, and a session keeps at most 20,000 lines and 16 MiB.
- Entries of the access log go after 30 days.

## Credentials and tools

Home’s image includes Claude Code, Codex, OpenCode, `gh` and `hf` for discovery, usage and quota checks. A hosted Home opens on a setup page that leads from an empty Home to a first agent: Hugging Face sign-in, the credential key (generated or your own, saved by you, then kept as the `LP_HOME_KEY` Space secret after a restart you confirm), GitHub sign-in, the Git identity, a first profile (Claude Code or Codex subscription sign-in, stored in the vault, with its default model and effort), a workspace with a first cloned folder, then the optional steps: a runner (done once paired, also while it is offline) and a first agent. Home opens when the required steps are done; optional steps never keep it closed. The GitHub step counts only while GitHub accepts the token; if it is later revoked or expires, the step and Settings → GitHub show it as not signed in (Home stays open) and **Sign in to GitHub** in Settings runs the same sign-in as the setup page. **Settings → Onboarding** opens the setup page again at any time, and **Open** next to a finished step shows it again to review or change it (sign in again, edit the Git identity, choose another model, clone more folders, approve a runner). Each sign-in and restart starts only on a click. Credentials in the bucket (vault secrets in backups, Home's own logins) are encrypted; other data stays as plain files you can browse. Agents never get Home's logins. Its backup is mandatory, with status in Settings → Hugging Face. After each backup, Home also copies every agent's original conversation files to the bucket, one file per trace, under `<workspace>/traces/` ([Hugging Face](hugging-face.md#traces-in-the-home-bucket)). On Home, the **Setup** page lists the same steps with their state and where to change them, and the sidebar's **Finish setup · N left** counts only the required steps.

Home keeps every credential agents use: open **Settings → Credentials and tools** on Home.

- **Harness logins:** a Claude Code token (`claude setup-token`) and a Codex ChatGPT login (from then on only Home refreshes it, so do not use that login elsewhere; when Home's quota check refreshes it, the vault keeps the newer login). On a Home in a Space, **Add a Claude Code login** or **Add a Codex login** runs the sign-in on Home itself, like the setup page: open the link, approve with the subscription account (for Claude Code, paste the code it shows back), and the login goes into the vault with an optional name and a new profile that uses it. Elsewhere, paste the token or `auth.json` (**Paste a login instead** in a Space). A profile can name its login. Otherwise it uses the harness's default login: the first by name, then by ID. The agents get that login, and Home reads its quota. **Refresh** on a login refreshes a Codex login on Home now, whatever its expiry (running agents get the new token within a minute), or checks a Claude Code token with a one-token request, then reads the quota again and shows the result under the login. When the provider refuses the login (a revoked or expired token, from Refresh or from Home's quota check), the login says it needs a new sign-in; on a Home in a Space, Refresh then starts the sign-in on Home for that login, and the new login replaces it in place (same ID and name), so its profiles and running agents keep it.
- **Tokens:** tokens and API keys for tools. Secrets are write-only: Launchpad never shows them again.
- **Tools:** adding a tool asks only for its API token, with a link to create one. For GitHub CLI and Hugging Face CLI, **Use Home's token** lends Home's own login instead (agents then act with Home's full access: a fine-grained token is safer). The **Advanced** section holds the rest. Each entry says how a runner installs the CLI (GitHub release, download URL, `cargo`, `uv tool` or `npm`), which variables get a placeholder (for example `GH_TOKEN`), on which hosts the proxy adds which token (Bearer, Basic, a header or a query parameter), and in which workspaces it is granted. **Settings** holds values that are not secret, one `KEY=value` per line (an endpoint, a read-only switch, an output format): runners set them only when the tool's own commands run, through a small wrapper script on the agent's PATH, never in the agent's environment, so they need an install. GitHub CLI and Hugging Face CLI are ready-made; **Copy as TOML** exports the list. Which granted tools a new session gets is set by the [default tools](#default-tools). A host is a plain host name such as `api.example.com`, or `*.example.com` for its subdomains: no port, path or user name. Home saves it in lowercase. The proxy adds one token per host: when two tools that are on send different tokens to the same host, a launch gets only the first one by name, and switching the other on in the composer's Tools switches the first one off.
- **Slack:** the **Slack** card sets up [slackline](https://github.com/co42/slackline) in two modes, each with its own Slack app and token. **Slack (read-only)** has read permissions only and the setting `SLACKLINE_READONLY=1`, which turns off every write command. **Slack (write)** can also post, reply, react, pin and upload. For each mode, **Open Slack to create the app** opens Slack's "Create app" page with the name and permissions filled in (the same page as `slackline token create`, or `--write`): pick your Slack workspace, click **Create**, open **Install App**, click **Install to Workspace**, then copy the **User OAuth Token** (`xoxp-…`) and paste it. Home tests the token after you save it. **Delete** removes the token from Home's vault (the tool and its workspaces stay; sessions lose it at their next lease renewal) and shows the steps again: to replace a token, delete it and paste the new one. Delete does not revoke the token in Slack: it stays valid there until you uninstall the app. Both modes are granted in every workspace: a launch gets read-only, and you pick **Slack (write)** in the composer's Tools when an agent must post, or turn read-only off in the [default tools](#default-tools) of a folder or bot that always posts. The setup page shows the same card as a recommended, optional step.
- **Proposed tools:** an agent that needs a CLI or API can propose a tool (`launchpad propose tool`). The card (in Today → Approve) shows what runners would install, the variables and the hosts that receive the token; **Add tool** adds it after you confirm (its token is always a new entry, never an existing one), then **Paste its token** opens its form. Tool proposals never start in auto mode.
- **Test:** a tool with a check URL (GitHub, Hugging Face and Slack have one; set it under Advanced for others) has **Test** in its **⋯**: Home sends one request there with the token and shows whether the host accepts it (a 2xx answer, without `"ok": false` in a JSON body). The token never leaves Home.
- **Git identity:** the author of agents' commits on every runner.

When a session starts, its runner gets a **lease** from Home: the session's login, its granted tools and their tokens. Home gives a lease only for a session it placed on that runner, in its current generation, and builds it from its own record of the session (workspace, folder, bot, login, tools), never from what the runner asks. The runner keeps the lease in its proxy's memory only. Agents see placeholders: when a request goes to a host of the lease, the proxy adds the real token and records host, method and path in the session's access log (Summary → Run → Credentials), naming actions such as "opened PR #3421". Other traffic passes through untouched. What a request may do is decided by the token's scopes: use fine-grained tokens. Summary → Run → Credentials lists the tools and MCP servers of the workspace, green for those the agent holds. An agent keeps its tools until it ends: to change them, stop it and launch a new one. Stop and Archive end the lease, and a runner that cannot reach Home drops it after an hour.

Quota: Home reads the quota of each vault login once and sends the readings to every runner, so quota protection works the same everywhere. Home also decides which login is a harness's default, so a runner checks a profile without its own login against the same reading as Home. Running Claude Code sessions also report the quota they see, and runners pass it to Home, so the reading stays current while Anthropic's usage endpoint refuses Home's checks (429).

Spending limits count every machine together: each runner and Burst job sends each cost increase to Home, and Home sends the total to every runner, which checks the limits. The status bar on Home shows the real spending of all of them.

## The jail

Every agent runs contained. On a runner it runs in a bubblewrap jail (`sudo apt install bubblewrap`; Ubuntu 24.04 needs user namespaces allowed for `bwrap`). Inside, the agent sees the system and the machine's toolchains read-only, and only its own folders read-write: its worktrees and plain folders, its harness home (`~/.local/share/launchpad-runner/sessions/<id>/home`, with its own `CLAUDE_CONFIG_DIR` and `CODEX_HOME`), its own `/tmp` and the build caches of its workspace (Cargo, and `sccache` for Rust builds when it is installed on the runner). Your home folder, `~/.ssh`, `~/.config/gh`, `~/.claude`, Launchpad's data and the Docker socket do not exist inside. No read-only mount holds your home folder, Launchpad's data folder or a credential folder (`~/.ssh`, `~/.config`, `~/.local/share`, `~/.gnupg`, `~/.docker`, `~/.kube`, `~/.aws`). A PATH folder that would hold one is left out. When a harness CLI's release folder would hold one, the jail mounts the CLI's `bin` folder instead, or only the program file. Title requests, harness TUIs and the folder's **Worktree setup** command use the same jail, lease and network capture. So you can edit a folder's setup command from any window: it never runs outside the jail. Agents cannot change it.

Agents can write the Git data of their worktrees, so the runner's own Git (snapshots, pushes, Files and Changes) ignores every Git setting an agent can write: the repository's config, hooks, filters, attributes and remotes. An agent's own `git config` in a clone (hooks, filters, LFS settings, remotes) therefore never affects what Launchpad saves or shows. The runner sends its Git credential only to Home's exact address. A terminal you open in a worktree is not covered: your shell and its tools still read the agent's Git config there.

On a runner whose jail uses bubblewrap, the runner's own Git also runs in a small bubblewrap sandbox. It sees only the system programs, a short list of `/etc` files and the folders it works in: the repository caches and worktrees, or one plain or temporary folder. Your home folder and the rest of Launchpad's data do not exist there, so a link or Git alternate that an agent plants to a file elsewhere on the machine never reaches Home. Such a runner needs bubblewrap for its own Git too: without it, saves, Files, Changes and terminals in Git folders fail with the message “bubblewrap is not installed”. The sandbox has no `~/.ssh`, so the runner no longer fetches a folder's SSH remote itself: Home sends the commits. Local VM and Burst runners skip this sandbox: the machine is the boundary, with no files of yours.

The runner also never follows a symbolic link that an agent plants in a folder it can write. This covers plain, temporary and asset folders, native traces, attachments, a session's `/tmp` and the files the runner writes in the harness home (logins, MCP settings, instructions, `.gitconfig`). The runner opens such paths one folder at a time and refuses a link on the way. It reads only regular files, never a link, a FIFO or a device. When it writes, it writes a new file and renames it into place, so a planted link is replaced, never written through. Your own links stay usable: the data folder and its first-level folders (such as `worktrees` or `sessions`) belong to the runner, so they may be links to another disk.

### Network

An agent reaches the same addresses with the same credentials in the jail, on a Local VM and on Burst, whatever tool it uses. Every agent process runs under Launchpad's **network capture**: a small supervisor that the agent cannot remove (a seccomp filter) hands each connection to the runner proxy, also for programs that ignore `HTTPS_PROXY`, static binaries and background processes. So a tool works on every runner or on none.

- **Where traffic leaves:** on your runners, from the runner's own network, so agents also reach its LAN and tailnet (a private GitHub server, a local database). On Burst, every connection leaves from Home, which reaches public addresses only.
- **Tokens:** on a host of the lease (HTTPS on port 443), the proxy adds the token as above, also for a client that ignores proxy settings. It adds it only when the request goes to exactly that host, on the default port and without a user name in the URL; a request built to reach another host gets an error instead. The runner CA is in the sandbox's system certificate store, so Go, OpenSSL and most Python and Rust clients trust it. A client with its own built-in certificate list fails with a visible TLS error on those hosts only, the same way everywhere.
- **Policy:** `localhost` is reached directly (the Launchpad CLI, harness logins, the agent's own servers). UDP reaches DNS (port 53) only: QUIC falls back to TCP, and other UDP (NTP, `ping`, WebRTC) is refused. Link-local addresses and cloud metadata servers (169.254.0.0/16, fe80::/10 and the like) are refused, except DNS on port 53. Unix sockets at a path work, but the machine's abstract Unix sockets (X11, D-Bus) are refused. IPv4 and IPv6 follow the same rules. io_uring is blocked.
- **Requirements:** Linux 5.9 or newer, on x86_64 or arm64. A runner where the capture cannot run starts no agent and says why.
- Processes an agent leaves running after its main process exits lose their network.
- **Browsers:** headless Chrome and Playwright work under the capture, with their crash handler and helper processes. In the jail, Chrome uses its own sandbox. On Burst, HF Jobs refuse the user namespaces that Chrome's sandbox needs: the image's `chromium` adds `--no-sandbox` itself, Playwright does by default, and another Chrome needs it passed.
- Where the kernel allows it (the jail on most systems), agents run in their own user namespace: groups other than their own show as `nogroup`, and files of other users as `nobody`.

**Check network** (Settings → Home and runners, on each connected runner) runs a fixed probe in a real session sandbox on that runner: capture, DNS, refused UDP, IPv4 and IPv6, the runner CA in the system store, the same checks from a non-dumpable process (as Chrome's helpers are), a connection the proxy received, Unix sockets at a path, refused abstract Unix sockets (X11, D-Bus) and refused link-local addresses (cloud metadata). A failed required check marks the runner **network differs**; IPv6 depends on the runner's network and is only reported.

### Local VM

Docker needs root, so it never runs in the jail. A **Local VM** is a runner inside a virtual machine, where the VM is the boundary: agents run without a jail and may use Docker, with the same lease, proxy and network capture. Agents in the VM cannot use `sudo` (the capture forbids gaining privileges), and containers that Docker starts are outside the capture: their traffic leaves directly and gets no token. The script also puts the runner CA in the VM's system store; run it again on an existing VM. `packaging/local-vm.sh <Home address>` creates one with Multipass (Ubuntu, Docker, Claude Code, Codex, the same tools as Burst except Chromium, and a runner set to `[runner] boundary = "vm"`), then pairs it. Home shows it as **Local VM · Docker**; choose it in the composer's **Runner** option for a task that needs Docker. Agents in the VM can read the runner's files, including its link to Home. That link is enough to act as the runner, never as you (see [What runners and agents may do](#what-runners-and-agents-may-do)). The runner keeps no sign-in token on disk, so the VM has no runner window or owner CLI.

## Versions

Home and its runners compare their protocol and build. A runner with another protocol cannot connect. A runner with another build of the same protocol takes no new sessions; its running sessions continue. The status bar then shows **<runner> needs an update**, the composer warns before a launch (the chosen runner, or with Automatic, where the launch goes instead), the Runner option marks it **needs an update**, and Settings → Home and runners explains how to update it.

**Update** (in Settings, in the composer warning, or in the runner's own window) updates it from Home: the runner downloads Home's own executable through its tunnel, checks its SHA-256, OS and architecture, waits until none of its agents is in a turn, replaces its executable and restarts itself in place (same process, so its systemd service keeps running). Its sessions continue after the restart. **Cancel** stops an update that still waits for agents. Only runners built with this feature (from November 5, 2026) offer Update; update older ones by hand once. By hand, with a Home in a Space, run the install command again on that machine: it installs Home's build and restarts the runner, which stays paired. Otherwise, install Launchpad at Home's commit and restart the runner daemon. The restart interrupts the runner's running turns: update it when its agents are done.

## Agent CLI updates

Runners keep their agent CLIs (Claude Code, Codex, OpenCode) up to date on their own:

- **Check.** Every six hours (and on **Check now** in Settings → Home and runners → **Agent CLI updates**), Home reads the newest release of each CLI's npm package (`@anthropic-ai/claude-code`, `@openai/codex`, `opencode-ai`) and asks each connected runner which version it has.
- **Same major version: automatic.** A newer release of the same major version installs without asking. Under semver, a 0.x version that changes its minor number is a new major version (0.166 → 0.167), so Codex asks for most of its updates: its app-server protocol, which Launchpad speaks, changes between 0.x minor versions. A runner behind a new major version still gets the newest release of its own major version.
- **New major version: your approval.** It waits in Today → Approve as **Update <CLI> to <version>: new major version**, with each runner's current version and the release notes. **Approve** installs it on those runners; **⋯ → Skip this version** removes the card (a newer major version asks again).
- **Who installs.** The runner daemon, never an agent. It finds how the CLI was installed: with npm (it runs `npm install --global --prefix <the same prefix> <package>@<version>`), or with the CLI's own installer (`claude install <version>`, `opencode upgrade <version>`). It waits until none of its agents is in a turn, starts no new agent until the install is done, then reads the version again. Running agents are never interrupted; an agent process that stays open between turns keeps its old version until it restarts.
- **When it cannot.** A CLI in a folder the runner's user cannot write (for example `/usr/lib/node_modules`), or installed another way (a system package, Homebrew), is left alone. Today → Fix says so, with the command to run on that machine (for example `sudo npm install --global --prefix /usr @openai/codex@0.167.0`). The next check sees the new version and marks it done.
- **Results.** Today → Review shows the newest completed update of each CLI: which runners, the old and the new version, and the release notes; **Mark read** moves it to Done. An update that failed waits in Today → Fix with **Retry**. Each update is asked once per runner: a failure, or a runner that restarted during the install, is never retried on its own.
- **Off.** Each CLI has **Automatic** or **Off** in the same card (`[home.cli_updates]` in `config.toml`, for example `codex = false`). Off: Home neither checks nor installs that CLI; runners keep what they have.

Burst jobs and Home's Space do not update their CLIs: they use the versions pinned in Home's image (`deploy/hf-home/release.json`), so a Burst job starts in seconds with tested versions. `deploy/hf-home/bump_tools.py` bumps those pins with the same rule (`--major` for a new major version); the next release or main package ships them.

## What runners and agents may do

A runner is a low-trust worker. Its link to Home reaches Home Git, plain folders, handoffs, leases and replication for the sessions Home placed on it, plus a short list of requests its own work needs, each checked against Home's records. It reads knowledge bases, bot files, plain folders and Local PRs only of the workspaces of its sessions. Nothing a runner sends runs as you: it never reaches the vault, MCP settings, connections, the Outbox, Suggestions, Local PR publication, Home updates or the sessions of another runner. So a runner you lose, or one whose agents read its files, reaches only its own sessions.

Contained sessions receive a session CLI credential bound to their ID and generation, not the runner's token. The runner forwards an agent's Launchpad CLI calls to Home, and Home checks them with that agent's access from its own records. Host settings, terminals, file APIs and publication still require your window.

Workspaces are a boundary for agents. An agent's lists, traces, Local PRs, proposals and admin actions cover only its session's workspace, and `launchpad work add-project` adds only folders of that workspace. Presets, shared settings, MCP tool switches, Home updates and diagnostics stay Launchpad-wide. See [Bots](bots.md#the-launchpad-cli-tool).
