# Chrome extension E0 — focused integration checks

2026-10-22. Direction: **go with option A**, a Launchpad-owned MV3 extension, daemon broker and stdio MCP bridge. E0 was deliberately limited to decisions needed for the read milestone; this is not the report's full site/latency benchmark.

## Harness transport and isolation

Installed versions: Claude Code 2.1.307, Codex 0.163.0, OpenCode 1.18.35. The bridge serves newline-delimited MCP JSON-RPC with initialize, tools/list, text results, cancellation and bounded calls (20-second broker wait, 30-second native timeout). Read tools advertise read-only/idempotent annotations. No owner confirmation waits or action retries exist in E1. Images and long confirmation waits are deferred with screenshot/action tools.

Codex's locally generated experimental schema exposes `config` on both thread/start and thread/resume. A real Codex thread completed the signed-in fixture task through all four browser tools, including its pinned Claude trace, and correctly answered “09:30” and “three blue notebooks” in a separate conversation. The first recorded complete assistant message arrived after 5.3 seconds and the complete turn took 13 seconds; a warm first-token measurement remains outstanding. Its initial never-approve policy blocked unannotated MCP calls; the read tools now carry annotations and the adapter explicitly approves this read-only server. Config overrides use nested objects: quoting names inside flat dotted keys created a literal quoted server name and an invalid transport. `config/read` also serializes unset numeric MCP options as empty strings; disabled-server overrides retain only transport fields rather than copying that readback. Browser overrides disable other configured servers, plugins and apps and select a read-only sandbox. Native shell tools remain available, so this is partial isolation, disclosed in the panel. Ordinary threads do not receive this MCP server.

Claude uses strict MCP config, no built-in tools, and an allowlist for this server. The local subscription was quota-paused by Launchpad, so its signed-in-page answer remains unverified; paid usage was not enabled to bypass protection. OpenCode accepted the ACP session/MCP configuration, but the available free model rejected use through ACP (“free tier can only be used from within OpenCode”). An account/model permitted through ACP is still needed for its full answer check. OpenCode's native config is merged, so the adapter explicitly disables existing MCP entries and permission keys rather than relying on empty objects.

References: [Codex app-server](https://learn.chatgpt.com/docs/app-server), [Codex MCP configuration](https://learn.chatgpt.com/docs/extend/mcp), [OpenCode config precedence](https://opencode.ai/docs/config/), [OpenCode permission rules](https://opencode.ai/docs/permissions/).

## Pairing and MV3 lifetime

Google Chrome 154 on Ubuntu successfully invoked the registered native host, exchanged a local pairing link for a revocable device cookie, and reopened the shared panel. The unpacked extension uses a pinned public key/ID. Developer mode must stay enabled; Chrome disabled the unpacked extension after a reload when that setting was off. Native messaging on macOS/Windows and Chromium snap was not exercised; reverse pairing remains available.

HTTP fetch with host permissions sends Launchpad's Strict cookie, but extension WebSocket handshakes omitted it in the real Chrome check. E1 therefore uses an authenticated HTTP-issued, 30-second, single-use socket ticket bound to the pinned origin and device validity. It preserves the existing cookie policy, Host/Origin checks, bus replay, pings and revocation. [Chrome's cookie documentation](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies) describes the extension HTTP exemption; the WebSocket behavior was checked directly.

## Shared UI, reads and explicit grants

The extension bundles the existing React composer/session components with its own Vite entry. Explicit Tailwind sources are required for shared component classes. Drafts have a per-extension-device namespace. Follow-up reuses the scratch folder and pins trace context but starts with an empty grant list; `browser_trace` reads only attached references without requiring a shell tool.

A throwaway, cookie-protected page was read in Chrome through the real broker/worker path. Article text, selection and outline passed; password/OTP values, hidden/private nodes and iframe content were excluded. Cross-session tab handles and a write-tool request were rejected. Same-document URL navigation invalidated access. Reloading the extension resets the document nonce and also requires a fresh grant. The reader bounds traversal, text and pagination; the proposed ten-site quality sweep (especially canvas editors and frames), debugger latency/bar and warm first-token benchmark remain outstanding. Debugger permission is absent from E1.

Verification: extension and web production builds/type checking, pinned strict workspace Clippy, all 99 existing Rust tests (83 core, 16 server), five existing composer regressions, seven draft regressions, four attachment regressions and eleven retry-operation regressions passed. The panel was inspected at 420 CSS pixels with no horizontal overflow or JavaScript exceptions. Its real Follow up action prepared a trace-linked draft with no grants and Launch disabled. Reverse code pairing rejected an incorrect secret, required explicit approval, and collected a device cookie. A socket ticket upgraded once and was rejected on replay; device revocation closed an upgraded viewer, and Stop removed session grants. Throwaway sessions/devices were closed/revoked afterwards. No new unit tests were added.
