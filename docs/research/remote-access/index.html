01 / FEASIBILITY

Yes. This is an extension of Launchpad.

The laptop UI is already a web UI. The desktop shell opens a webview onto an Axum daemon, which serves the React application, exposes JSON endpoints and streams events over WebSocket. We do not need to translate a native UI into HTML.

Shared UI

No near-duplicate web app

Keep web/. The same build can serve the local desktop and the VPS browser. Desktop and phone navigation can differ while using the same feature logic.

Headless

No desktop required on the VPS

The daemon already owns the agent harnesses. Build and run launchpad without running the Tauri shell. GitHub integration and repository access happen on the host.

Not turnkey

A proxy alone needs careful adaptation

The server binds to loopback, rejects unknown Host and Origin headers, and requires its token. Several buttons also launch desktop programs on the server.

Repository evidence: server and auth, desktop shell, browser transport. These conclusions come from inspected code, not a remote deployment test.

02 / DEPLOYMENT

Choose where the work lives first.

“Access through the web” and “run on a VPS” are separate decisions. The backend’s machine owns every path, checkout, command and credential. Your phone is a remote control, not the machine doing the coding.

The attractive part

Always available, one source of truth for the remote workload, agents keep running after you close the phone, and the laptop browser sees precisely the same sessions. No synchronization protocol between those two clients.

The price

Your development environment moves too: repositories, uncommitted files, worktrees, language runtimes, private package access, SSH keys, gh and harness logins. Editing those files from the laptop needs a remote editor/SSH workflow.

The existing native laptop app still points to its local daemon. Using a browser for the VPS is the simplest first client. A remote-host selector in the desktop shell would be separate work.

The attractive part

You control your existing sessions from the phone. Desktop and phone talk to one daemon, so committed changes, dirty files, pre-drafts and local suggestions need no migration. A reverse SSH tunnel or private overlay avoids public inbound connectivity to the laptop.

The price

The laptop must stay awake and connected. Sleep, Wi-Fi changes or a tunnel failure make the phone unavailable. The VPS adds routing, not computing capacity or restart survival.

A private tailnet with Tailscale Serve is another route that may eliminate the VPS relay. Serve limits sharing to the tailnet; Funnel exposes a service publicly. Either still needs Launchpad’s request checks handled.

A simple host picker is possible without a worker fleet: each host retains its own data and you select one at a time. Namespace every query cache, browser draft and selected session by host. Clearly label the execution target on Launch.

A unified fleet is a different product: host routing, worker heartbeats, unavailable-host queues, credentials, session ownership, aggregate quotas, scheduling, and partial failure recovery. The previously reverted Phase 7 worker design is not available to reuse as a built feature.

Do not share a live SQLite database or a writable worktree between daemons over a network filesystem. Treat hosts as distinct environments; transfer committed work through explicit Git operations.

My recommendation

Use a single execution host for the first version. If the real goal is “trigger agents from my phone against the work already on my laptop,” start with B. If the goal is “launch work while my laptop is asleep,” choose A and make the VPS the home of that workload. Share the UI in both cases. Keep C as an optional host picker, not a distributed worker system.

How the gateway could fit the current server

You already check access upfront on the VPS, so there is no need to build Launchpad accounts, passwords or roles for this proposal. Keep the daemon private behind that gateway and serve UI, /api/ and /ws under one origin, such as https://launchpad.example.net/. Avoid putting the live client on HF while the API sits elsewhere: that introduces CORS, cookies and cross-origin WebSocket plumbing for no useful gain here.

Prototype: trusted adapter proxy

An adapter can inject the daemon bearer token upstream, present the allowed loopback Host, and map approved external Origins to the internal origin. The gateway must validate the original browser Origin for mutations and WebSocket upgrades before rewriting it, and remove conflicting client authorization headers.

Inference from auth.rs: likely workable without changing the daemon. It must be demonstrated on a separate dev instance; this report does not include a tested proxy configuration. The upstream token belongs only on the server. An ordinary reverse_proxy declaration will not handle all these checks by itself.

Daily-use version: explicit remote policy

Add a configured public origin and a trusted-proxy mode, preserving local defaults and CLI access. Prefer validating the real external origin over permanently disguising it. Keep bearer injection or a gateway-to-daemon identity; ensure the access gate covers all methods, assets and upgrades.

Browser WebSocket constructors cannot attach an arbitrary Authorization header. Gateway injection or an appropriate same-origin session mechanism solves that without embedding secrets in JavaScript. HTTPS should use Secure cookies if remote cookies are retained.

Evidence: auth.rs. Caddy supports WebSocket proxying; TLS and upstream routing are readily available infrastructure. Use a dedicated hostname initially; subpath hosting needs separate router and asset-base work.

03 / THE HARD PARTS

The browser is easy. Remote semantics matter.

Highest risk

1. “Did my launch happen?”

A phone can lose reception after the daemon accepts Launch but before the reply arrives. Retrying today can create another session: the launch endpoint receives a LaunchSpec and the core allocates a fresh UUID. Ordinary input also gets its message id on the server, not a client retry key.

Proposed fix: generate a stable operation id on the client, durably record its accepted result on the daemon, and let the phone query or retry that same operation. Reuse the existing claim-before-side-effect principles. Do not promise exactly-once external effects; ambiguous sends after a crash may still require inspection.

Disabling a button during submission handles double taps, but not a lost reply. This deserves a small focused design, not a generic distributed jobs platform.

Highest operational cost

2. The VPS is a full development machine

Register VPS paths, clone repos and install actual toolchains, build dependencies and private package access. A phone folder picker cannot register a folder from your laptop on the VPS. A VPS agent cannot use laptop-only MCP servers or desktop browser tools without deliberate connections.

Bring over committed branches explicitly. Transfer dirty changes and untracked files deliberately; Git alone does not preserve them. Preserve pre-draft worktree refs and local notes if migrating. Prefer starting with one fresh VPS project over copying the entire current state.

3. Closing a tab differs from restarting the host

Closing the browser leaves daemon-owned agents running. Restarting the daemon currently interrupts active turns; Linux harness children get a parent-death signal and the systemd unit stops its control group. A VPS reboot behaves similarly.

Do not bundle restart survival into basic remote access. First accept manual resume with honest Interrupted/Failed states and planned idle updates. If truly necessary later, scope a process supervisor/session worker design independently.

Evidence: process ownership and systemd, Phase 7 scope correction.

4. Mobile connections are temporary

Wi-Fi → cellular, screen lock and background suspension are normal. The existing client reconnects, refreshes query data and reloads stored session events; gaps have sequence-based recovery. That is valuable groundwork.

Add a visible freshness state, reconnect on foreground, heartbeat/timeout detection and a deliberate retry story. The current server handles incoming pings but does not initiate periodic application heartbeats. Live-only text/tool deltas are not a complete replay log; settled events are the recovery baseline.

Evidence: event transport and session store.

5. Native actions need a capability boundary

Open in editor, Open in terminal, New window and desktop notifications execute on the daemon’s machine. On a headless VPS they will not open something useful on your phone or laptop. Hide unsupported actions or replace them with intentional alternatives.

Proposed capability response: execution-host identity, browser-tab support, local editor/terminal availability and notification channels. A laptop browser connected to a VPS should offer “Copy SSH command” or “Open remote editor” only when configured. Terminal handoff stays out of the first mobile release.

6. Credentials and quotas belong to the host

Authenticate GitHub CLI and each harness on the VPS. Official OpenAI documentation describes device-code login and fallbacks for headless Codex. Claude supports subscription login and other credential modes, but VPS unattended operation must be checked with the installed version.

Keep Launchpad’s rule: it reads Claude OAuth credentials and never refreshes them. Harness-owned sign-in remains the supported path. API keys change billing and may not provide the same quota readings. Separate laptop/VPS daemons can share account limits without coordinating local readings.

VPS operations, without overbuilding

  • Service: one daemon under a dedicated Unix account, loopback binding, gateway in front. Configure the user service to survive logout and start at boot (or use a suitable system service). Check its login-shell environment; a GUI session should not be required.
  • Packaging: build UI then cargo build --release --locked -p launchpad. Tauri/GTK are not needed for the daemon-only target. Existing installers deploy desktop/autostart resources too; design a documented daemon-only path rather than treating the full desktop installer as a headless installer.
  • Capacity: remote models do the inference, so no GPU is required for normal hosted Claude/Codex use. A planning starting point is 2–4 vCPUs, 4–8 GB RAM and 40–80 GB SSD for a few lightweight jobs; Rust/Node builds, browser automation and concurrent agents can need much more. These are sizing hypotheses, not benchmarks or a VPS purchase recommendation.
  • Limits: manage maximum concurrency, disk growth and build memory. CPU-heavy commands can starve the daemon even if LLM requests are cheap. Containers can help isolate environments later; they are not required to prove the product.
  • Backups: preserve state.db, session/raw logs, config, repositories, Git metadata, worktrees, harness histories and necessary credentials securely. cache.db can be rebuilt. Use an application-consistent SQLite backup or stop the daemon for a copy; a raw file copy while writes/WAL are active is not a backup plan. SQLite provides an online backup API.
  • Updates: install only when agents and outstanding commands are idle. The existing updater’s main-artifact/tag mismatch is already a blocker; headless release selection is work regardless of remote UI. OS reboots still interrupt processes.
  • Time: crons use host local time. Make the VPS timezone deliberate and show the host timezone in mobile schedules; specify what happens through daylight-saving transitions. A Paris phone connected to a UTC server should not silently shift a launch.
  • Access boundary: use your existing VPS gate, including WebSocket and mutation requests. Agents can execute unrestricted commands as their Unix user; keep that user’s environment separate from unrelated VPS services. No new Launchpad login system is proposed.
Unavoidable tradeoff: a single remote host eliminates client data synchronization, but adds a network dependency to every control action. You can read cached information or save a phone draft offline; launching and stopping agents require a reachable daemon.

One backend. One web application. Several shells.

Code that should remain shared

LaunchSpec validation, send/stop/resume behavior, quota decisions, scheduling conditions, GitHub caching and publication checks, local suggestions, Markdown rendering, query hooks, context selection and state badges.

Keep responsive changes around route containers and component composition. Do not make a second mobile backend or independently recreate the “Running” predicate.

Code that can differ deliberately

Navigation, list/detail presentation, composer container, touch menus, action arrangement and native adapters. It is reasonable to write a small MobileShell beside the existing wide Shell in the same application.

A lightweight companion is a curated surface over the same services. It should not become a fork with copied feature implementations and divergent rules.

Protect the laptop experience

  1. Retain the current wide layout and spacing by default. Add narrow containers and touch variants, rather than increasing every desktop row and button.
  2. Use container/viewport breakpoints based on actual available space. At today’s default 120% zoom, fixed 200 px sidebar + 280 px agent list already consume about 576 visual pixels before any detail. The 440 px composer is another panel. Header wrapping at 480 px does not make the whole app mobile-ready.
  3. Keep virtualized long lists, memoized rows and useFlushSync: false. Choose a fixed row height for each presentation (compact desktop vs touch mobile); remeasure when presentation or zoom changes. Do not let uncontrolled wrapping change virtual row heights.
  4. Keep all five desktop zoom choices and WebKitGTK behavior. A phone reading/touch scale should be client-local; the existing daemon config zoom should not let the phone unexpectedly resize the laptop. Keep laptop preferences intact.
  5. Check Chrome desktop, Linux WebKitGTK and Android Chrome at 360/390/430 px, tablet widths, and laptop widths at every desktop zoom. Test on a physical phone: emulation cannot prove soft-keyboard, permission or lock-screen behavior.
  6. Preserve per-workspace selection and composer drafts. Browser localStorage/sessionStorage belongs to each origin and device; unsent drafts, pins and viewed markers are not automatically shared. Cross-device drafts or preference sync would need an explicit daemon-backed feature, with conflict rules.

Evidence: current fixed layout and zoom, product UI rules. No dependency split or repository split is necessary.

Details that prevent a “shrunk laptop” app

  • Navigation: a short bottom bar for Agents, Projects and Inbox, persistent Launch, and a visible workspace control. Settings remains a visible destination. Avoid a multirow desktop workspace header eating the whole phone screen.
  • Touch: roughly 44–48 px targets in the mobile presentation; no hover-only actions, no required swipe gestures. Preserve click-only controls and the existing field exceptions. The visible Send button remains usable with an on-screen keyboard.
  • Viewport: use dynamic viewport height and safe-area insets; handle keyboard resize and orientation changes. Ensure message entry and Launch remain reachable without trapping scroll behind a modal.
  • Diffs: one file at a time, unified by default, with horizontal scrolling confined to code. Keep monospace indentation; offer wrapped prose separately. Do not wrap diff rows unpredictably inside a fixed-height virtualizer.
  • Images: phone photos may be HEIC or too large; current API accepts PNG/JPEG/WebP/GIF with explicit limits. Show validation before upload and consider format conversion/compression later. Camera capture is not automatically delivered by the existing desktop paste feature.
  • Disconnected state: show last updated time, preserve unsent text, and distinguish queued locally from accepted by the daemon. Do not replay launches, messages or GitHub publication automatically from an offline service worker.
  • Host identity: “Launch on VPS” makes remote execution concrete. All code and Git views refer to that host, not whichever device is holding the screen.

A few useful extensions, after the foundation

“Needs me” view

Combine questions, quota pauses and completed outcomes needing owner attention, using recorded state. Keep the established agent groups available and do not rename Done into an invented success state.

Share a GitHub URL

A phone share action could open Launchpad’s composer with an issue or PR attached. Start with paste + a visible Add context button; add an Android share target only when useful.

Prompt now, send deliberately

Save a quick idea on the phone while offline, then inspect its project, host and quota settings before Launch when connected. Durable cross-device drafts would be a separate scoped enhancement.

06 / INSTALLABLE & ANDROID

Build the browser experience first.

An Android app can use exactly the same daemon features. The Android device should remain a client; porting the Rust daemon and coding harnesses onto the phone is a different, much harder goal.

PWA installation · TWA architecture · Tauri mobile prerequisites · Capacitor · Android WebView.

Recommended path

Responsive web companion → optional installed PWA → Android package only if you need capabilities the browser lacks. For a personal app, a home-screen shortcut may already satisfy the “Android app” feeling without an APK.

If native integration becomes important, first evaluate a thin Tauri mobile shell because Launchpad already uses Tauri. A TWA is attractive when all you need is a package for the same hosted app. Neither requires another backend.

Remote page vs bundled UI

Loading the hosted page in a shell keeps web UI/backend releases aligned and preserves same-origin communication. Bundling assets makes app startup less dependent on the network but introduces backend-origin configuration, credential transport and release skew.

Remote content should receive only narrowly scoped native capabilities. Tauri documents explicit remote capability configuration; do not expose general native commands merely because a page has your hostname.

Tauri capabilities and remote access.

Notifications are their own feature

Current completion notifications run on the daemon’s desktop. They will not notify your phone from a VPS. Web Push requires a service worker, a browser subscription, a daemon notification channel and subscription lifecycle handling. Include deep links to the session and send minimal notification text so private code does not appear on a lock screen. Delivery can be delayed and should never be a correctness dependency. MDN describes the push subscription model.

A service worker is event-driven, not a permanently running socket client. Keep the daemon responsible for schedules and crons. Cache the UI shell cautiously, keep live state network-first, label cached views stale, and coordinate asset updates with the daemon’s existing build-id reload behavior. Android packaging does not remove sleep, network or notification permission constraints. MDN explains offline and background operation.

07 / PROPOSED SCOPE

A sequence of useful, bounded steps.

This is a candidate plan, not approval to implement Phase 7. Estimates are engineering judgment for a solo developer familiar with the repo, exclude provider troubleshooting and daily-use time, and are not measured delivery promises. Steps can overlap.

0

Pick one host and prove its environment ½–2 focused days

Choose VPS execution or laptop relay. For VPS: install the daemon, git, gh, both chosen harnesses and one project’s toolchain. Verify quota readings and a harmless real turn. Confirm required MCP tools can run without a desktop.

Acceptance: a test project launches, commits locally and reports its result headlessly; no GitHub publication, production restart or state migration required.
1

Browser access proof 1–3 focused days

Use the existing VPS access gate and a dedicated HTTPS origin. Prove upstream Host/Origin/token handling on a separate dev daemon, route WebSocket and assets, and open projects and agent state from a remote laptop browser.

Acceptance: real remote browser can launch a throwaway task, close the tab, reconnect, answer a question and inspect the result. Local daemon defaults and CLI remain intact.
2

Remote behavior you can trust 4–8 focused days

Add explicit remote policy/capabilities, host labels, submission identity and uncertain-delivery handling, stale-state UI, mobile foreground reconnect and proxy timeout checks. Document daemon-only operation, backups and recovery. Handle the existing updater source gap separately if updates are in scope.

Acceptance: lose a Launch reply and resolve it without a second agent; force a connection drop; verify tab close does not stop a task; verify daemon restart is shown honestly and never silently reruns uncertain work.
3

The smaller mobile companion 5–10 focused days

Keep shared feature logic. Add narrow navigation, project/agent list routes, Summary/Trace, full-screen composer, questions and essential GitHub detail. Defer complex code review, terminal handoff, history import and new scheduling editors.

Acceptance: on a real Android phone, choose a project, launch, lock the screen, reopen, answer, send follow-up, Stop and Resume; inspect an issue and a local agent draft. Laptop UI keeps its five zoom positions and virtualization behavior.
4

Installability, then optional notifications 1–3 + 3–6 focused days

Add manifest/icons and standalone behavior first. Scope service-worker caching and Web Push separately, including permission denial, expired subscriptions, deep links and stale asset recovery. An installed icon does not require an offline mutation queue.

Acceptance: installation works on your phone; reopening shows current daemon state. If push is selected, a notification opens the right session, and denied permissions leave the app usable.
5

Android shell only if justified Separate spike

Try TWA or a thin Tauri client against the same daemon. Do not promise a native release until signing, device permissions, access-gateway cookies, deep links and update behavior have been proven. No second backend or mobile agent runtime.

Acceptance: one concrete native need, such as sharing a GitHub URL into the composer, works more reliably than in the PWA and does not duplicate feature logic.
Practical expectation: a browser experiment is a matter of days. A dependable remote + smaller mobile experience is plausibly a few focused weeks, plus real daily use. Full mobile feature parity, push, Android distribution, restart survival and multi-host orchestration can turn this into a much larger project; they are separate choices.

What I would explicitly leave out of the first version

Multiple users, account management, a synchronized worker fleet, embedded terminal/PTY, process survival across daemon restart, offline agent execution, automatic publication, rewritten native Android screens and two-way filesystem synchronization. Existing daemon-owned quota protection, local suggestions and explicit publication rules remain the source of truth.

Minimum proposed acceptance routine

  1. Use a throwaway repository and local bare origin; no real GitHub comments, reviews, merges or publication during automated checks.
  2. Open the same host in laptop and phone browsers; show matching agent state and scope counts. Preserve device-specific selection and unsent text.
  3. Launch a harmless task on the phone, lock it, and verify execution continues. Reconnect over another network and compare stored outcome with the laptop.
  4. Answer a question, send one follow-up, Stop a running task, exercise quota pause and explicit paid override without deliberately exhausting a subscription.
  5. Lose the HTTP reply after acceptance and verify the proposed operation lookup prevents a duplicate session. Treat any crash-ambiguous external delivery as requiring inspection.
  6. Exercise restart recovery only on the dev instance. Check backup restoration into a separate environment, headless boot and a denied access-gateway request including WebSocket.
  7. Check long lists, unified diffs, image validation, soft keyboard and all desktop zoom positions. Daily-use acceptance remains necessary after these checks.
08 / DECISIONS & DRAWBACKS

Questions worth settling before coding.

Should the VPS replace the laptop, or complement it?

This drives almost everything. If it replaces the execution environment for selected projects, remote SSH editing and one daemon are clean. If it complements the laptop, use separate host state and visible selection. “Same UI everywhere” does not imply the same filesystem everywhere.

Can I reuse current sessions and local pre-drafts on the VPS?

Not by copying state.db alone. Absolute project/cwd paths, worktree registrations, Git refs, raw event files, native harness history and credentials must agree. Prefer an explicit fresh project to establish remote feasibility. Any migration should be an owner-controlled offline transfer, never two daemons opening the same database.

Would the existing laptop app be damaged by adding mobile?

It need not be. Most risk comes from changing shared layout assumptions indiscriminately: button size, global zoom, overflowing panels and virtualizer measurements. A narrow Shell with shared components keeps the wide Shell stable. Browser and Android shells should feature-detect machine integration instead of changing domain behavior.

Can the phone publish a PR or a drafted review eventually?

Yes, through the same backend and explicit owner buttons, with the same head checks, idle/clean-worktree requirements and durable posting claims. That does not authorize an agent or automated check to publish. A first companion can expose drafts and local notes while leaving complex publication to the laptop.

Do I need an API versioning framework?

No for the first version: serving UI and API from the same daemon keeps them aligned. The existing hello/build-id mechanism reloads clients when the UI changes. A later bundled Android client can remain installed while the backend updates, so add targeted compatibility handling or prefer hosted UI before designing a large versioning framework.

Could Hugging Face host Launchpad itself?

This Space hosts only the static research report. It has no Launchpad daemon or credentials. An executable Space would need a different runtime, durable writable state, repository storage, harness installation, lifecycle control and suitable networking. Those needs make your VPS a more straightforward execution host. A protected Space hides repository source but serves the rendered application publicly; it is not an access gate for a coding daemon.

Could existing agent remote-control features solve it sooner?

Possibly for a narrow urgent task. Claude’s own Remote Control can continue local Claude sessions from other devices. It does not replace Launchpad’s combined projects, Codex, GitHub cache, local pre-drafts, schedules and shared quota behavior. Treat provider remote controls as an alternative for a specific session, not automatically as Launchpad’s transport layer.

Known drawbacks

Extra server operations and backups; environment duplication if local execution stays; network dependence; slower large diffs and traces; separate browser drafts/preferences; unavailable desktop hooks; credential renewal; possible shared-account quota lag; server-side scheduling timezone; interruptions on updates and reboots.

Unproven assumptions

Your gateway must support long-lived WebSocket upgrades and all API methods. Your specific VPS must run both harnesses and needed tools. Credential modes must yield useful quota readings. Real Android behavior must be checked. Effort and resource numbers above are estimates.
