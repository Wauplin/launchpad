# Harness adapters

Adapters live in the `launchpad-harness` crate (`crates/harness/`). Its `REGISTRATIONS` list in `crates/harness/src/lib.rs` is the only host list of harness identities. The contract (`Harness`, `LiveSession`, `Registration`) and the registry are in `launchpad-core` (`crates/core/src/harness/mod.rs`); the `launchpad` binary hands the list to the core at startup (`launchpad_harness::install`). The core never names an adapter. Claude Code, Codex and OpenCode are registered integrations. Pi is intentionally left for a follow-up that checks this boundary in practice.

## Files to change

1. Add `crates/harness/src/<name>.rs`, with private protocol helpers and an SVG asset if needed.
2. Declare the module and add its `REGISTRATION` to `REGISTRATIONS` in `crates/harness/src/lib.rs`.
3. Run `cargo run -p launchpad -- gen-types` when changing shared metadata types. Registering an adapter alone does not change the shared types.

A registration contains an ID (`HarnessKind::new("stable-id")`), display metadata, integration capabilities, documented environment variables (`env_vars`), the variables that select another subscription login (`account_env`, for example `CLAUDE_CONFIG_DIR`) and preset profiles (`profile_templates`, each with a `ProfileKind`: subscription, API key or provider) for Settings → Profiles, an adapter factory and an inherited-environment-marker predicate. The ID is stored in sessions, launch specs and schedules. IDs must be unique; unknown IDs fail explicitly. Native conversation IDs remain opaque strings. Assets live beside the module, with their source/license recorded in `crates/harness/src/icons/README.md`.

`Harness` is the adapter contract. Only startup and version discovery are required; defaults for optional hooks return empty discovery, no services/title request, or a clear unsupported error. Set capabilities only for hooks actually implemented. For cost-reporting adapters, `cost_model_prefixes` restricts pricing to supported model families (empty means unrestricted). Never forward fallback prices for unknown models: set `Usage.cost_unavailable` and clear `cost_usd`; the host retains tokens, disables cost management and warns the owner. The factory can own native processes and routing state, as Codex does (one app-server per distinct session environment, so one per contained session, shut down when its last session is dropped); it can also be stateless and create one process per session. Native messages that change state (turn ends, command completions, requests) must never be dropped: deliver them in order through a lossless queue, never a broadcast channel that skips on lag.

## Native behavior belongs in the adapter

- `start`: create or resume the native conversation from `StartSpec`, set its ID/model through `Sink`, and return a `LiveSession`.
- `LiveSession`: implement input and delivery acknowledgments, interruption, structured answers and final process stop. `turn_active` covers a turn waiting for input too. `ready_for_turn` must remain false until outstanding commands and questions settle. A silent command is still running. Expose `has_open_questions` if multiple requests can be pending. Optional `set_model` applies model/effort overrides from the next turn; return false to have the host replace the idle process with a native resume on the next input. Optional `idle_release` returns how long the process may stay between turns: once the session is Done, Stopped, Interrupted or Failed for that long, with no open question, quota pause, capacity retry, active turn or background work, the host releases it (`Sessions::release`, the same path as before a move) and the next input resumes the conversation. Codex uses 10 minutes for a session's own app-server. Tool-call events upsert metadata by item ID when native inputs/titles arrive later. Emit final messages and `TurnEnd` before the final status; preserve Stopped/Interrupted on cancellation.
- `skill_locations` / `skill_instruction`: declare ordered project/global/config roots for prompt completion and render explicit invocation. Profile and host configuration is resolved by the shared read-only discovery service; keep vendor directory names and invocation behavior in the adapter. The current fallback reads selected `SKILL.md` files explicitly; native slash dispatch requires transport-specific validation.
- `models`, `defaults`, `efforts`, `version`: read native discovery. Never read the machine's own harness settings or history (`~/.claude`, `~/.codex`) for defaults: a session's model comes from its profile or launch spec, and no adapter reports defaults today. The host polls model lists independently so one missing executable does not block other integrations. Version errors appear beside the harness in the status bar.
- `spawn_services`: start notification routing or updates. Publish version data through `StatusHandle::update_harness(ID, ...)`.
- `spawn_quota`: poll the included quota of one subscription login (`quota::QuotaAccount`: its key and its `account_env` values; Home runs it with its own copy of each vault login, `vault::login_home`) and publish it with `StatusHandle::update_quota(&account.key, ...)` or `quota_error`. The host calls it once per login used by a subscription profile and aborts the returned task when no profile uses it; do not put provider parsing or daemon-owned native process fields in `App`.
- `terminal_command`/`terminal_env`/`terminal_resume_markers`: return an argument vector, native environment overrides and markers identifying the native resume command. The host resolves the executable and opens the integrated terminal on the runner, in the session's jail.
- `project_moved`: relocate native path-dependent history in the session's harness home when a temporary folder is kept as a folder (moved and renamed), if necessary.
- `native_trace` / `restore_native`: export the session's native conversation files unchanged for the handoff to Home, and put them back on the runner that adopts the session after a move (or starts it after Archive). Never synthesize a conversation from events. A harness whose conversations live in its own database restores at the next start, in the session's jail and folder: OpenCode's `restore_native` only checks the export and writes it unchanged to the harness home, and its `start` runs `opencode import --pure <file>` first; any other output fails the start visibly, and `native_trace` returns the waiting file while it is not imported.
- `title_command`/`title_response`: optional auxiliary title request, used at launch and after each turn with bounded root conversation context. Adapters should select a small model and minimal effort. The host runs one initial request at a time per session, retries a failed one after 1, 4 and 16 minutes and then keeps the prompt title, cuts a reply to its first line (80 characters), handles timeout and subscription protection, and adds the cost the reply reports to the session usage (and so to the profile's spending ledger), also when the request failed or the title was unusable. `title_response` reads the output of a failed process too; set `TitleReply.error` for a native failure that still reports its cost. Codex parses its event stream and reports no cost; Claude reads `--output-format json` and returns `total_cost_usd`. With no hook, the local prompt-based title stays.
- `environment_marker`: remove only inherited session markers that should not reach another process. Credentials and normal native configuration stay in the user's environment.
- `contained_memory`: turn the harness's own memory off in a contained session's harness home and install the given knowledge base instructions as its user-level instructions (Claude Code: `CLAUDE.md`, `autoMemoryEnabled: false`; Codex: `AGENTS.md`, `[memories]` off; OpenCode: `AGENTS.md`). Harnesses save their conversations and history normally in a contained session's harness home. `native_memories` lists the harness's own memory folders on a runner, for the one-time import.

The host owns persistence, prompts, project/worktree creation, scheduling, quota holds and publication guards. Normalize protocol output into the existing event model rather than exposing protocol-specific fields to React. A genuinely new interaction may require extending the shared contract; adding a harness with existing interactions should not.

## Reusing ACP

OpenCode is the first consumer of `acp::start(command, spec, sink, extensions)` (`crates/harness/src/acp.rs`). Its module supplies native child-update capabilities/translation and delegation-tool identification through `acp::Extensions`, as well as `opencode acp` with the correct working directory/environment, CLI model/version discovery, metadata and terminal resume arguments. The reusable client handles stdio JSON-RPC v1, negotiated new/load/resume, model config options, text/images, ordered updates, tool completion, permission cards, cancellation and transport failure. It advertises no client filesystem or terminal services: the harness runs its own tools.

ACP permission responses select an advertised option; arbitrary typed answers are rejected. Image support is checked against the negotiated agent capability as well as the static integration descriptor; a selected model may still reject an unsupported image. ACP tool output snapshots are converted to incremental output, and reported before/after texts become unified diff previews. Native agents may report only the replaced fragment; the Git panel remains the source for full-file diffs. Reported USD usage is cumulative, without claiming that the provider billed that amount.

Current OpenCode limits are explicit: no messages while a turn is running, effort override, auxiliary AI title, subscription quota monitor or hard spending cap. Native configuration, credentials, model defaults and permissions remain OpenCode's responsibility. Profiles pass environment overrides through `StartSpec.env`; adapters must apply them to every native session process. The host resolves profile defaults and billing, and `capabilities.cost` enables limits based on cumulative reported USD usage. Claude and OpenCode support this; Codex does not report dollars. SSH and billing ledgers remain deferred.

## Checks

While working, `cargo check --all-targets` rebuilds only `launchpad-harness` and the binary. Before committing, run strict workspace Clippy, UI typecheck/build and the existing short pure-function tests. Exercise the installed native process through an isolated dev database: launch, stream, follow-up, permission answer, stop, archive and resume. Inspect the composer and session controls for capability handling. Do not mock harnesses, publish GitHub items, restart production or start uncancelled test schedules/crons. Keep native behavior gated appropriately for supported operating systems.

## Native subagents

Emit `Subagent` metadata with the reported native ID and direct parent, then normalize each child's events through `sink.child(id)`. Child sinks preserve the root session ID and sequence while wrapping events; they must not update root usage, model, identity or preview text. Root-facing native questions still use the root answer routing. Include observed child turns/tools in `ready_for_turn` and interruption; never infer completion from silence. Persist only reported states and show unavailable traces honestly. The UI consumes the shared envelopes without harness identity branches. OpenCode's optional ACP child extension stays in its adapter; older versions can expose delegation-only records, which native records supersede.

## Permission modes

Claude and Codex advertise `capabilities.permission_modes`. The composer offers **YOLO** (initial default), **Ask for approval**, and **Auto approval**. The launch spec stores `permission_mode`, including for scheduled launches; old specs deserialize to YOLO. Successful launches restore defaults independently for each harness/profile, like model and effort. A deliberate mode selection is also remembered immediately on that browser, before launch. Restored unsent drafts retain their own mode.

Claude uses `--permission-mode auto` for its native AI classifier or `--permission-mode default` for manual approvals, with `can_use_tool` requests sent to explicit approval cards. Codex uses `approvalPolicy: untrusted` and `sandbox: workspace-write`; safe reads and operations allowed by native rules may proceed without prompting. Codex Auto uses `approvalPolicy: on-request`, `approvalsReviewer: auto_review` and `sandbox: workspace-write`; manual approval explicitly selects `approvalsReviewer: user`, independently of native configuration. Auto startup/resume checks the returned reviewer and fails visibly if it was not enabled. Native account, model and managed policy restrictions still apply; Claude reports a visible notice if initialization selects a different mode. YOLO keeps the previous bypass flags/policies. Resume and terminal handoff carry the saved mode. OpenCode continues to use its native permissions.

Approval cards show the requested tool input, command, working folder, reason or proposed file changes where supplied. They appear in Trace, Summary and Today, with explicit choices and touch-sized buttons. Codex offers session approval when the native protocol permits it. Typed replies cannot grant permission; invalid or stale choices are rejected. Cancellation, archive and process exits settle requests, and child requests route through their parent session. Explicit Cancel turn decisions use `LiveSession::answer_stops_turn` so the host treats them as silent owner stops. Approval waits are silent under the existing notification policy.

Codex native `item/autoApprovalReview/started|completed` events become distinct **AI approval review** tool cards, with the reported action, decision, risk and rationale; native reviewer warnings become notices. They do not ask the owner to approve the AI review itself or create normal coding-agent records. Human-only native requests continue to use permission cards. Auto is native AI review, not Codex's `--full-auto` preset or Launchpad automatically accepting permission requests. See [Codex Auto-review](https://developers.openai.com/codex/concepts/sandboxing/auto-review) and [Claude permission modes](https://code.claude.com/docs/en/permission-modes).

Permission modes are editable in the session header on laptop and phone, as well as the Summary. `POST /api/sessions/{id}/permissions` persists the choice for this conversation and native resume/terminal handoff. A running turn is interrupted as an owner action, then resumed with the same native conversation ID and a continuation message after its outstanding commands settle. Pending requests are cancelled rather than granted; the agent reconsiders the action under the new native mode. Idle/archived sessions use the new setting on their next turn. This reuses native startup/resume enforcement rather than assuming a settings update changes an already-running turn. Quota, cost, publication, setup and terminal guards still apply; background commands must finish before replacement. If interruption does not settle within 20 seconds, the mode is unchanged and the owner can retry once idle. Agents never grant permissions: `agent_auth::permission_guard` refuses an agent's `session.answer` of a request whose question has `permission: true` (and of an unknown request), and an agent's `session.permissions` that is not stricter than the current mode (`PermissionMode::strictness`: YOLO, then Auto, then Ask for approval). OpenCode keeps native configuration.
