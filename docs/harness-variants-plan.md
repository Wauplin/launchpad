# Harness profiles (formerly variants) and reported-cost limits

Owner-selected follow-up on 2026-10-10: implement variants/settings and PAYG budgets after the harness registry work. Pi and SSH/remote agents are excluded.

## Scope

Settings → Harnesses configures named variants of registered local harnesses: a stable ID, display name, environment overrides, default model/effort, subscription or PAYG billing, and an optional default USD cost limit. Variants inherit the base icon. Environment values stay in config.toml and are applied to native processes and terminal handoffs; sessions, schedules and crons persist only the variant ID. Missing variants fail visibly on startup. Existing processes keep their startup environment until reattached. Model discovery and subscription quota monitoring still use the base account; alternate accounts should use PAYG mode because their quota is not monitored.

The composer prefills the variant cost limit and allows no limit. Claude/OpenCode sessions expose cost-limit editing in Summary and progress in the header. Cost limits persist with the session and gate messages, question answers and quota continuation at cumulative reported USD cost. The daemon asks active turns to interrupt best effort. Raise or remove a limit to permit manual continuation; changing the limit sends no input. Codex cannot enforce USD limits because its protocol does not report dollar cost. Claude reports at turn end, and resumed process totals are added to earlier reported cost. OpenCode reports native cumulative session usage through ACP. Missing or delayed costs cannot enforce an exact provider spending cap, and commands may finish after interruption. Terminal TUIs and external activity are outside the guard. PAYG and limited sessions keep prompt-based titles to avoid extra unaccounted naming requests.

No billing ledger, automatic pricing estimates, remote transport, Pi integration or custom icon upload is included. Config saves are validated and use mode 0600 on Unix; Windows relies on the user's profile permissions.

## Profiles: every harness setup, several subscription accounts (2026-10-22)

Owner request: make the variants section collapsible, manage the default Claude Code / Codex / OpenCode subscription setups the same way as variants under a clearer name, make subscription setup obvious, and settle how profiles behave on SSH hosts. Owner decisions: the name is **Profile**; no built-in profiles; support several subscription accounts at a time with their own quota protection; credentials may be sent to SSH hosts when a profile allows it; rename `LAUNCHPAD_PROFILE` to `LAUNCHPAD_ENV`; no backward compatibility needed (old `[[variants]]` files still load anyway).

- Settings → Profiles: one collapsed row per profile (harness icon, name, what pays, model, quota or spending, a status dot per machine) that expands into Name, Harness, Billing, model/effort/provider, cost and spending limits, **Works on** and a closed **Advanced** section (environment, model list URL, Send credentials to SSH hosts). New, unsaved and invalid profiles open automatically. **New profile** asks how the work is paid (subscription login, API key, another provider, custom) and then lists the matching adapter templates: Claude Code · Subscription / Another account / API key / Hugging Face, Codex · ChatGPT subscription / Another ChatGPT account / OpenAI API key, OpenCode. A GitHub CLI card replaces the old Sign-in card.
- Composer: the Profile row lists only profiles, with a Manage profiles link; a draft without a profile takes the first profile of its harness, and with no profile at all the composer links to Settings.
- Quota per login: a login is the harness plus its `account_env` values (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`). Each login used by a subscription profile has its own monitor, reading (`Status.quotas`), status-bar meter pair (labeled with its profile names when a harness has several logins), phone sheet entry, dashboard row and Analytics history, and sessions are held, paused and continued on their own login's reading.
- Works on: this computer's sign-in check per profile and each host's `profile:<id>` check, with Install and Sign in buttons that run the adapter's fixed command with the profile environment in a visible terminal (account folders created first), and Check again.
- SSH hosts: profiles are global. `~/` expands to the home folder of the machine that runs the process; `${NAME}` is resolved by the host from its own login shell unless **Send credentials to SSH hosts** is on, which resolves it on this computer and sends the value. Literal values are always sent; sign-in files never are. Profiles not ready on a project's host are disabled in the composer with the reason.
